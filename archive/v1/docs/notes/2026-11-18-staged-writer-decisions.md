# Staged writer: API and the decisions taken while implementing ADR-007 (M0 WP3 / M1)

- Date: 2026-11-18
- Author: Mohamed (T2)
- Reviewer requested: Adham (T1); Ahmed (T5) for the CLI items marked T5
- Backlog: B-006, B-008, B-009, B-012
- Status: implemented on master (commits 69108bd to 0ef8746). The decisions below are open for T1 review for one sprint (AGENTS.md §7). Changing any of them is a follow-up commit, not a revert.

This note replaces the writer API pairing that was planned for 2026-10-29 and did not produce a written record. It answers the six questions at the end of [the WP1 inventory](2026-10-24-unsafe-write-paths.md) and lists where the implementation differs from the wording of ADR-007.

## 1. API (`internal/output`)

| Type / function | Purpose |
|---|---|
| `Policy{Protected []Protected}`, `Policy.Check(dir)` | Refuses an output dir that equals or contains a protected dir (config, contract, working dir; home and the filesystem root always), or that already holds `.veld` files. Uses canonical absolute paths, symlinks resolved, and a trailing-separator prefix test that is case-insensitive on Windows and macOS. |
| `NewSession(policy)`, `Session.Stage(dir)` | Creates a staging root under the system temp dir. `Stage` checks the policy and returns a staging dir that keeps `dir`'s base name. |
| `Session.Plan(Options)` | Compares the staged files with disk and the previous manifest: Create, Update, Unchanged, Delete, Keep. Returns `*ConflictError` (and plans nothing) when a staged file would overwrite an unmanaged file with different content. Reads only. |
| `Plan.Apply()` | Writes each file atomically (temp file and rename), deletes stale managed files and the directories they leave empty, then writes the manifest. On failure it writes a recovery manifest of the old entries plus everything written so far. |
| `Clean(dir)` | Deletes manifest-listed files whose hash still matches, the directories that leaves empty, the manifest, and the dir itself only if it is then empty. |
| `ReadManifest(dir)`, `ManifestName`, `ManifestVersion` | Manifest v1, size-capped, every path validated (clean, slash-separated, `filepath.IsLocal`). |

The CLI host is `generate()` in `cmd/veld/stagedgen.go`. `generate`, `watch` and `ci` all go through it, and it is the only code that commits output.

## 2. Answers to the WP1 questions

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Refuse an `out` inside the config dir that contains `.veld` sources? | **Yes**: any output dir that already contains a `.veld` file is refused, wherever it is. An `out` inside the config dir without contracts (the `veld init` default `veld/generated`) stays allowed. | With a manifest it is no longer destructive, but generated files could still collide with contracts, and the LSP would index them. |
| 2 | Migration: existing output has no manifest. | In a directory **without** a manifest, an existing file that would be overwritten is adopted if its first 512 bytes contain `AUTO-GENERATED BY VELD` or start the generated README (`# Generated by Veld`); identical content is always adopted. Anything else is a conflict and needs `--overwrite-unmanaged`. Once a manifest exists, adoption is off. | No user-visible break for projects generated by older Veld, without trusting arbitrary user files. Verified by hand: old-binary output plus a user file, then the new binary: everything adopted, user file kept. |
| 3 | Generated `README.md`. | Kept, as a managed file. Its text now says user files are never touched. It is written only into the entry's own backend/frontend dirs; before, each workspace entry wrote its README into every workspace directory. | Users rely on it; the manifest makes it safe. |
| 4 | `tsshared` files when backend and frontend share a dir: which emitter owns them? | Ownership is per **directory**, not per file. Both emitters write into the same staging dir (the second overwrites the first, as before), and the manifest records the emitter list for the dir. | Per-file ownership needs emitters to return files (M2). Nothing is lost for safety, because deletion is decided by manifest membership and hash, not by owner. |
| 5 | Exit codes (with T5). | **Not settled; T5.** Every refusal (unsafe path, unmanaged conflict, `clean` without a manifest, `init` on existing files, `--strict`) currently exits 1 with a message naming the paths. The acceptance tests assert only non-zero, so B-046 can assign numbers later without touching them. | B-046 owns the taxonomy. |
| 6 | Failing tests: build tag or merged with B-006? | Build tag until the last fix, then removed (772232e). All 9 tests run in the default `go test ./...`. | Kept master green at every commit. |

## 3. Where the implementation differs from ADR-007's wording

1. **Staging location (§2).** The ADR says `<out>.veld-staging-<pid>` beside the output dir. Staging is under the system temp dir instead, because (a) `--dry-run` must not create anything in the project, (b) a killed run must not leave a staging folder in the user's repo, and (c) an `out` next to the config dir would put staging next to the contracts. Atomicity is kept by writing each file through a temp file **in the destination directory** and renaming it.
2. **Hand-edited stale files (§2).** The ADR deletes every file in the previous manifest that is not regenerated. The implementation deletes it only if its hash still matches the manifest. A file edited since generation is kept, dropped from the manifest, and reported (`keep` in `--dry-run`, a warning otherwise). `veld clean` follows the same rule.
3. **Emitters still write files (§1).** The ADR has emitters return `[]OutputFile`. In M1 they still call `os.WriteFile`, but only into the staging dir they are handed, so the safety guarantees hold for all 20+ emitters at once. Returning files is part of the M2 IR migration (T2 M2 task "route all built-in emitters through the safe writer"). Until then, `EmitOptions.DryRun` is always false for emitters and should be deleted at that point.
4. **`--dry-run` output (§6).** It lists files to create, update, delete or keep per resolved absolute output dir. A content diff is not printed yet.
5. **`--verbose` (§5).** There is no `--verbose` flag. Resolved absolute paths appear in `--dry-run`, in every refusal message and in the `clean` output. If T5 adds `--verbose` under B-046, it should print `Session.Dirs()`.
6. **Manifest fields (§3).** `irVersion` and `langVersion` are not recorded because there is no IR or language version yet. Adding them means bumping `ManifestVersion` (ADR-009).

## 4. Open items for others

- **T1 (B-007):** with `runClean` gone, the lock is no longer deleted, and `--strict` / the prompt fire again (`TestOutputSafetyStrictBlocksBreakingChange` passes). The lock is saved after the commit. What remains of B-007 is the ordering inside the gate itself: `computePreChanges` parses a second time and returns nil on a parse error, so the gate is silently skipped for a broken contract. The run still fails later, without writing.
- **T1:** workspace entries resolve their config dir to the working directory (`BuildResolved` with `InputSet`), so each entry's lock and cache go to the working dir and overwrite each other. This existed before and is unchanged here.
- **T5:** exit-code numbers (question 5); the `veld init` default puts the frontend output in `veld/generated` inside the config dir (WP1 note, "default layout observation"); a Windows CI job so that `TestDeterministicOutput` runs on two operating systems.
- **Q8 owner:** the tool generators (`dockerfile`, `cicd`, `env`, `scaffold-tests`) detect the language by looking at files in the output dir. They see only the staging dir, which holds their own output. That detection was already broken before (the old `runClean` emptied the dir first), and Q8 replaces these generators.

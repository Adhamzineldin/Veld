# Target: `rust` (server and client)

Status: normative for the built-in Rust generator. It follows `spec/targets/typescript.md` and `spec/targets/java.md` semantically: the same contract gives the same wire behaviour, the same errors with the same signatures, and the same canonical bytes. One implementation of models and runtime serves both roles.

## 0. Hard rules
- **Rust 1.75 or newer** (`async fn` and `impl Future` in traits). The generated crate declares `edition = "2021"` and `rust-version = "1.75"`, builds with zero warnings and passes `cargo clippy -- -D warnings`.
- **One core dependency decision: `serde` and `serde_json`.** Rust has no JSON in `std`. The two alternatives were an embedded JSON codec (as the Java target does) or the de-facto standard. The generator takes the standard: derive-based models are what a Rust developer expects (`#[derive(Serialize, Deserialize)]`, usable with any serde format and any framework), it avoids shipping and maintaining a second JSON parser in every crate, and `serde_json::Value` is the natural type of the contract's `json` scalar. The cost is two dependencies instead of zero; they are the only dependencies of the core. Everything else (the router, validation, canonical bytes, the regex engine for `@pattern`) is embedded in the crate (`src/veld/`), so there is no `regex`, no `chrono`, no `uuid`, no `base64`, no `thiserror`.
- **Only the chosen framework is a dependency.** A server adds `axum` (`framework = "axum"`, the default). A client adds `reqwest` plus `tokio` (the `time` feature, for reconnect backoff) or `ureq` (`framework = "ureq"`). `futures-core` (the `Stream` trait, nothing else) is added only when the contract has streams; `tokio-tungstenite` and `futures-util` only for a `reqwest` client of a contract with `ws` endpoints. A server with `ws` endpoints enables axum's `ws` feature and `tokio`'s `time`.
- **Identity by signature, never by type.** Every model, enum, union and error has `const VELD_SIG`, equal to the IR signature verbatim (`spec/ir.md` §5.1). Two copies of a declaration generated into different crates are different Rust types; `same` compares signature, operation and canonical bytes.
- **Unsupported is loud.** The limits are `E0801` for a client of a contract with `ws` endpoints on the blocking `ureq` transport (it has no WebSocket client) and for endpoint rules on a `ws` endpoint (§10.2). Nothing wrong is emitted.
- Every Rust file starts with `// Code generated by veld. DO NOT EDIT.`. Output is deterministic (sorted maps, no timestamps, no absolute paths). Generated code is not rustfmt-formatted: run `cargo fmt` over it if you want, the manifest keeps a hash of what Veld wrote.

## 1. Options and layout

Options (`[server.options]` or `[client.options]`, validated, unknown keys are `E0802`):

| Option | Default | Meaning |
|---|---|---|
| `crate-name` | `<package of the first service>-<role>` | The name in `Cargo.toml`. Letters, digits, `-` and `_`, starting with a letter, else `E0802`. |
| `transport` | `reqwest` | The HTTP transport of the clients that a **server** contains for its `consumes`: `reqwest`, `ureq` or `none` (bring your own `Transport`). Anything else is `E0802`. |
| `validate` | `true` | `false` skips run-time **request** validation by default (the types are unchanged): the client's `ClientOptions` default to no validation (`validate(true)` turns it back on) and the generated hooks' `validate_requests()` returns `false`. Responses are validated only when `validate_responses()` is `true`. |

| `testing` | `false` | Server only (`E0802` on a client). `true` adds the **test handler** (`spec/rules.md` section 12.4, this document section 10.3) next to every service that has endpoint rules: `src/<package>/<service>_test_server.rs`. Never mount it in production. |

The target also has the runtime config of section 15 (`src/runtime_config.rs`) when it has settings, and its name (`target-name`, set by the core, never by the user) gives the type `<Target>Runtime`.

`framework` (server): `axum` (default). `framework` (client): `reqwest` (default) or `ureq`. Any other value, or a framework on a role that takes none, is `E0803` and the message lists the valid values. `actix-web` is not provided: a server framework is an adapter over the runtime's `Handler` (§5), and writing one for another framework is a few dozen lines against `Handler::invoke` and `Handler::ws`.

The output is a complete crate:

```
Cargo.toml                         dependencies: serde, serde_json, the chosen framework(s)
README.md
src/lib.rs                         module list; allows a few clippy lints that suit generated code
src/veld/                          the runtime (identical bytes in both roles where shared)
  canonical.rs  RFC 8785 JSON, ECMAScript number formatting
  error.rs      Error, Problem, Issue, VeldDecl, VeldValue, DeclaredError, same, Identity
  schema.rs     Schema, validation, defaults, the wire mapping, canonical bytes
  regex.rs      the @pattern engine (language.md §7.1)
  spec.rs       EndpointSpec and friends (static data)
  page.rs  util.rs  mod.rs
  server.rs     the core: router, auth, middleware, binding, error mapping, SSE, WebSocket   (server role)
  client.rs     ClientOptions, Transport, Core, SSE streams, WsChannel                       (client role, or a server with `consumes`)
  stream.rs     BoxStream, unfold, SseEvent, SSE framing and parser                          (streams only)
  transport_reqwest.rs | transport_ureq.rs                                                    (by framework)
src/prelude.rs                     prelude errors: NotFound, Internal, Unauthorized, ValidationError, ...
src/<package>/mod.rs               the modules of a contract package
src/<package>/<module>.rs          models, enums, unions, errors and constants of one contract module
src/<package>/<service>_client.rs  <Service>Client<T>, request structs, ENDPOINTS         (client role)
src/<package>/<service>_server.rs  <Service>Service, <Service>Hooks, <Service>Handler      (server role)
src/adapters/axum.rs               router(handler)                                          (server role)
src/clients/<service>/...          a self-contained client tree for each consumed service   (server role)
```
Package, module and service names become snake_case module names (`.` and `/` become `_`). Names that would clash with the crate's own modules (`veld`, `prelude`, `adapters`, `clients`, `std`, ...) get a trailing `_`.

## 2. Type mapping

| Veld | Rust | Wire |
|---|---|---|
| `string` | `String` | string |
| `int` / `long` / `float` / `bool` | `i32` / `i64` / `f64` / `bool` | number; **`long` is a decimal string** |
| `decimal` | `String` (the text is significant: `1.50` is not `1.5`) | string |
| `date` / `time` / `datetime` / `uuid` | `String` (validated by the schema; canonical form is UTC `Z` / lower case) | string |
| `bytes` | `Vec<u8>` | base64 string |
| `json` | `serde_json::Value` | any JSON |
| `T[]`, `Map<string, T>` | `Vec<T>`, `std::collections::BTreeMap<String, T>` | array, object |
| `Page<T>` | `veld::Page<T>` (`items`, `total: i64`, `page`, `size`) | `{items,total,page,size}` |
| `model` | `struct`, fields in `snake_case` with `#[serde(rename = "wire")]` where the wire name differs; reserved words are raw identifiers (`r#type`, `self` becomes `self_`) | object |
| `enum` | `enum`, variants in `PascalCase`, `#[serde(rename = "WIRE")]`, `wire()` gives the contract value | string |
| `union` | `enum` with one newtype variant per arm and `#[serde(tag = "<discriminator>")]` | object with the discriminator field |
| `error` | like a model, plus `DeclaredError`, `From<E> for veld::Error`, `Display` and `std::error::Error` | problem+json |
| `const` | `pub const NAME: i32 = 50;` (strings as `&str`); constants of other types are `E0801` | n/a |

`datetime`, `date`, `time`, `uuid` and `decimal` are `String` so that the generated crate needs no `chrono`, `time`, `uuid` or `decimal` dependency; the schema validates them and canonical bytes normalise them. Optional fields are `Option<T>` (absent on the wire, never `null`). A recursive reference is boxed. Defaults are applied by the schema when a value is decoded (`T::from_wire`, the server's binding, the client's response decoding) and when canonical bytes are computed; `readonly` fields are dropped from request bodies. A declaration named like an item of the standard prelude (`Option`, `Result`, `String`, ...) gets a trailing `_`. `#[deprecated]` is never emitted (the generated code itself uses every item); the deprecation is written into the docs.

The *typed form* (what `serde` derives produce: `long` as a number, `bytes` as an array) and the *wire form* (what travels) differ only in those two scalars. `VeldDecl::to_wire` and `from_wire` convert, applying defaults; `serde_json::to_string(&value)` is the typed form, not the wire form.

## 3. Identity, equality and canonical bytes

```rust
pub trait VeldDecl: Serialize + DeserializeOwned {
    const VELD_SIG: &'static str;
    fn schema() -> &'static Schema;
    fn to_wire(&self) -> Value;                       // wire form, defaults applied
    fn from_wire(wire: &Value) -> Result<Self, Error>;
    fn validate(wire: &Value) -> Vec<Issue>;
}
pub trait VeldValue {                                  // implemented for every VeldDecl and for veld::Error
    fn veld_sig(&self) -> &str;
    fn veld_op(&self) -> Option<&str> { None }
    fn canonical(&self) -> Vec<u8>;                    // RFC 8785, defaults applied, UTC datetimes, lower case uuids
}
pub fn same(a: &dyn VeldValue, b: &dyn VeldValue) -> bool;
```
(`veld_sig` returns `&str`, not `&'static str`: a decoded `Error` carries a signature that it read from the wire.)

- `same(a, b)` is true when both have a signature, the signatures are equal, the operation signatures are equal (errors; a value that is not an error has none) and the canonical bytes are equal. It never compares types. Two different declarations with identical fields are never the same. An error without a signature (`Error::Http`, `Error::Transport`, `Error::Other`) is never the same as anything. `same_all` compares slices element by element.
- **Across crates** every generated crate has its own `VeldValue` trait. Build `veld::Identity::of(&value)` in each crate (plain data: `sig`, `op`, `canonical`) and compare with `veld::same_parts(&a, &b)`; the fields are public, so an identity of one crate converts to the other's.
- `DeclaredError::matches(&err)` is true for this declaration from any operation; `matches_service(&err, "orders/Orders")` also fixes the service of the operation; `from_error(&err)` returns the typed value.
- Canonical bytes of a model, union or enum are `canonical(&value)` of its wire form after decoding (`spec/ir.md` §5.3) and equal the goldens in `tests/wire/`.

## 4. Errors

```rust
pub enum Error {
    Problem(Problem),          // a declared error: sig, title, status, op, data (wire form, defaults applied)
    Invalid(Vec<Issue>),       // a request that could not be decoded (validation off); answered as ValidationError
    Http { status: u16, body: String },  // a non-2xx response that is not a declared problem
    Transport(String),         // the network failed or a body was unreadable
    Other(String),             // anything else; on a server it becomes Internal without its message
}
```
- Service methods return `Result<T, veld::Error>`. `Err(OutOfStock { sku }.into())` (or `.into_error()`) is a declared error.
- **Server behaviour:** an error whose `sig` is declared for the endpoint is answered as problem+json at the declared status with `operation` set. Anything else, including an undeclared declared-looking error, becomes `500 Internal` with empty data; the original goes to the `on_error` hook.
- **Client behaviour:** a problem+json `type` that is a declared error of the endpoint is `Error::Problem` with `op` and `status` set; recover the value with `OutOfStock::from_error(&err)`. A problem with an unknown `type` and any other non-2xx response is `Error::Http`. A network failure or an unreadable body is `Error::Transport`.
- Problem+json members are written in the order `type`, `title`, `status`, `operation`, `data`.

## 5. Server

```rust
pub trait OrdersService: Send + Sync + 'static {
    fn get_order(&self, request: GetOrderRequest, ctx: &RequestContext)
        -> impl Future<Output = Result<Order, veld::Error>> + Send;   // implement with `async fn`
}
pub trait OrdersHooks: Send + Sync + 'static {
    fn auth_bearer<'a>(&'a self, token: &'a str, ctx: &'a RequestContext) -> impl Future<Output = Option<Principal>> + Send + 'a;
    fn middleware_rate_limit<'a>(&'a self, ctx: &'a RequestContext) -> impl Future<Output = Result<(), veld::Error>> + Send + 'a;
    fn on_error(&self, err: &veld::Error, ctx: &RequestContext) {}
    fn validate_requests(&self) -> bool { true }   // false with `validate = false`
    fn validate_responses(&self) -> bool { false }
}
let handler = OrdersHandler::create(service, hooks);   // or OrdersHandler::plain(service) when no hooks are needed
// A target with a runtime config (section 15) passes it last and gets a `Result`:
// OrdersHandler::create(service, hooks, &runtime)?
let app = axum::Router::new().merge(adapters::axum::router(handler));
```
- The hooks trait has exactly the hooks the endpoints need (`auth_bearer`, `auth_basic`, `auth_api_key`, `middleware_<name>`) as required methods, so a missing hook is a compile error. A service that needs none gets `plain(service)` and a `NoHooks` type.
- One request struct per endpoint holds the path, query, header and body parameters by name (the `ws` stream body is not part of it).
- `veld::server::Handler` is the framework-agnostic core: `handle(Request) -> Option<Response>` (`None`: no route), `invoke(name, Request)` (one named endpoint through the same pipeline, for frameworks that route themselves) and `ws(Request) -> Option<WsConversation>`. Routing is exact on literal segments with parameters extracted; a trailing slash is ignored; HEAD is not implicit; literal routes win over parameterised ones.
- Pipeline: match, auth (`401 Unauthorized`), middleware in declared order, bind and validate path, query, headers and body (`422 ValidationError` with `issues`), call the implementation, optionally validate the response, serialise with the declared success status. `RequestContext` has `method`, `path`, `headers` (lower case names), `header(name)` and `principal::<T>()`.
- **axum adapter** (`adapters::axum::router(handler) -> Router`): one route per endpoint at its real path (`{id}` parameters), plus the trailing-slash variant, built on `Handler::invoke`; merge it into your application. The status codes and bodies are exactly the core's.

## 6. Client

```rust
let client = OrdersClient::reqwest(ClientOptions::new().base_url("https://api.example.com").bearer(|| token()))?;
let order = client.get_order(GetOrderRequest { id }).await?;
```
- `<Service>Client<T: Transport>` is **generic over the HTTP stack**: `veld::client::Transport` is two async functions (`send`, and for streams `open` and `sleep`; `connect_ws` for WebSockets). Implement it for the HTTP library you already use and call `OrdersClient::new(transport, options)`. The generated crate includes a ready-made adapter as its framework: `reqwest` (`ReqwestTransport::with_client(your_client)` shares your pool) or `ureq` (blocking: its futures complete without waiting, drive them with `veld::block_on`).
- `ClientOptions` has `base_url`, `header`, `header_supplier`, `bearer`, `basic`, `api_key`, `validate`, `timeout` (default 30 s) and `reconnect`.
- **Base URL:** the `base_url` option and nothing else: there is no environment variable and no URL compiled into the client (`spec/runtime-config.md` section 5). A constructor without one is `Error::Transport` (`no base URL: pass `base_url` in the client options`). `runtime_config::clients` (section 15) fills it from the runtime config.
- Path parameters are percent-encoded; query objects use repeated keys for lists, keys are sorted, absent optionals are omitted.
- With validation on, the request is validated first and a `ValidationError` with `op` set is returned locally (no request is sent). Responses are decoded, not validated.
- A method without parameters takes no argument; one without a response body returns `Result<(), Error>`.

## 7. Streaming: Server-Sent Events and WebSocket

The wire behaviour is the TypeScript target's, byte for byte (`spec/targets/typescript.md` §4b, `tests/wire/streaming/sse.json`).

**SSE** (`get ... -> stream T`). The server method returns `Result<veld::stream::EventStream<T>, veld::Error>`, where `EventStream<T>` is `Pin<Box<dyn Stream<Item = Result<SseEvent<T>, Error>> + Send>>` and `SseEvent::of(item).event("tick").id("7").retry(1500)` sets the optional fields. The first item is pulled before the status is sent: an error before the first event is a normal problem+json response; after that it is a final `event: error` frame and the stream ends. The server **drops the stream** when the client goes away, so `Drop` is where an implementation cleans up. The client method returns `Result<BoxStream<Result<T, Error>>, Error>`: the HTTP call is eager (a non-2xx response is the error of the method), later errors are the stream's last item, `<name>_with(request, SseOptions)` resumes (`SseOptions::resume_after(id)` sends `Last-Event-ID`) and reports ids (`on_event_id`). Drop the stream to cancel. `veld::stream::{unfold, iter, next}` build and read streams without another dependency.

**WebSocket** (`ws "/path" name(params, body: stream In) -> stream Out`). Frames are text. Server to client: `{"data":<canonical JSON>}` or the final `{"error":<problem JSON>}` followed by a close; client to server: the bare canonical JSON. Close codes: `1008` for declared errors, validation and auth, `1011` for `Internal`, `1000` for a normal end, `1003` for a binary frame. The server method receives a `WsSession<In, Out>` (`()` marks a side with no messages): `recv().await -> Option<Result<In, Error>>` (validated; `?` on an `Err` ends the conversation with a `ValidationError` frame whose issue paths start with `message`), `send(Out)`, `close()`; returning `Ok(())` closes with 1000. Auth uses the same hooks as HTTP, from headers or, when absent, `?access_token=` (bearer) and `?api_key=`. `@header` parameters are also read from the query string. A failed auth is answered after the upgrade (problem frame, then close). A path that is not a `ws` endpoint is not routed, so the **axum adapter refuses the handshake with `404`** (it has no socket to close with `4404`). The conversation future is dropped when the client goes away. The client method returns `Result<WsChannel<T, In, Out>, Error>` connected: `send(Out)` (validated, local `ValidationError`), `recv() -> Option<Result<In, Error>>` (`None` after a normal end or `close()`), `close()`. `wss://` needs a TLS feature of `tokio-tungstenite` that the generated crate does not enable.

**Reconnect** (`ClientOptions::reconnect(Reconnect { initial_ms, max_ms, retries })`, or per call). Off by default; defaults 1000 ms doubling to 30000 ms, 10 consecutive failures. Only connection failures are retried; a typed error, an error frame or event, a normal end and a dropped channel never reconnect. SSE reopens the request with `Last-Event-ID` set to the last event id delivered, so the stream is continuous. A `WsChannel` reconnects inside `recv()` (a new socket and a new conversation on the server), queues what `send` is given while the connection is down and sends it after the reconnect; a message already written to the broken socket is lost. When the attempts run out the last `Error::Transport` is returned.

## 10. Rules (`spec/rules.md`)

Supported: `rules_invariants` (10.1), `rules_endpoint` (10.2, 10.3), `rules_transitions` (section 11) and `rules_policies` (section 12). Partial checks (`spec/rules.md` §5.4) are TypeScript only. A crate has the rules runtime when any declaration it emits has a rule; otherwise every generated byte is exactly what it was before rules existed (the runtime files carry their rule hooks in `// #if rules` regions that are removed for such a crate).

### 10.1 Invariants

- **Runtime.** `src/veld/rules/mod.rs` is the thin layer; `decimal.rs`, `instant.rs`, `num.rs` and `text.rs` next to it are the helper files of the reference evaluator (`crates/veld-rules/src/helpers`), embedded byte for byte, so generated code and the oracle run the same helper source. `rules::Violation` is the object of §7 (`to_text` writes `rule`, `path`, `fields`, `message`, `error` in that order). Evaluation errors are `Result`s (`rules::Fail`, `Res<T>`); generated code propagates them with `?` and never panics. A proven-present optional is read with `rules::some`, a decimal or instant is parsed with `rules::dec` and friends; text that is not one, or an absent "proven present" value, is `Fail::Input`. Validation rules both out, so it cannot happen on a validated value. The rule fails closed with `error: "invalid_value"`, the one `error` value outside §3.7.
- **Printer.** `crates/emitters/rust/src/rules.rs` implements `veld_codegen::ExprPrinter`. A rule is one closure returning `rules::Res<bool>`: `&&`, `||` and `implies` stay lazy, helper calls end in `?`, comprehensions are `rules::all|any|count|sum_*` over a list converted element by element (`rules::list`). Values are `bool`, `i32`, `i64`, `f64`, `Decimal`, `&str` (also uuid), `i64` (datetime and date in epoch milliseconds and days, time and duration in milliseconds) and the enum itself. `==` and ordering use the converted values (decimals by `compare`, uuids case-insensitively), never the raw strings. Anything the printer cannot express is `E0801`.
- **Per declaration with rules**: `RULE_<NAME>` constants (the rule ids, inherited rules included), `check()` (full) and `check_request()` returning `Vec<veld::rules::Violation>` for the value and everything inside it, and `impl veld::rules::Invariants` whose `check_rules` evaluates the declaration's own rules in list order on one typed value. `check_rules` carries an `#[allow]` for the lints that user expressions trip (`a >= 1 && a <= 10`, redundant comparisons).
- **Nesting through the schema.** The schema walk of the runtime works on JSON, the check functions on typed values. The bridge is one function pointer: `ModelSchema.invariants: Option<fn(&Value, Mode, &str, &mut Vec<Violation>)>`, `Some(veld::rules::run::<T>)` for a declaration with rules. `rules::check_wire(schema, wire, path, mode)` converts the wire value once with `Schema::from_wire` (defaults applied, `long` and `bytes` typed), then `walk` visits it in the order and with the path syntax of validation (`$`, `$.rows[1]`, `$.named.k`, `body.items[2]`, `.items` of a page, the arm of a union): an object's own rules first (`run::<T>` reads that one object with serde and calls `check_rules`), then its fields in declaration order. There is one walk, shared by `check()`, the vector driver, the client and the server. The cost is one extra serde read per object that has rules (depth times size), the price of keeping rules on typed values.
- **Request position.** A request body has no `@readonly` fields, but the generated struct needs them. In request mode `check_wire` first fills each absent required read-only field with a placeholder of the right shape; every rule that reads such a field is skipped, so no evaluated rule sees one. The server fills the same placeholder when it decodes the body for the handler (`Schema::from_wire` in request mode), so a body without the field, or with it, reaches the handler with a placeholder in it.
- **Errors.** `veld::Problem` gains `rulings: Option<Box<Rulings>>` (boxed so `veld::Error` stays small; the crate's `lib.rs` allows `clippy::result_large_err`). `Error::violations()` (empty when the problem document has no `violations` member) and `Error::is_local()` expose them; `problem+json` is written with a `violations` member after `data` when there are any. The typed `ValidationError` of the prelude keeps its declared shape (`issues`), so its signature does not change; read the rest from the `veld::Error`.
- **Client.** `ClientOptions::check_rules(false)` turns the local check off (default on). Before sending, a body or `query` object that passed validation is checked in request mode; on a violation nothing is sent and the call returns the `ValidationError` problem (`status` 422, `op` set) with one issue per violation (`code` `rule`, or `rule_error` for an evaluation error), the violations, and `is_local()` true. A response with a `violations` member is decoded into the same fields (`is_local()` false). A local shape-validation failure is `is_local()` too.
- **Server.** Step 5 (bound `body` and `query` object, after shape validation of that parameter) answers `422 ValidationError` with `data.issues` and the top-level `violations`. Step 8 (the success value of an HTTP endpoint) follows the rule output mode: `rules.output` of the runtime config (section 15), or `Hooks::rules_output()` in a server whose config has no such setting. `Strict` (default; `500 Internal`, no rule detail), `Audit` (sent unchanged) or `Off`; unless `Off`, the result's shape is validated first (a malformed result is `500 Internal` in `strict`; in `audit` its rules are skipped). `Hooks::on_rule_violation(&RuleEvent)` receives `rule`, `operation`, `position` (`Input` | `Output`), `outcome` (`Rejected` | `Audited`), `violation` and `elapsed_micros` (of the check). A mode other than `Strict` is printed once to stderr when `Handler::new` runs. The axum adapter goes through the same core.
- **Declared errors are outputs** (`spec/rules.md` §5.2). Wherever the server encodes a declared error (the HTTP response, the final `event: error` of an SSE stream, the error frame of a WebSocket: all go through one function of the core) it checks the error's data like a result, under the output mode and with the path root `$`: `strict` answers `500 Internal` with no rule detail and no `violations` (the original goes to `on_error`, the violation to `on_rule_violation` as position `Output`, outcome `Rejected`), `audit` sends it and reports it, `Off` skips. A client never checks an error it decodes (`violations()` stays empty).
- **Stream items are outputs.** Every item of an SSE stream and every message a server sends with `WsSession::send` is validated and checked under the output mode before it is written. `strict`: it is not sent. The check is an `Err` of the item step, so the stream ends as on any server failure: a violating first SSE item is a plain `500 Internal` response, a later one the final `event: error` with `Internal`, and `send` returns `Err` into the implementation, whose `?` ends the socket with an `Internal` error frame and close code 1011. A WebSocket session reaches the server's hooks through the handler it was created by (`WsIo` holds the core behind a private trait), so the generated service trait is unchanged.
- **Client messages on a WebSocket are inputs.** `WsChannel::send` checks the message in request mode after the shape check, with the path root `message`, under the same option (`check_rules(false)`, `validate(false)` and the digest rule of 10.2 apply); a violation returns the local `ValidationError` before anything is written. `WsSession::recv` rejects a violating message the way it rejects one of the wrong shape: `Err(Error::Problem(ValidationError))` whose problem carries `data.issues` and `violations` (path root `message`), so the conversation ends with that frame and close code 1008; the hook gets position `Input`, outcome `Rejected`. `problem_of` keeps the `violations` of every problem that has them, which is also how a failed `require` and a rejected message reach the wire.
- **Request validation turned off** (`validate = false`, or `Hooks::validate_requests()` returning `false`): step 5, the check of WebSocket messages, the local check of the client and every endpoint statement but loading the facts, the policies and the transition guard are off (`spec/rules.md` §5.3). `Handler::new` prints once to stderr that the rules of bodies, query objects and messages are not enforced, when the service reaches rules (`Endpoints::reaches_rules`, a constant of the generated dispatch). Generation reports `W0904` through `Generator::warnings` for such a target that emits a declaration or an endpoint with rules (`crates/emitters/rust/src/warn.rs`).
- **Tests.** `crates/emitters/rust/src/rules/tests.rs` (exact printer output for every expression kind and operand type, and for the roots of a block), `tests/rules.rs` (the 101 non-partial vectors of `tests/rules/core` through generated crates and a generated driver, plus `cargo clippy -D warnings` on them), `tests/rules_http.rs` (a snapshot of the bookings contract and the HTTP round trip of `tests/toolchain/rust/rules-harness`, with a server whose validation is off), `tests/rules_extras.rs` (`W0904`; `tests/toolchain/rust/rules-live-harness`: a declared error, SSE items and WebSocket messages in both directions in `strict`, `audit` and `off`; the `422` golden of `tests/wire/rules` through `tests/toolchain/rust/rules-golden-harness`: the generated server's answer, canonicalised with RFC 8785, equals `problem.json` byte for byte).

### 10.2 Endpoint rules and the rules digest (`spec/rules.md` §9)

A crate has the endpoint-rules runtime (the `// #if endpoint_rules` regions of `src/veld/server.rs` and `src/veld/rules/mod.rs`, a sibling of `rules`; it switches `rules` on) when a **served** service has an endpoint with statements. A contract without an endpoint block gets exactly the bytes it got before, and one with invariants only does not get the endpoint-rules regions. A **client** crate never has them: it enforces no block, so for a contract with endpoint rules `src/veld/rules/mod.rs` differs between the two roles (the one exception to "the shared runtime is the same bytes in both roles"). The printer (`src/rules.rs`, `RustPrinter::for_block`) reads a parameter from the typed request (`p.body.guests`), a fact from its local (`(*fact_room).capacity`), the result from the typed success value (`(*r).status`) and `now` from the clock reading (`i64` milliseconds); an optional parameter or fact is read through `rules::some` and tested with `.is_some()`. `old(e)` reads the same names from the copy that step 6 saved (`old_p`, `old_fact_<name>`). **Choice:** the operand of `old` is evaluated when its `ensure` runs, from that copy, not at the end of step 6; the copy is taken before the handler runs, so the value is the same, and an `old` that fails with an evaluation error fails exactly the `ensure` that reads it (the reference evaluator saves the error, with the same effect). The principal is read from the local `principal` (section 12). Printing is generation-time: an expression the printer cannot express, a computed date, time or collection used as a fact key or as an `else` payload value (read the field itself: a bare path is cloned or serialised as it is), and an endpoint rule on a `ws` endpoint that a server serves are `E0801` (a client of such a contract generates).

- **Facts.** For each endpoint with facts, `<Endpoint>Facts` (`room: Room`, `coupon: Option<Coupon>`) next to the request struct. The service method takes it after the request: `fn create_booking(&self, request: CreateBookingRequest, facts: CreateBookingFacts, ctx: &RequestContext)`; an endpoint without facts keeps its signature. For each service with facts, one loader trait, `<Service>FactLoaders`, with one method per entry of `Service.facts` (`fn room(&self, key: String, ctx: &RequestContext) -> impl Future<Output = Result<Option<Room>, veld::Error>> + Send`; a fact without a key takes only `ctx`). `Ok(None)` is "not found"; an `Err` is answered like an error of the handler. The handler of such a service is built with the loaders, which the type system requires: `<Service>Handler::create(service, hooks, loaders)` and `plain(service, loaders)`. The facts of step 6 are added to the bound arguments, so the dispatch decodes the request and the facts from the same map.
- **Step 6** (`pub async fn step6_<endpoint>`, generated, `#[doc(hidden)]`, called by `Endpoints::prepare`): one clock reading (`Hooks::clock(&self, ctx) -> SystemTime`, default the system clock); the facts in declaration order (the key is evaluated as a closure over the parameters and the facts before it; a required fact that is not found is `404 NotFound` with `resource` set to its name; an optional fact whose key reads an absent value is absent and its loader is not called: the key closure reads through `rules::absent`, whose `Fail::Absent` means "no fact"); then every `require` in source order, the first failure ending the request. With `else E`, the answer is `E` built from the payload (typed JSON by wire name, defaults applied by the schema, `rules::else_rejection`), carrying the one `violations` entry (`path` `request`, `fields` the parameters read, the message or `precondition failed`/`violates rule <name>`, `error` for an evaluation error). Without `else`, `422 ValidationError` with one `rule` issue (`rules::request_rejection`). An `else` payload that cannot be evaluated, or an error that breaks its own invariants, is `500 Internal` and the violations go to the hook as position `Output`. `Halt` is what step 6 returns instead of a `Prepared`: `Error`, `Broken` or `Early`. Step 6 reports the violations of its error to `on_rule_violation` as position `Input`, outcome `Rejected`.
- **Step 9** (`pub fn step9_<endpoint>`, called by `Endpoints::ensure` from `success()` after step 8 and before the response is validated): every `ensure` in source order on the typed success value, under the output mode (`strict` `500 Internal` with no detail, `audit` the hook only, `Off` skipped); position `Output`. An unnamed `ensure` says `postcondition failed`. What step 9 reads (the typed request, the facts when an `ensure` reads one inside `old`, the clock reading) is kept in the `RequestContext` by step 6 as an opaque `Prepared`.
- **Request validation off:** step 6 loads the facts, runs the policies and the transition guard (sections 11 and 12) and no `require` (nothing saved), step 9 does not run.
- **The rules digest** (`spec/rules.md` §9.7). For every service with a `rules_digest` (so for invariants-only contracts too; this is the one place the Rust target differs from the TypeScript one, which sends it only with endpoint rules): the server core stamps `Veld-Rules: <digest>` on every response of a matched endpoint, errors and the dry-run answer included (a request no route matches gets none; a WebSocket upgrade has no response header to carry it). The generated client calls `Core::with_digest(service, digest)`. It keeps the digest of the last response per client (shared by its clones), **rejects locally only while that digest equals its own**, sends anyway before its first response and after a response without the header, stops its local checks (bodies, query objects and WebSocket messages) on a different digest, and calls `ClientOptions::on_contract_mismatch(|m: &ContractMismatch| ...)` once for every digest it had not seen, with `m.service`, `m.client_digest` and `m.server_digest`. A WebSocket upgrade shows the client no digest, so a client whose first call is a WebSocket sends its messages until some response has shown the digest.

### 10.3 The test handler (`testing = true`, `spec/rules.md` §12.4)

`src/<package>/<service>_test_server.rs` (registered by one `pub mod` line in the package's `mod.rs`; nothing else of the crate changes with the option, the production module and `src/veld/` are byte-identical, and no file other than this one mentions a test header). ## 11. State machines (`rules_transitions`, `spec/rules.md` section 10)

The runtime pieces sit in `// #if guards` regions of `src/veld/rules/mod.rs` and `src/veld/server.rs`, sibling regions of `endpoint_rules`: they exist only for a **server** with an `allow` or a `transition`, and come on top of `endpoint_rules`. A contract without either gets the bytes it got before.

- **Helpers (client and server).** An enum with at least one `flow` gets `pub const fn next_states(self) -> &'static [Status]` (the states that can follow, in declaration order of the edges; a final state has none) and `pub const fn is_final(self) -> bool`. An enum without flows is unchanged.
- **The guard** is in step 6, after the facts and the policies and before the first `require`, and it runs when request validation is off (`validate = false`) too. It reads the typed fact (`fact_booking.status`); when the state is not one of the sources it answers `409 InvalidTransition` through `veld::rules::refusal` with `field` (the wire path inside the fact), `from` and `to` (wire values) and one violation: `rule` is the transition id, `path` `request`, `fields` empty, `message` `violates rule transition`. The hook gets position `Input`, outcome `Rejected`.
- **The transition handed to the handler.** The service method takes `transition: veld::rules::Transition<Status>` (`field: String`, `from: Status`, `to: Status`) after the facts and before the context. Step 6 puts it into the bound arguments under the key `transition` (the generated dispatch reads it back with `veld::server::decode_key`). The doc comment of the method and of `Transition` say that this is a guard, not an atomic guarantee, and that the handler must write conditionally and answer `InvalidTransition` itself when the row has moved on.
- **The target check** is in step 9 after the written `ensure` statements, when the success type is the fact's own declaration: `strict` answers `500 Internal`, `audit` reports to the hook, `off` skips it, and request validation off skips it. Its violation message is the reference evaluator's (``the result must hold the state `paid` in `status`, found `pending` ``). Step 9 exists for an endpoint that has an `ensure` or this check.
- **`can_<endpoint>`** (section 12) also covers a transition: `matches!(booking.status, Status::Pending | ...)`.
- An optional fact, or a path through an optional step, as the object of a `transition` is `E0801`.

## 12. Policies and the principal (`rules_policies`, `spec/rules.md` section 11)

- **The principal.** For a service with a principal that some endpoint reads or calls a policy for, each auth hook of `<Service>Hooks` returns `Option<User>` (the generated type of the principal's model) instead of `Option<veld::server::Principal>`; the dispatch wraps the value with `Principal::new`, so the runtime is unchanged. Step 6 of an endpoint that reads the principal starts with `let Some(principal) = ctx.principal::<User>() else { ... }` (a missing principal is `500`), and an `ensure` that reads it gets a clone in the saved state. A principal that nothing reads changes no bytes.
- **Policy functions** (client and server). For every policy that an `allow` of the generated services names, a module `<contract module>_policies` in the policy's package (`_` is added when a contract module has that name) has `pub fn manage_booking(user: &User, booking: &Booking) -> bool` (reads the system clock, `veld::rules::system_now_ms`) and `pub fn manage_booking_verdict(user: &User, booking: &Booking, now: i64) -> Result<(), String>`: `Ok` when the policy permits, else the denial text. Every parameter is a reference. The verdict function evaluates the `forbid` clauses first, in source order (the first true one ends it with its message, or `not permitted`), then the `permit` clauses. A clause that cannot be evaluated fails closed (`unwrap_or(true)` for a `forbid`, `unwrap_or(false)` for a `permit`). A policy that no `allow` names generates nothing and does not turn the rules runtime on; a parameter called `now` is renamed `now_`.
- **`allow`** is in step 6 after the facts and before the transition guard, in source order, and it runs when request validation is off. The arguments are borrowed places (`&(*fact_booking)`, `&(*principal)`, `&p.body`) or computed values (`&vr::num::div_i32(..)?`); one that cannot be evaluated denies with `not permitted`. A denial is `403 Forbidden` (`veld::rules::refusal`): the error's `message` and the one violation's `message` are the denial text, `rule` is the policy id, `path` `request`, `fields` the `reads` of that `allow`. A computed `datetime`, `date`, `time`, `duration` or collection as an argument has no developer-facing form and is `E0801` (read the field itself).
- **`can_<endpoint>`** is a free function of the client module (`<package>::<service>_client::can_pay_booking`) for every endpoint with an `allow` or a `transition`. It takes references to the facts (declaration order), the principal and the parameters that the `allow` arguments and the transition read, in that order, and nothing else. It reads the system clock, answers `false` when an argument cannot be evaluated, and never sends or rejects anything.
- **The test handler** decodes `Veld-Test-Principal` (unpadded base64url of the wire JSON) through the principal model's schema into the generated type, for a service with typed hooks; without the header there is no principal and a statement that reads it answers `500`. Other services keep the untyped `Principal::new(serde_json::Value)`.
- **`validate = false`:** the policies and the transition guard still run; `require`, `ensure` and the target check do not (`spec/rules.md` section 5.3).

## 13. Events (`spec/events.md`, phase E1)

The server declares the capability `events`. The client ignores events: the same files with and without them. A contract without events generates the same bytes as before.

- **Files.** A server that serves a service which publishes or subscribes also gets `src/veld/events.rs` (the runtime: `Transport`, `MemoryTransport`, the publish and consume pipelines) and, for each such service, `src/<package>/<service>_events.rs`. The event types, and the declarations only events reach, are in the package's `t`-style model modules with the event's signature. When the contract has no invariant that an event reaches, the crate has no `veld/rules` runtime. A service with events and no endpoints generates only its events (no `<service>_server.rs`, no framework adapter). The files do not depend on the chosen framework.
- **Publisher.** `create_<service>_publisher(transport: Arc<dyn Transport>, options: <Service>PublisherOptions) -> <Service>Publisher`. One accessor per channel (`publisher.booking_events()`), on it one `async fn` per event of the channel (`.booking_paid(&event)`), returning `Result<PublishedEvent, veld::Error>`. A failed pipeline step returns the `ValidationError` problem and sends nothing. `<Service>PublisherOptions = veld::events::PublisherOptions`: `new_id(f)`, `clock(f)` (both inject the id source and the clock), `on_rule_violation(f)`.
- **Subscriber.** `trait <Service>EventHandlers` has one method per `on` line, `fn <handler>(&self, event: <Event>, meta: EventMeta) -> impl Future<Output = Result<(), veld::Error>> + Send`. `subscribe_<service>_events(transport, Arc<H>, <Service>SubscriberOptions) -> Result<SubscriptionHandle, veld::Error>` connects every `subscribes` line under its group; `handle.close().await` stops it. A rejected message is acknowledged and reported; a handler that returns `Err`, or panics, is not acknowledged and is delivered again.
- **Hooks** (`<Service>SubscriberOptions = ConsumerOptions`, same names and shapes as Node, section 5f of `typescript.md`): `on_event_rejected`, `on_contract_mismatch`, `on_handler_error`, `on_rule_violation` (also on the publisher options). An audited rule is reported and never rejects.
- **Memory transport.** `MemoryTransport::new()` (or `with_max_attempts(n)`) implements `Transport` with section 9 of the events spec: one queue per topic and group, one delivery at a time per group so that the order per key holds, competing consumers inside a group, every group gets every message, a topic nobody subscribed to drops the message, redelivery until `Done` or until `max_attempts` (then `dead_letters()`). It needs no async runtime: `idle().await` completes when nothing is pending, `run()` returns the delivery future for an application that drives it itself, and `veld::block_on` drives a future on the calling thread.
- **Choices where the events spec is silent.** A publisher accessor per channel (not one flat method per event) so that an event on two channels is unambiguous. The envelope is canonical JSON bytes written by the generated `veld::canonical` helpers, the datetime is written by the runtime itself (UTC, `Z`, `.fff` only when the milliseconds are not zero), a `long` key is its decimal digits. Handlers are an `impl Future` trait (no `async_trait`, no dependency), like the service traits of section 5.
- **Tests.** `crates/emitters/rust/tests/events.rs`: the byte goldens of `tests/wire/events` (publish through a recording transport with the id and clock fixed, consume, hand-back), the event examples of `tests/events/bookings.veld`, two services in one process (`tests/toolchain/rust/events/process.rs`), the audited rule of `tests/wire/events/edges.veld` (`audit.rs`; the test that catches a missing report call is `the_edges_crate_reproduces_the_goldens_and_reports_an_audited_rule_without_rejecting`), snapshots of the generated files, and `check_events_are_generated` in `tests/conformance.rs`.

### Phase E2: retry, dead letter, inbox, adapters (`spec/events.md` section 10)

The server declares `events_delivery`. The names are those of `spec/targets/typescript.md` 5f in snake case; where Rust differs, the difference and its reason are below. A contract with events and none of the three annotations generates the same `<service>_events.rs` as before (`publish_event`, `subscribe_events`); only `src/veld/events.rs` changes.

- **The transport takes the options of the channel.** `Transport::publish(topic, key, bytes, options)` and `subscribe(topic, group, deliver, options)` take a `ChannelOptions { ordered, dead_letter }` (`ChannelOptions::NONE`) last. *Differs:* Rust has no optional argument, so a transport written for E1 adds the parameter; the memory transport ignores it, an adapter uses it as section 10.1 says.
- **Generated code.** A channel with `@ordered` or `@deadLetter` gets `static <CHANNEL>_OPTIONS: veld::events::ChannelOptions` and its publisher calls `publish_event_with(ctx, &CHANNEL, OPTIONS, &DEF, event)`. A service with a subscription to a channel with any of the three annotations calls `subscribe_events_with(transport, vec![(SubscriptionDef { .. }, Delivery { retry: Some(RetryPolicy { max, backoff: Backoff::Exponential }), dead_letter, ordered })], options)`; `Delivery::NONE` for a line without annotations. *Differs:* a struct literal cannot omit a field, so the E1 forms stay for a channel without annotations and the E2 forms are separate functions, which keeps the bytes of E1 files.
- **The consumer** (`veld::events`). `ConsumerOptions` gains `inbox(Arc<dyn Inbox>)`, `sleep(f: Fn(u64) -> BoxFuture<'static, ()>)`, `retry_delay_ms` (1000) and `retry_max_delay_ms` (60000). `HandlerFailure` gains `attempt` and `is_final` (*differs:* `final` is a keyword). The loop is that of section 10.4 and the Node runtime: `max + 1` runs, `meta.attempt` = the transport's attempt + the runs made, the wait after run `k` through `sleep`, every failed run reported, the last one copied (reason `handler`) and acknowledged when the channel has `@deadLetter`, `Again` at the first failure without `@retry`. A handler that panics is a failed run. The default `sleep` is a timer thread that wakes the task, so the memory transport and the consumer still need no async runtime; a test passes a `sleep` that does not wait.
- **The copy.** `dead_letter_copy(original, DeadLetterReason, group, attempts, &[Issue], &[Violation]) -> Vec<u8>` is public (every case of `dead-letter.json` reaches it). The consumer publishes it to `<topic>.dlq` with the key of the original and `ChannelOptions::NONE` before it answers; a publish that fails makes it answer `Again`, for a rejected message and for used-up retries. `on_event_rejected` is called after the copy was decided.
- **The inbox.** `trait Inbox { fn handle(&self, source, id, run: BoxFuture<'_, Result<(), Error>>) -> BoxFuture<'_, Result<bool, Error>> }` and `MemoryInbox` (`has`, `len`, `is_empty`). *Differs:* `run` is the future of the run, and an error of `run` comes back as the error of `handle`. A message the inbox skipped is acknowledged and reaches no hook; with `@retry` every run goes through the inbox.
- **The test handler** (`testing = true`). A service that subscribes gets `<service>_test_server.rs`; one without endpoint rules gets a file with `probe()`, `router()` (no application: `GET /__veld/test` and `POST /__veld/test/event`) and `deliver_event(topic, key, deliveries, bytes) -> Result<EventOutcome, Error>`, one that has both keeps its handler and its `router(handler)` adds the event route. The probe lists `subscribes`. The delivery uses the service's own `subscribe_<service>_events` over a fresh `MemoryTransport`, a fresh `MemoryInbox`, a `sleep` that does not wait and handlers that only count; the application's handlers are not called. `EventOutcome::to_json()` is the answer of section 10.9. A missing or empty `Veld-Test-Topic` and a `Veld-Test-Deliveries` that is neither `1` nor `2` are `400` with `{ "error": "<text>" }` (`application/json`; the number is no longer clamped). A program that serves several services merges the `EventOutcome`s of their modules by the rule of `spec/events.md` 10.9 (the tests' `delivery_serve` does: `rejected` wins, then `handled`; `reason` of the first rejecting service in name order; `called` the union; `violations` joined; `deadLetters` added); the tests check the `400` on that program and on one generated handler served alone (`delivery_single`). The crate gets `axum` for it, also when no service has an HTTP surface.
- **The adapters** (`[server.options] messaging = "kafka" | "rabbitmq" | ["kafka", "rabbitmq"]`; deduplicated; an unknown value, the option on a client and on a target none of whose services publishes or subscribes are `E0802`). One module each, `src/adapters/kafka.rs` and `src/adapters/rabbitmq.rs` (`adapters/mod.rs` lists them next to `axum`), the only modules that name their library; the generated `Cargo.toml` names the library, and `tokio` with `macros`, `rt`, `sync` and `time`, only for a chosen adapter. Both need a tokio runtime (one task per subscription). Without the option: no module, no dependency.
  - `KafkaTransport::new(config: rdkafka::ClientConfig)` and `.redelivery(Redelivery { initial_ms, max_ms })` (1000, doubling to 30000), `close().await`. `rdkafka = { version = "0.38", default-features = false, features = ["cmake-build", "tokio"] }`: `cmake-build` builds librdkafka with `cmake` and a C and a C++ compiler and needs no system library; `libz`, `zstd` and `ssl` are off (an application that needs TLS or compressed topics adds `ssl` and `libz`/`zstd` to its own `rdkafka` line, which cargo unifies). The adapter sets `enable.idempotence`, `acks=all`, one request in flight and `partitioner=murmur2_random` on the producer (created at the first publish; `murmur2_random` is librdkafka's "Java Producer compatible Murmur2 hash of key, NULL keys randomly partitioned", so a key lands where the Java client puts it, `spec/events.md` 10.1; librdkafka's default is the CRC32 `consistent_random`) and `group.id`, `enable.auto.commit=false`, `auto.offset.reset=earliest`, `allow.auto.create.topics=false` on every consumer (the adapter no longer sets it on the producer and makes no claim about what a producer can create: librdkafka's `CONFIGURATION.md` lists the property for both client kinds, but only a consumer is documented to use it, and whether the cluster creates a missing topic is its own `auto.create.topics.enable`, `spec/events.md` 10.1), over the application's `ClientConfig`. Record: the key text as the key, the envelope as the value, the header `content-type`, `partition 0` with `ordered`. `subscribe` returns when the group assigned partitions (the rebalance callback; an error after 60 s).
  - `RabbitMqTransport::new(connection)` / `with_redelivery(connection, Redelivery)`, and `.publish_timeout_ms(ms)` (default 30000): `publish` waits for the broker's confirm at most that long and then fails with an error that names the timeout (`spec/events.md` 10.7). The broker program `publish_does_not_wait_for_ever` uses 0 ms, which ends at the first poll and so is certain.
  - *Keeping the place in the group.* A subscription is one tokio task that takes one record at a time. While a delivery runs or waits to be tried again the task **pauses every assigned partition and keeps awaiting `StreamConsumer::recv()`**, which is the poll that `max.poll.interval.ms` is measured against (`StreamConsumer` wakes a pending `recv()` itself every half of `max.poll.interval.ms`, `rdkafka` 0.38 `stream_consumer.rs`; so a delivery of any length is polled at least that often); a record that had been fetched before the pause took effect is given back with a seek to its offset. After `Done` the record is committed (synchronously; a refused commit after a rebalance is ignored, the new owner reads it again). **A revoked partition ends the delivery:** the consumer context counts the revocations of each partition (`pre_rebalance`, served by the polls of the waiting `recv()`); a delivery notes the count when its record arrives and checks it after every answer and every wait: when it changed the record is abandoned (no redelivery, no commit, no seek; a stray record of a partition that is not assigned any more is not given back either) and the loop takes the next record of what it owns now. The decision is the function `still_owns`, unit-tested in the module; the broker program `a_revoked_partition_ends_the_delivery` runs two consumers of one group and checks that only one of them is delivering once the group has settled and the partitions resume. `Again` waits `redelivery` (doubling) and delivers again with `attempt + 1`, inside the same record. `close()` of a subscription stops waits at once, waits for a delivery that runs, commits nothing that did not finish and drops the consumer.
  - `RabbitMqTransport::new(connection: Arc<lapin::Connection>)` and `::with_redelivery(connection, Redelivery)`, `close().await`; `lapin = { version = "4", default-features = false, features = ["tokio"] }` and `futures-core` (no TLS feature: the application enables the one it needs). The declarations are those of section 10.1: the durable `fanout` exchange of a topic (once per topic, on a channel of its own), the durable queue `<topic>.<group>` and its binding on a channel of the subscription with `basic_qos(1)` (and `x-single-active-consumer` for `ordered`), with `deadLetter` the durable exchange and queue `<topic>.dlq`, bound to each other; `publish` is on one confirm channel, persistent, content type of section 6.2, routing key the key text (`""` for none, and `""` is delivered as no key), and fails on a `Nack`. A message answered `Again` stays unacknowledged and the same task delivers it again after `redelivery`; AMQP heartbeats are lapin's own, so a long delivery needs nothing more than the broker's `consumer_timeout`.
  - Rows of section 10.1: all hold as written. `attempt` counts the deliveries by this consumer since it started.

### Phase E3: the outbox (`spec/events.md` section 11)

The server declares `events_outbox` (the client of such a service generates nothing for it and keeps its bytes: `check_events_outbox_is_ignored_by_clients`). It mirrors `spec/targets/typescript.md` 5f, "Phase E3", in Rust's idiom; the behaviour is `spec/events.md` 11.1 and 11.2 and is not repeated. A contract without an emitting move (a `transition` whose edge has `emits`) gets the bytes it got before in every file: the runtime pieces are behind the gate `outbox` (`Features::outbox`: a served service with an emitting endpoint; it implies `events` and the `refactor` split of `run` into `run` and `run_ctx`, where the stamp of `Veld-Test-Emitted` is). `publish_event_with` is the old text when the gate is off.

| What | Rust |
|---|---|
| The interface the application implements | `veld::events::Outbox: Send + Sync + 'static`, object safe and async like `Transport` (`BoxFuture`): `save(&self, topic: &str, key: Option<&str>, bytes: &[u8])`, `pending(&self, limit: usize) -> Vec<OutboxEntry>` and `done(&self, entry: &OutboxEntry)`, each returning `BoxFuture<Result<_, veld::Error>>`. `OutboxEntry` is `{ id: String, topic: String, key: Option<String>, bytes: Vec<u8> }`; `id` is the application's own |
| For tests | `veld::events::MemoryOutbox`: ids `"1"`, `"2"`, ... in the order of the saves, `pending(limit)` the first `limit`, `done` removes one, `size()` and `entries()` |
| The hooks | `<Service>Hooks` has `type Outbox: veld::events::Outbox; fn outbox(&self) -> &Self::Outbox;` (required, as the idempotency store and the flag provider are: a server without an outbox **does not compile**, which is how "creating the handler fails" is met in Rust; such hooks have no `NoHooks` and the handler no `plain`) and `fn events(&self) -> veld::events::PublisherOptions` (the id source, the clock, the rule hook, and the flag provider of `emit`; the default is a random id, the system clock and nothing). The `clock` of the endpoint rules is another thing and is not used |
| What the handler gets | `<Endpoint>Emit<'a>` (`PayEmit<'_>`) in `<package>::<service>_events`: one `async fn` per entry of `transition.emits`, in the order of the IR, named like the publisher's (`emit.booking_paid(&event).await?`), taking `&Event` and returning `Result<PublishedEvent, veld::Error>`. It follows the facts, `version` and `transition` and comes before the context (`spec/rules.md` 11.12): `fn pay(&self, request, facts, transition, emit: PayEmit<'_>, ctx)`. A move that emits nothing has no `emit` argument. A parameter or a fact whose Rust name is `emit` on an emitting move is `E0801` (a field of the request struct would not clash, but the other targets cannot give it that name, and a contract should mean the same everywhere) |
| The relay | `run_<service>_outbox_relay(outbox: &dyn Outbox, transport: &dyn Transport, options: &RelayOptions) -> usize` in `<service>_events.rs`, over `veld::events::relay_outbox`. `RelayOptions::new().limit(n)` (100) and `.on_error(\|error: &Error, entry: Option<&OutboxEntry>\| ...)` (`None` when `pending` itself failed; a hook that panics is ignored). Pass a transport you hold in an `Arc` as `&*transport`. The options of the channels are `ChannelOptions` by topic (`<SERVICE>_RELAY_CHANNELS`); a topic of no channel is published with `ChannelOptions::NONE` |
| Written by the handler | `veld::events::Emission::emit(channel, def, event)` (behind `<Endpoint>Emit`), which is steps 1 to 5 of publishing and then `Outbox::save`; `veld::events::check_written(expected, written) -> String` answers `ok`, `missing E`, `twice E` or `unexpected E` (the table `written` of `outbox.json`); `check_emitted` is the check of the server |

**`emit` shares the publisher's code.** `publish_event_with` is split in the runtime's `build_message` (flags, `prepare`, id and clock, envelope, bytes: steps 1 to 5 of `spec/events.md` section 7) and the call of the transport; `Emission::emit` is `build_message` and `Outbox::save`. `Emission` holds a `PublisherContext` whose transport is a `NoTransport` that nothing reads (a copy of the context type would be a second description of the same four things). In a build without the outbox `publish_event_with` is in one piece (`@if outbox` and `@if !outbox` pair the header and the tail of the function; the shared body sits between them). The flagged invariants of the event are evaluated by `emit` as by a publisher, with the provider of `Hooks::events()`. `<Endpoint>Emit` uses the statics of the events file (`<NAME>_CHANNEL`, `<NAME>_DEF`, `SOURCE`, `VALIDATION`), so the descriptions of channels and events exist once and keep their visibility. The channel is the one `transition.emits` names.

**The server.** The generated `call` of an emitting endpoint, after step 6 has handed `transition` over and the request is decoded, writes `let emits = <events>::pay_emits(veld::events::transition_from(&args));` (the table of `<events>::pay_emits(from)`: by wire value of each source state, the declaration names of the events of the edge from it to the target, worked out at generation time from the flows of the enum, what `veld_rules::outbox::expected_events` gives), `let emit = <events>::PayEmit::begin(self.hooks.outbox(), self.hooks.events(), &ctx.emitted);` and, **right after the handler returns `Ok`**, `veld::events::check_emitted("pay", emits, &ctx.emitted)?;`. A fault is an `Error::Other` (`pay: the move wrote the wrong events to the outbox: missing BookingPaid`), so the answer is `500 Internal` and it goes to `on_error`; the events already saved stay in the outbox, which is why the application's transaction has to end with the failure. A handler that returns an error is not checked (the `?` leaves before it). The check runs before the output rules and the `ensure` statements (steps 8 and 9 are in the core, after `call`). A stream (`sse`) gets `emit` and is not checked. What the request wrote is `RequestContext.emitted` (`veld::events::EmitLog`, a hidden public member behind the gate), one log for the request, shared by the `emit` and the check. The `emit` of a request that is refused before the handler is never built, so nothing is written.

**The test handler** (`testing = true`). `Endpoints::test_emitted()` (default `false`) is `true` in the dispatch of a test handler of a service that emits: `Handler::context` then makes the request's log a *scratch* log, and `Emission::new` writes to a `MemoryOutbox` of the request's own instead of the application's (the hooks the test handler is created with still have to name an outbox, which is never asked, like the idempotency store). `Handler::run` stamps the answer with `Veld-Test-Emitted`: `EmitLog::header()`, the declaration names of the events written, `,` without spaces, in write order, absent when nothing was written. With `Veld-Test-Result` the application's handler does not run: the dispatch of the test handler calls `ctx.emitted.set(<events>::emitted_by(endpoint, veld::events::transition_from(&args)))` (the events the edge taken emits, `expected_events`), and the check is not run because `inner.call` is not. `Veld-Test-Dry-Run` stops before the handler, so the header is absent. No file but the runtime's `server.rs` names the header.

**Choices where `spec/events.md` was silent.** The names above; `Outbox` is object safe with `BoxFuture` (not `impl Future` like the idempotency store) so that `Emission` and the relay need no type parameter and the test handler can swap in its own; `emit` is a value of type `<Endpoint>Emit<'a>` that borrows the hooks' outbox for the length of the call; the relay takes borrowed `&dyn Outbox` and `&dyn Transport`; `check_written` reports the first fault in the reference's order (a missing event first, then a repeated one, then an unexpected one); `emit` returns the `PublishedEvent` of a publisher; `MemoryOutbox` is synchronised and `size()` counts the pending entries; the relay looks at the first `limit` entries `pending` gave it, counts an entry whose `done` failed as sent (it is pending again and is sent again), and a failure of `pending` itself goes to `on_error` with no entry and the run answers 0; the check does not look at flags: an edge whose flag is off still expects its event (the generation-time table does not know the readings), as in Node and Java.

**Tests.** `crates/emitters/rust/tests/events_outbox.rs` with the programs `tests/toolchain/rust/outbox/{relay,http,serve}.rs`: `the_entries_of_the_golden_are_what_emit_saves` (every `entries` case of `outbox.json` through the generated `emit`: a probe service for each pair of channel and event is added to the contract, with a move that emits the event, the id and the clock are fixed, a recording outbox must receive the topic, the key and the bytes of the golden and the log must name the event), `relay.rs` (every `relay` case through `run_bookings_outbox_relay`, every `written` case through `check_written`), `http.rs` (`tests/events/outbox.veld.pending` over `BookingsHandler::create` in process: a handler that writes, one that forgets, one that writes twice, one that writes the event of another edge, each source of `cancel` with its own event on its own channel, a declared error, a guard that refuses, an invalid event, a move that emits nothing; then the relay with the memory transport and the subscriber of `Notifications`, run twice, with a transport that fails, with a limit), `serve.rs` (the call examples with `expect emitted` and the event examples of the same contract through the generated test handlers and `veld_testing::Live`; `outbox-serve`), the options of a channel at the relay, `E0801` for a parameter or a fact called `emit`, a server whose hooks name no outbox failing to compile (`E0046`), a generation test that a contract without `emits` has none of the words of the outbox, an emitting move next to a timed edge, a deadline, a service level, an idempotency key, a flagged statement and a flagged event (`tests/toolchain/contract/platform_p2/outbox_four.veld`, with and without `testing`, built with `clippy -D warnings`), snapshots, and `check_events_outbox_is_generated` (here and in `tests/conformance.rs`).

## 14. Version and idempotency (`rules_version` and `idempotency`, `spec/rules.md` sections 11.7 to 11.12)

Both capabilities are declared in both roles. A contract without `@version` and `@idempotent` generates the same bytes as before: every line of the runtime that serves them is behind a gate (`etag`, `idempotency`, `conditional`, `version`), and no snapshot changes.

- **Files.** `src/veld/conditional.rs` (`IfMatch<V>`, `parse_if_match`, `etag_of`, the message of the `If-Match` issue) in a crate that has a guard (server or client) or a served `ETag`; `src/veld/idempotency.rs` (`IdempotencyStore`, `Begin`, `StoredAnswer`, `MemoryIdempotencyStore`, `fingerprint`, `sha256`, `is_valid_key`, the two `Conflict` messages, `seeded_begin` for the test handler) in a server with an `@idempotent` endpoint. The generated crate has no new dependency: SHA-256 (FIPS 180-4) is written out in `idempotency.rs` and the canonical JSON is the `veld::canonical` of the crate.
- **The core** (`src/veld/server.rs`). Each `Endpoints` implementation says what an endpoint owes through `fn conditional(&self, endpoint: usize) -> Conditional` (`guard`, `etag`: the wire name of the version field of the success model, `idempotency: Option<Idempotent { header, required, caller }>`); `EndpointSpec` is unchanged, so no `ENDPOINTS` literal changes. Neither feature needs endpoint rules: the core does the header syntax, the lookup, the replay, the `409`, the store calls and the `ETag` without `veld/rules` when the contract has no rule.
- **Step 5.** `If-Match` of an endpoint with a guard, and the key of an `@idempotent` endpoint, are checked next to the other issues, header issues first, with the exact issues of section 11.10; a rule violation in the same request stays as `violations` (the issues of the headers are put in front of its issue). This does not depend on `validate_requests`.
- **The guard.** `step6_<endpoint>` has, after the facts and the policies and before the transition guard, `// version <fact>.<field>`: when `ctx.if_match()` is a version it compares it with the field of the fact (an absent optional fact passes) and answers `412 PreconditionFailed` through `veld::rules::refusal` with `expected` and `actual` as decimal strings and the one violation of section 11.9 (`path` `request`, no fields, `violates rule version`); `*`, no header and a malformed header (already refused) hand nothing over. The hook gets position `Input`, outcome `Rejected`. The guard needs the facts runtime, so `guards` is on for a service with a guard.
- **The version the handler receives.** The service method takes `version: Option<i64>` (`Option<i32>` for an `int` field, the Rust type of the field) after the facts and before the transition and the context: the order is the one of the pipeline, facts, `version`, `transition` (`spec/rules.md` section 11.12). Step 6 puts it into the bound arguments under `version` (`null` when nothing was compared) and the dispatch reads it back with `decode_key`. The doc comment says it is a guard, not an atomic guarantee, like the one of a transition.
- **`ETag`.** The success response of an endpoint whose type is the model itself carries `etag: "<version>"` (a `long` is a string on the wire and an `int` a number: both are written as digits), whatever the 2xx status, and so does a replayed success (the header is stored with the answer).
- **The store.** `trait IdempotencyStore: Send + Sync + 'static` has `begin(scope, key, fingerprint)`, `complete(scope, key, answer: StoredAnswer)` and `release(scope, key)`, each returning `impl Future<Output = Result<_, veld::Error>> + Send + 'a` (no `async_trait`, like the loaders). It is not object safe: the hooks name it by an associated type. `Begin` is `Started`, `Replay(StoredAnswer)`, `Running`, `Other`. `StoredAnswer` is `status: u16`, `body: Vec<u8>` (the bytes that were sent), `content_type`, `etag`, `location` (`Option<String>`). `MemoryIdempotencyStore` keeps every entry, is atomic under its mutex, and has synchronous twins (`begin_now`, `complete_now`, `release_now`) and `insert_stored` / `insert_running` for tests.
- **The hooks.** A service with an `@idempotent` endpoint has two required members in `<Service>Hooks` (no default; `NoHooks` and `plain` are not generated for it): `type IdempotencyStore: veld::idempotency::IdempotencyStore; fn idempotency_store(&self) -> &Self::IdempotencyStore;` and, when an endpoint has `caller: true`, `fn idempotency_caller(&self, principal: &Principal, ctx: &RequestContext) -> String` (`&User` when the hooks are typed). The types require them, so a server without the store, or without the caller hook where it is needed, **does not compile**; this is how section 11.12's "creating the handler fails" is met in Rust: there is no handler to create, and no runtime path that finds out at the first request.
- **The run.** After step 5, for a request with a key, the core takes the fingerprint (the first 16 hex characters of the SHA-256 of the canonical JSON of the bound parameters in wire form: `Schema::to_wire_fingerprint(typed)` of each non-stream parameter that was bound, so defaults are applied, read-only fields, unknown members and absent optionals are left out, a uuid is in lower case and a datetime is UTC with `Z` and `.fff` only when the milliseconds are not zero, the form of an event's `data`; `null` is kept for a `json` member and a `json` map value only) and the scope (`<operation signature>` and, when `caller` is set, `\n<caller text>`), and calls `begin`. `Started` runs the request through steps 6 to 9 and then `complete` for a status below 500 and `release` otherwise; until then the request holds the key in a guard (`Hold`): if the request future is dropped (a client that hangs up) or the handler panics before `complete` or `release` has finished, the guard's `Drop` hands `release(scope, key)` (or, once the answer exists and is below 500, `complete(scope, key, answer)`, so that a request dropped while its answer is stored is not run a second time) to a task of its own (`tokio::spawn` on the runtime the request ran on, which the axum adapter always has; the crate then depends on `tokio` with the `rt` feature, which `axum` already pulls in; a thread of its own driven by `veld::block_on` when there is no runtime), so the key is never left "running". A store that fails in that release has nobody to report to and is ignored (a store that fails there changes nothing in the answer: the error goes to `on_error`); `Replay` sends the stored status, bytes, `content-type`, `etag` and `location` plus `veld-idempotent-replay: true` with no fact loaded and no handler called; `Running` and `Other` are `409 Conflict` with the two messages of section 11.10 (the declared `Conflict` of the endpoint); a `begin` that fails is `500` with the handler not run and the error in `on_error`. The rules digest header is added after, to a replay too.
- **The test handler** (`testing = true`) is generated for a service with endpoint rules or an `@idempotent` endpoint. Its dispatch overrides the store calls: `idem_begin` builds a fresh `MemoryIdempotencyStore`, fills it from `Veld-Test-Idempotency` under the fingerprint of the request (`other`: under `other:<fingerprint>`, `running`: under it, `stored`: the answer built from `status`, `type` and `data` through the schema of the error, or of the success, with its `ETag`) and asks it; `complete` and `release` do nothing (the store lives for one request). Its caller text is the canonical JSON of `Veld-Test-Principal`, or `caller`. The hooks it is created with still have to name a store (they are never asked). A replay is answered before the dry run stops the request, as section 11.10 says.
- **The client.** The request struct of a client method has, after the declared parameters, `if_match: Option<veld::conditional::IfMatch<i64>>` (`IfMatch::Any` or `IfMatch::Version(3)`; `i32` for an `int` version) for an endpoint with a guard and `idempotency_key: Option<String>` (`String` with `required: true`: the type requires it) for an `@idempotent` one. They are `ParamSpec` header parameters of the client's `ENDPOINTS` (`If-Match`, and the header of the annotation), so `Core::build` sends them like any header; `IfMatch` serialises as its header text and is skipped when deserialising. The client never invents a key and checks the syntax of neither value. A declared parameter whose Rust name is `if_match` (with a guard) or `idempotency_key` (with `@idempotent`), and a guard on a streaming endpoint, are `E0801` in either role.
- **Datetime forms.** `Schema::to_wire_fingerprint` writes a datetime with `normalize_datetime(.., millis = true)` of `schema.rs`: UTC, `.fff` cut at the millisecond and only when it is not zero. `events.rs` has its own `canon_datetime` with the same output (the events runtime is a separate file that a crate may not have); the two are not shared. The older `normalize_datetime(.., false)` (canonical bytes of `same()`) trims trailing zeros of the fraction instead (`.5Z`), which differs for a value with a fraction.
- **Choices where the spec is silent.** `IfMatch` is generic over the version type (`IfMatch<i64>` is the default), so that a client of an `int` version is typed like the field. The store errors are `veld::Error` (the one error type of the crate). The caller hook is synchronous and takes the principal and the context; a request whose principal is missing from the context (it cannot happen after authentication) has the empty caller text. The core finds the declared `Conflict` by its name and status 409 in the endpoint's errors. A request future that is dropped, or a handler that panics, gives its key back (the `Hold` guard above). **The caller hook cannot fail:** `idempotency_caller` returns a `String`, so the case of section 11.12 (a failing hook is treated like a failing `begin`: `500`, handler not called) does not arise; an application whose caller text can fail answers it in `auth_*`, which refuses the request before the store is asked.
- **Tests.** `crates/emitters/rust/tests/version.rs` and `idempotency.rs`: snapshots of a small contract with both annotations (server, client, test handler, runtime), the shape of the hooks and of `conditional`, the words a contract without the annotations must not contain, `E0801` for a clashing parameter, and, in scratch workspaces, the crates build and pass `clippy -D warnings` with `tests/toolchain/rust/version-harness` (a matching tag, a stale one with its `412` body and violation, `*`, no header, twelve malformed forms, `validate = false`, an `int` version, an absent optional fact, an endpoint without a guard that ignores `If-Match`, the `ETag`, the order policy, version, transition, the client's headers) and `idempotency-harness` (a new key, the replay with nothing run and no fact loaded, other parameters, a request that is running, a stored declared error, a `500` that is not stored, a missing and a malformed key, a header issue next to a rule violation, a key header of its own, two callers, the `ETag` and a `204` replayed, a store that fails in `begin`, `complete` and `release`, the atomicity of `begin`, the first five goldens of the reference fingerprint, a request future that is dropped mid-handler and one dropped while its answer is stored (`handle` under `tokio::time::timeout`: the key runs again, and the handler is not run twice), a handler that panics, and what the client sends), and all 19 examples of `version.veld.pending` and 21 of `idempotency.veld.pending` through `veld_testing::Live` (`version-serve`, `idempotency-serve`; a skipped example is a failure). The fuzzer of `veld_testing` does not send `If-Match` or a key, so these two contracts are not fuzzed. `tests/conformance.rs` asserts `check_version_is_generated` and `check_idempotency_is_generated`. `tests/idempotency.rs` also runs all 115 cases of `tests/wire/idempotency/fingerprints.json` through the generated production server (`tests/toolchain/rust/fingerprint-harness`: every case is sent over HTTP, the fingerprint the server gives to `begin` must be the reference's, a `rejected` case must be answered with its status and never reach the store, `same_as` and `differs_from` are checked on what the server computed; the contract is compiled as the file `t.veld` of the package `bookings`, so its module is `t`).

## 15. Runtime config (`spec/runtime-config.md`)

A target that has settings (a client target, a server with `clients = true` that consumes a service, a server whose contract has rules; `spec/runtime-config.md` section 2) gets the module `src/runtime_config.rs` and the engine `src/veld/config.rs`. A target without a setting (a server without rules that consumes nothing) generates the bytes it did before: no module, no engine, no `config` line in `src/veld/mod.rs`, no argument. The core passes the target's name; a target that has settings and no name is `E0802`. `runtime_config` is a reserved module name (a package with that name gets a trailing `_`).

- **The type.** `<Target>Runtime` derives `Debug`, `Clone` and `serde::Deserialize` with `deny_unknown_fields` (and `Default` when no setting is required). Its members, sorted by key at each level, are `rules: RulesSettings` (with `#[serde(default)]`; `output: RuleOutputMode`, `Strict`, `Audit` or `Off`, default `Strict`) when the target has `rules.output`, and `services: <Target>Services` when it has URLs. `<Target>Services` has one `ServiceSettings { url: String }` for each service; a field is named in snake case, and `#[serde(rename = "card-service")]` is added whenever the Rust name differs from the path segment (a keyword is a raw identifier). Two services whose Rust names clash are `E0801`. `RuleOutputMode` converts into `veld::rules::RuleOutput`.
- **The check and the readers.** All of them end in one engine (`veld::config::Table`), which holds no message text of its own: the table and every message are generated from `veld_codegen::runtime_config`.
  - `check(&self) -> Result<Self, ConfigError>` runs the checks `serde` cannot (an empty or invalid URL) and returns the checked copy: URLs without a trailing `/`.
  - `from_value(&serde_json::Value)`, `from_map(&BTreeMap<String, String>)` (paths as keys), `from_env(&[(&str, &str)])` (pairs of path and variable name) and `from_env_with(names, &dyn Fn(&str) -> Option<String>)` (the same with an environment you give). They build the type and check it. Unlike a plain `serde` deserialization, `from_value` reports every problem with the exact text of `spec/runtime-config.md` section 4, including `<path> must be an object`.
  - `values() -> BTreeMap<String, String>` is the value of every setting by path, defaults filled in.
  - What plain `serde` reports instead: a wrong JSON type, a misspelt or unknown key, a missing required field and a value outside the list of `rules.output` are `serde`'s own errors (`invalid type: ...`, `unknown field ...`, `missing field ...`, `unknown variant ...`), one at a time. `null` for `rules` or a service is an error of `serde`, not an absent value. Use `from_value` (or `from_map`, `from_env`) where the text and the full list matter. The golden program accepts the derived path only where it agrees: a nested value that `serde` accepts must give the golden result through `check`.
  - `ConfigError` (`veld::config::ConfigError`, re-exported by the module) holds the problems (`problems() -> &[Problem]`, each with `path` and `message`, sorted by path then message) and displays `invalid runtime config: ` and the messages separated by `; `.
- **The clients.** `<Target>Clients<T>` has a field for each client of the target (snake case of the service name; two clients with the same field are `E0801`). `clients_with(&runtime, options, transport: impl FnMut() -> T)` checks the config, then builds each client with `options.clone().base_url(<its url>)`: a package with several `service` blocks gives all of them the one URL. `clients(&runtime, options)` is `clients_with` on the default transport of the crate (`reqwest` or `ureq`; it is not generated with `transport = "none"`). A client that cannot be built is a `ConfigError` with one problem at its URL path.
- **The server entry.** `<Service>Handler::create(service, hooks[, loaders], runtime)` and `plain(...)` take the runtime config last, after the hooks and the loaders, and return `Result<Handler<..>, ConfigError>`; the check runs first. The test handler's `create` and `plain` take no runtime config and return the handler itself (section 10.3). The argument is `&<Target>Runtime`, and `Option<&<Target>Runtime>` exactly when no setting is required (`None` is the default config). Every served service of the target takes it, the ones that read no setting too (the test handler excepted). A service that only publishes or subscribes has no entry and takes nothing.
- **The output mode.** `<Service>Hooks` never has `rules_output` (`spec/runtime-config.md` section 5). With `rules.output`, the dispatch holds the mode (`output`) that the config gave. A server whose config has no `rules.output` (its rules are all in consumed services) has no mode: its dispatch has no `output` and the core runs in its default, `Strict`. The rules runtime is emitted for a target that has `rules.output`.
- **Removed.** The client has no `VELD_<SERVICE>_URL`, no `base-url` and no default: `Core::new(transport, std, validate, options)` fails with `Error::Transport` when `options.base_url` is not set. `ClientOptions::new()` is unchanged. `base-url` of `veld.toml` reaches only the OpenAPI export.
- **"Has rules".** The generator asks `veld_codegen::runtime_config::contract_has_rules` for `rules.output`. The predicate counts a declaration with a derived field like one with a rule, and an `allow` and a rule with `@rollout` like any statement. The emitter's own `rules` flag (the rules runtime) is broader only for consumed services: a server whose consumed services have rules but whose own contract has none has `services.<s>.url` only and no output mode. A server with `rules.output` and no other reason for the rules runtime gets the runtime anyway.
- **Choices where the spec is silent.** The module is `src/runtime_config.rs`, its nested types are `RulesSettings`, `ServiceSettings` and `<Target>Services`, and the clients struct is `<Target>Clients`. `from_env_with` and `from_value` are additions; `from_env` reads `std::env::var`. The engine is shared by all crates (`src/veld/config.rs`) and is not gated further. A `create` that cannot fail (no URL, `rules.output` only) still returns a `Result`, so that the entry has one shape.
- **Tests.** `crates/emitters/rust/tests/runtime_config.rs`: snapshots of the runtime modules (server with rules and services, client, rules only, services only), of the engine, of the server entry (required and optional) and of the client; the type names and settings of `tests/wire/runtime-config/cases.json` against the generated modules; no environment variable and no compiled-in URL; no module for a target without settings; `E0801` for clashing fields; `E0802` without a name; and, in a scratch workspace, four generated crates build with `clippy -D warnings` and `tests/toolchain/rust/runtime-harness` runs `golden` (all 47 cases and the URL list through `from_value`, `from_map`, `from_env_with` and `serde` plus `check`, counted) and `behave` (a bad config fails at creation with the whole list, the output mode from the config in the three modes, the optional argument, the clients' URLs and options, a client without a URL, the environment reader). `veld-emit-conformance` passes a target name to every generator it runs (`options()`).

## 16. Derived fields (`rules_derived`, `spec/rules.md` section 17.2)

Both roles declare `rules_derived`. A contract with no derived field generates the same bytes as before: the schema has no `derived` or `derive` member, the runtime has no derived region (`// @if derived`, `// #if derived`), and no declaration has `derive`. A derived field brings the rules runtime in, also when no declaration has an invariant.

- **The Rust type.** A derived field is a required member of the struct, of the type the contract gives it (`total: String` for a `decimal`): the struct is one type for what a handler receives and what it returns, so it cannot be optional in one and present in the other. This follows the idea of `@readonly` and of defaults (section 10.1): the member is there, and the server decides its value. **What a handler receives holds the computed value. What a handler returns, and what a client writes into a request struct, holds any value of the type as a stand-in**, which the server replaces (the doc comment of the field says so; write `0`, `String::new()` or a copy of the old value). A derived field that cannot be computed (an evaluation error, or a read of a field a request does not have) is left without a value on the wire and, in a struct the application reads (a request, a handler's fact), holds the stand-in of its type. **What a handler gets for a derived field that is absent in a request** (it reads a `@readonly` field, directly or below the first level, or reads another derived field that is absent) is that stand-in (`0`, `String::new()`, an empty list): the type does not say that the value is missing. Making exactly those fields `Option<T>` was considered and not done: the struct is one type for what a handler receives, returns and what a client writes, and every place that reads a field by its IR path (the rule printer's field chains, the endpoint blocks `p.body.next`, the policies, `Derive` and the client's models) takes the Rust type from the IR, where the field is not optional; an `Option` for those fields only would have to be threaded through each of them (the printer would need the declaration of every step of a path, as `src/rules/reach.rs` resolves it). A handler that must know reads the contract: the fields are those whose expression reaches a `@readonly` field. The compiler could name them (one more key next to `derived`, `alignment-fixes.md`), and the three generators could then mark them in the type.
- **The schema.** `vs::Field` has `derived: bool` and `vs::ModelSchema` has `derive: Some(veld::rules::derive_object::<T>)` (`None` for a declaration without a derived field) in a crate that has one. `Schema::without_derived(&wire)` drops every derived member at every depth; `validate` never requires a derived member and never checks its constraints (`spec/rules.md` section 17.2: a constraint on a derived field is not checked); `to_wire(typed, request = true, ..)` leaves a derived member out (a client never sends one) while `to_wire_fingerprint` keeps it; `from_wire` puts a stand-in where a derived member is absent.
- **The computation.** `veld::rules::derive_walk(schema, typed, path, mode, out)` visits the typed JSON of a value: list items, map values, page items and union arms first, the members of an object in declaration order, then the object itself through `derive_object::<T>`, which reads the object as `T` (a derived member is replaced by a stand-in first, so what was there is never believed) and calls the generated `Derive::derive_fields`. That function computes the fields in the order of `Decl::derived_fields()`, each from the previous values (`self.<field> = v`, and the member is written into the JSON), through the same printer and helpers as an invariant (`derived_value` in `src/rules.rs`; the value is widened to the type of the field when the language says so, and a `date`, `time` or `datetime` is written back by `vr::format_date`, `format_time` and `format_datetime`, the text `veld_rules::wire` writes). A field that reads another that has no value, or, in a request, a `@readonly` field, is not computed, with no violation (`mode != Mode::Request` and `ok_<field>`). **At any depth:** `derive_object` hands `derive_fields` the patterns of the derived fields that have no value below the object (`veld::rules::absent_patterns`: the wire names from the object down, `.` between them and `[]` for a list: `total`, `customer.total`, `items[].total`), a field that reads one (a path `customer.total`, or a variable of a quantifier over a list, `sum(items, i => i.total)`) is guarded by `!vr::is_absent(absent, "items[].total")`, and one that reaches a `@readonly` field below the first level (`sum(parts, p => p.seq)`) by `mode != Mode::Request`. The generator finds the reads with `src/rules/reach.rs` (the types of the steps of a path, the lists a variable ranges over). The members that are absent below the object are filled with stand-ins (`fill_derived`) while the object is read, so a failing derived field of an item no longer makes the whole parent unreadable. A field whose expression raises an evaluation error is one violation: `rule` is `Field.derived_id`, `error` is the error, `fields` are the wire names it reads, the message is `field <name> could not be computed`. **Types.** A derived field may have any type but `duration` (`E0801`, and a field cannot be declared with that type): a number, a `bool`, an enum, a `string`, `uuid`, `decimal`, `date`, `datetime` or `time` as before; `bytes`, `json`, a model, a map and a `Page` are copies of a field of that type (`(&self.blob).clone()`); a list is built element by element from the list the expression gives (a field of that type read through `vr::list`, or a list literal), each element converted to the element type of the field as a scalar is (`vec![a, b].into_iter().map(|e| e)`, `.map(|e| e.to_string())`, `.map(|e| vr::format_datetime(e))`, `.map(|e| e.clone())`), so a list of lists is converted level by level. The test `a_derived_field_may_have_any_type_but_duration` generates a crate with each and builds it with `clippy -D warnings`.
- **The invariants** read the computed values: `check_wire` (the check of the server's step 5, of the client's local check, of the publisher and the subscriber, of the audited rules) derives first and then walks, so `Order::check()` computes, reports the violations of the derived fields and then those of the rules. A rule that reads a derived field that has no value, at any depth, is skipped, by the `absent` argument (the patterns above, `&[String]`) of `Invariants::check_rules_absent` (a declaration that has a derived field, or a rule that reads one below its first level, has it; `check_rules` calls it with no field absent): no rule is evaluated against a stand-in. **A limit:** the skip is by pattern, not by item: when one item of `items` has no `total`, a rule that reads `items[].total` is skipped for the whole list, where the reference evaluator, which meets the missing field when it reaches that item, can still fail the rule on an earlier item. The violation of a derived field that could not be computed is reported anyway and rejects the request.
- **Where it runs.**
  - A request (step 5): `without_derived` before `validate` (a value the caller sent, malformed or not, is dropped and is never a `422`), `check_wire` for the violations (`422 ValidationError`, `violations`, hook position `Input`), and the typed value handed to the handler is the one the computation made (`Bound::derived`), a stand-in where a field could not be computed. With `validate = false` or `validate_requests() == false` the derived fields are still computed (they are values, not rules); a field that cannot be computed rejects the request with the same `422`, because the handler could not be given the field (`without_validation_the_fields_are_computed_and_a_failing_one_rejects` in the derived-edges harness). The same holds for a body, a `query` object and a WebSocket message (`WsSession::recv`).
  - **Endpoint blocks read the absence too.** Step 5 keeps, for each bound parameter, the patterns of its derived fields that have no value (`Bound::absent`, copied into `RequestContext.absent`, a hidden public member of a crate with derived fields; `veld::rules::absent_in(&ctx.absent, "body", "next")` asks it) before the stand-ins are filled. A `require`, an `ensure` and the `old(...)` of an `ensure` that read such a field of a parameter (directly, through a path, or through a quantifier over a list parameter: `src/rules/reach.rs` `reach_params`, with the parameter's own type as the root, a first-level derived field included) are skipped; the `ensure` of step 9 reads the patterns from its saved state (`state.absent`). **An `allow` that reads one denies** (`403 Forbidden`, `not permitted`, `spec/rules.md` 11.3): the argument that cannot be evaluated is `Err(Fail::Absent)` of the verdict closure, which `vr::denial` turns into a denial. This covers an argument that reads the field itself and an argument that is the parameter (or a part of it) while the policy's clauses read the field (`allow_absent_condition`). A fact key and the payload of an `else` still read the stand-in. Tests: `endpoint_statements_and_pages_read_a_missing_derived_field` (`tests/toolchain/rust/derived-edges`), `endpoint_statements_read_the_absent_patterns_of_step_five`.
  - **A derived field in the items of a `Page`:** `collect_absent` walks the items of a page (pattern `page[].next`). No expression can range over a page (`E0906`), so the only reads are the rules of the item itself, which were already guarded; the walk makes the patterns of a parent complete.
  - A fact and the principal: after the loader returns, `vr::complete_with(schema, &mut fact)` (the fact's own schema, so also a list or a page of models); **the principal is completed once per request, after authentication and middleware, for every endpoint** of a service whose principal model has derived fields (not only one whose rules read the caller): `Endpoints::complete_principal` (the generated dispatch; the test handler forwards it) replaces `ctx.principal` by the completed value, so the policies and rules read it and the handler's `ctx.principal::<User>()` is that value. The hooks of such a service return the model itself (`Option<User>`, as for a service with policies), because the server must know the type to complete it. A field that cannot be computed is `500 Internal` (the handler is not called), reported to the hook as an output violation, as for a fact.
  - A result, a declared error (also the payload of an `else`, built by `else_rejection`), a stream item and a message of a WebSocket server: `RuleSink::derive_output` computes the derived fields of the typed value before the output rules (`check_computed`, the walk without the derivation) and before the bytes are written, also for `ensure`, which reads the completed result. The output mode decides what a failure does: `strict` is `500 Internal` (the hook hears the violation with outcome `Rejected`), `audit` sends the value without the field and reports it with outcome `Audited`, `off` sends it without the field and reports nothing; every mode computes the others.
  - An event: the publisher computes before the shape check and the invariants, and a field that cannot be computed returns the `ValidationError` problem with the violations, nothing is sent and the hook hears them (position `Output`, outcome `Rejected`). The subscriber drops the derived members of the data of the message before it validates and checks it and computes its own for the handler; a message whose derived value is wrong or malformed is accepted with the right value. **A message whose derived field cannot be computed is rejected** (`on_event_rejected`, reason `rule`, that field's violation) whether or not its digest is the consumer's: with the same digest the check of the invariants reports it, with another one `decode` derives (`veld::rules::derive_violations`) and rejects, so the handler is never given a stand-in.
- **The fingerprint** of an idempotent request is taken from the typed parameters after step 5, with `to_wire_fingerprint`, so it covers the computed values and not what the caller sent (`holder_*` of `tests/wire/idempotency/fingerprints.json`).
- **The client** computes the derived fields of a body or a `query` object before its local check (`check_wire` in request mode: a rule may read a derived value, and the rules digest covers their ids), never sends them (`to_wire` of a request) and takes a derived value of a response as it came (`from_wire` keeps a member that is there). A message of a WebSocket client is sent without them. The client is generated for a derived field that an endpoint reaches; a fact or the principal that only a server sees is the server's.
- **The public function.** Every declaration with a derived field has `fn derive(&mut self) -> Vec<veld::rules::Violation>` (the code the server runs, `Mode::Full`) and `fn derive_request(&mut self)` (`Mode::Request`: a field that reads a `@readonly` field is left at its stand-in) next to `check()` and `check_request()`. They compute the fields of the value and of everything inside it and return the violations of the ones that could not be computed.
- **Choices where the spec is silent.** The Rust type and the stand-in above. `derive_object` removes what was there instead of comparing it. Failing derived fields of a fact, the principal and a stream item are reported like an output violation. `contract_has_rules` of `veld_codegen::runtime_config` counts a declaration with a derived field like one with a rule, so a contract whose only rule-like feature is a derived field has `rules.output`, the setting that governs a failing derived field of a response. `Schema::to_wire(.., normalize = true)` is unchanged; the datetime form of the fingerprint is section 14.
- **Tests.** `crates/emitters/rust/tests/derived.rs`: snapshots of a chain (models, server, the rules runtime, the client's models), the shape of `derive` and of the generated computation, a contract without derived fields that has none of the words of the feature, a derived field without a rule, the vectors of `tests/rules/core/derived.json.pending` through a generated crate and a driver (21 of the 22: the partial check of a draft is TypeScript only; `expect`, the violations and the `computed` paths are compared, with `.pending` read by its name), the 9 examples of `tests/rules/endpoints/derived.veld.pending` through the generated test handler (`tests/toolchain/rust/derived-harness`, `derived-serve`), `check_derived_is_generated` in `tests/conformance.rs`, and `a_read_of_a_nested_derived_field_is_guarded_by_its_pattern` and `a_derived_field_may_have_any_type_but_duration` (builds a crate with every type), `tests/toolchain/rust/derived-edges` over HTTP and the memory transport (also `a_derived_field_without_a_value_skips_at_any_depth_in_a_request`, `the_principal_is_completed_for_every_endpoint` and `a_consumed_event_that_cannot_be_computed_is_rejected_whatever_the_digest`; a request whose derived values and malformed values are replaced, a failing expression, a rule that reads a computed value, validation off, a fact and the principal, a declared error from an `else`, a fact that cannot be computed, a stream item, the three output modes, the fingerprint, `derive`, the client and an event published and consumed).

## 17. Platform phase P2: timed moves, flags, deadlines, service levels (`spec/platform.md` sections 10 to 16)

The behaviour is `spec/platform.md`; this section holds the names and the choices of the Rust target, which mirror `spec/targets/typescript.md` 5j in Rust's idiom (snake case, traits where the others have interfaces). The four capabilities (`rules_timed`, `rules_flags`, `timeouts`, `slo`) are declared one after the other; a contract that uses none of them generates the bytes it generated before: each runtime line is behind a gate (`timed`, and the others below), and the `run` function of the server core is the old text when `timed` is off.

### 17.1 Timed moves (`rules_timed`)

Both roles declare it. The server tree has `Features::timed` / `Tree::timed` when a served endpoint takes a timed edge (`// #if timed` in `src/veld/rules/mod.rs`, `// @if timed` in `src/veld/server.rs`).

- **The guard.** In step 6, right after the state check, `if !vr::due(now, &fact_booking.pending_since, 86400000_i64)` answers `409 InvalidTransition` with `field`, `from` and `to` as usual and the violation message `violates rule transition: not due`. `now` is the one clock reading of step 6. `vr::due` is `now - since >= after_ms` with checked arithmetic: exactly `after` is due, a millisecond less is not, a `since` in the future or that is not an RFC 3339 datetime is not due. The milliseconds come from the edge of the machine; the transition has one source.
- **`timed_moves()`** is an associated function of the generated enum of a machine with a timed edge, in server and client (not in a machine without one): `pub const fn timed_moves() -> &'static [(Status, Status, i64)]`, `(from, to, milliseconds)` in the order of the edges. *Differs:* a tuple, not a struct, so the client needs no runtime for it; a variant of the enum called `timed_moves` cannot clash because variants are `PascalCase`.
- **The loaders and the runner**, generated into `<service>_server.rs` for a service with a timed endpoint: `trait <Service>DueLoaders` (one `fn expire_booking(&self, before: SystemTime, limit: usize, ctx: &RequestContext) -> impl Future<Output = Result<Vec<ExpireBookingRequest>, veld::Error>> + Send` per timed endpoint: the request structs the loader answers are the endpoint's own), `struct <Service>DueOptions<D> { loaders, now: Option<SystemTime>, limit }` (`new(loaders)` gives limit 100 and the clock of the hooks) and `run_<service>_due_moves(handler: &Handler<E>, options: &<Service>DueOptions<D>) -> Result<veld::server::DueReport, veld::Error>` with `DueReport = BTreeMap<String, DueCounts { ran, moved, refused, failed }>` keyed by the endpoint's contract name (`expireBooking`). *Differs from the TypeScript names:* the loaders are in the options as there, and the runner takes the handler (which owns the service and the hooks) instead of `impl` and `hooks`.
- **The principal.** `<Service>Hooks::timer_principal(&self) -> impl Future<Output = Option<Principal>>` (the principal model when the hooks are typed) has a default body that answers `None`. The runner asks it once; an endpoint with authentication and no principal makes the run return `Err("<endpoint>: hooks.timer_principal is required")` before the loader is asked or anything runs. The clock is `options.now`, else `Hooks::clock(ctx)`.
- **The run.** For each timed endpoint: `before = now - after`, the loader, then each answer (at most `limit`) is turned into a wire request (`veld::server::due_request`: path, query, headers, body from the parameter bindings of the endpoint) and run in process by `Handler::due_move`, which enters the same pipeline after step 3: `RequestContext` carries a hidden `TimerCall { principal, now }`, the guard skips authentication and middleware for it, and step 6 reads `now` from it. Steps 4 to 10 are the ordinary ones, so the policies, the idempotency key, the output rules and the digest apply. An answer below 300 counts as `moved`, a `409` whose type is the endpoint's `InvalidTransition` as `refused`, any other as `failed` (a `4xx` goes to `on_error` from the runner; a `5xx` was reported by the pipeline); a loader that fails is one failure of its endpoint, goes to `on_error` and does not stop the other endpoints.
- **Tests.** `crates/emitters/rust/tests/platform_timed.rs`: snapshots, the words of the feature (and their absence for a contract without a timed edge), `check_timed_is_generated` in `tests/conformance.rs`, and in scratch workspaces the crates build and pass `clippy -D warnings` with `tests/toolchain/rust/timed-harness` (exactly due, one millisecond early with its message, a state check before the due check, `since` in the future, one that is not a datetime, `timed_moves()` in both roles, the runner with a memory loader: the timer's principal reaches the handler, `before`, a move another request made first is `refused` and never reaches the handler, a failing handler is `failed` and does not stop the others, `limit`, `now` and the hooks' clock, a run without `timer_principal`) and `tests/toolchain/rust/timed-examples` (the 8 examples of `tests/rules/endpoints/timed.veld.pending` through `veld_testing::Live`).

### 17.2 Flags (`rules_flags`)

Both roles declare it. `Features::flags` (`// #if flags` in `src/veld/rules/mod.rs` and `src/veld/server.rs`; implies `rules`) is on for a crate whose used services (or consumed ones) have a flagged statement; `Features::flags_server` (the file `src/veld/flags.rs` and the provider in the hooks) when a served endpoint can reach a flag.

- **The provider.** `veld::flags::FlagProvider` is a trait with `fn is_on<'a>(&'a self, name: &'a str, context: &'a FlagContext) -> impl Future<Output = Result<bool, veld::Error>> + Send + 'a`. **`is_on` is async** because the other hooks that reach outside the process (`auth_*`, the idempotency store, the fact loaders) are, and a flag service is a network call; an `Err` is a failing provider. `FlagContext { principal: Option<Principal>, tenant: Option<String>, operation: String }` (`tenant` is never set: tenancy is not generated; `operation` is the whole operation signature). `MemoryFlagProvider::new(["a", "b"])` and `set(name, on)` serve tests. The hooks of a service whose endpoints can reach a flag have two required members, as for the idempotency store (an associated type and an accessor, so a server without a provider does not compile, which is how "creating the handler fails" is met): `type Flags: FlagProvider; fn flags(&self) -> &Self::Flags;`. Such hooks have no `NoHooks`, and the handler has no `plain`.
- **One reading per request, and where.** As in the Node target, every flag an endpoint can reach is read once, after authentication (and middleware and the completion of the principal), before binding: `Endpoints::read_flags(endpoint, ctx)`, which the generated dispatch implements over `hooks.flags()` and the generated function `flag_names(endpoint)` (sorted: the flags of the endpoint's own `require` and `ensure`, of the clauses of the policies its `allow` lines name, of the edges its `transition` can take, and of every flagged invariant of the declarations of the tree). The readings are `RequestContext.flags: veld::rules::FlagView` (`On`, `Off`, `Failed`); a failing `is_on` is a `Failed` reading and goes to `on_error` of the hooks. This departs from "at the first statement that has it" as the Node target does.
- **Statements.** An invariant is `if vr::invariant_on("f")` around its code in the generated check (so the bytes serve both roles: with no view in force, a client's local check, it is not evaluated; a `Failed` reading counts it as on). `FlagView::statement_on(name, when_failed)` decides a `require` and an `ensure` (`when_failed` true: a skipped `require` or `ensure` is not evaluated, an `ensure`'s `old(...)` operands with it, because they are evaluated inside the `ensure` that reads them: with the flag off the operand is not evaluated, which the reference does and the Node target still does not; step 6 keeps the view for step 9 in its state). A policy clause is `vr::flag_on("f", false) && permit` and `vr::flag_on("f", true) && forbid`, read from a thread-local view: the server core puts the view of the request in force (`rules::enter`, a guard) in `bind`, `success` and `problem_of`, which are synchronous, and around the verdict of an `allow` in step 6 (`vr::with_view`); checks are synchronous, so no view is held across an `.await`. A flagged flow edge is part of the sources of the transition guard only while its flag is on (`ctx.flags.statement_on("f", false)`: a failing provider counts a `flow` as off), so the guard refuses with `InvalidTransition`.
- **Clients.** `can_<endpoint>` and the policy function take a last argument `flag_answers: Option<&dyn Fn(&str) -> bool>` (only for an endpoint or a policy that has a flagged clause or edge; the name cannot clash with a parameter in practice, and `flags` is left free for the user's own parameters). With it a view is built from the contract's flag names (`vr::answers`) and put in force; without it the statement counts as a failing provider decides (a flagged `permit` and `flow` are off, a flagged `forbid` is on). The `*_verdict` function has no extra argument: it reads the view in force. `next_states()` lists flagged edges too.
- **The test handler** reads `Veld-Test-Flags` (base64url JSON array of names, padded or not, or standard base64): the dispatch of the test handler implements `read_flags` over the names in the header and the endpoint's `flag_names`, and never asks the provider of the hooks (which the hooks it is created with still have to name, like the idempotency store). Without the header every flag is off.
- **Choices where the text was silent.** The pre-read above.
- **Streams.** The checks of a stream item and of a message run after the call that made the stream or the conversation, so the view of the request is put in force around them. An SSE item is framed under `with_view(&ctx.flags)` (`start_sse`, for the first item and the later ones, so also a declared error that the frame writes). A WebSocket conversation carries the readings of its upgrade request: `WsIo` has them (`with_flags`, set by `run_ws` once the guard has read the flags) and `WsSession::recv` and `send` hold a `rules::Window` (`WsIo::window`) for their synchronous checks, never across an `.await`. So a flagged invariant of a message the client sends, of a message the server sends and of a stream item is evaluated with the flags the request read; the readings are not taken again for each message. (Regions `// @if flags`.)
- **Events.** `veld::events::PublisherOptions` and `ConsumerOptions` gain `flags(Arc<P>)` (`P: FlagProvider`; the options hold the provider with its type erased, so they need no type parameter) and `on_flag_error(f)`, and every generated `EventDef` has `flags: &[...]`, the sorted flags of the invariants of the event and of every declaration it reaches (a narrower list than Node's and Java's "the tree"; the readings are the same for the invariants that can be reached). `publish_event_with` and the consumer's `decode` read each flag once per message through the provider, with `FlagContext::of_event(<event signature>)` (no principal, no tenant, the whole signature of the event as the operation), and evaluate the invariants with those readings in force (`rules::with_view`). Without a provider the flagged invariants are off; a failing provider is a `Failed` reading (the invariant counts as on) and the error goes to `on_flag_error`. The consumer reads only when the digests agree (the only case in which it runs invariants). The code is behind the gate `event_flags` (`// @if event_flags`): a crate with no flagged event keeps the bytes it had, and `Features::flags_server` (the file `src/veld/flags.rs`) is on for such a crate. A crate that only publishes or subscribes has no server core, so its `FlagContext` has no `principal` member (`// @if server`). The test handler's event route (section 13) has no provider: a flagged invariant of an event is off there.
- **A service with only flagged invariants** has a test handler (`testing = true`): it is generated for every service whose endpoints can reach a flag, the production dispatch has `pub(crate)` members for it, and the crate has the endpoint rules runtime when `testing` is on.
- **Tests.** `crates/emitters/rust/tests/platform_flags.rs`: snapshots, the words of the feature and their absence for a contract without a flag, `check_flags_are_generated` (in `tests/conformance.rs`), the core vectors of `tests/rules/core/flags.json.pending` (`flags`, `provider: "failed"`) through a generated client crate and a driver that puts the case's readings in force, and in scratch workspaces `tests/toolchain/rust/flags-harness` (a flagged `require`, `permit`, `forbid`, `flow` and `ensure` on, off and failing; the failure reaching `on_error`; one reading per request and flag with the context checked; a request refused at authentication reading nothing; the `old(...)` operand of an off `ensure` not evaluated (`resizeRoom`); the client's `can_<endpoint>`, the policy function and `next_states` with and without the function) and `tests/toolchain/rust/flags-examples` (the 14 examples of `tests/rules/endpoints/flags.veld.pending` through `veld_testing::Live`). `tests/events_flags.rs` with `tests/toolchain/rust/events/flags.rs` (`tests/toolchain/contract/platform_p2/flags_events.veld`: the publisher and the consumer with no provider, one that says on, off and one that fails; the context; one reading per message; `on_flag_error`) and, in `platform_flags.rs`, `a_flagged_invariant_of_a_stream_item_and_a_message_is_evaluated` with `tests/toolchain/rust/flags-streams-harness` (`tests/toolchain/contract/platform_p2/flags_streams.veld`, over real sockets: SSE items, messages in both directions, a failing provider, and the `Veld-Test-Flags` of the test handler of a service whose only rules are flagged invariants).

### 17.3 Deadlines (`timeouts`)

Both roles declare it. `Features::timeouts` (`// @if timeouts`): `EndpointSpec` has `timeout_ms: Option<u64>` (written into every `ENDPOINTS` literal of the crate, server and client, as `Some(200)` or `None`) and `StdSigs` has `deadline` (the signature of `DeadlineExceeded`); a crate without a deadline has neither, and its server core is the text of before (`run` is split into `run`, `run_ctx` and `run_after_guard` only when `timed`, `timeouts` or idempotency need it: the gates `refactor` and `split`).

- **The context.** `RequestContext.deadline: Option<SystemTime>` (arrival plus `timeout_ms`; `None` for an endpoint without one) and `expired()`. *Differs from the others:* there is no signal object: a handler is cancelled, as the spec says for Rust, by dropping its future.
- **The answer.** The guard (steps 2 to 5) and then steps 6 to 10 (`run_after_guard`, with the handler) each run under `tokio::time::timeout_at` of the same instant (`within`). When the instant comes first the future is **dropped, which is a real cancellation** (at its next `.await`; what a handler already wrote stays written, and its doc says that a handler which writes must watch `ctx.deadline`), and the answer is `504 DeadlineExceeded` with `{ "timeoutMs": "<ms>" }` (a `long` is text) built by `Handler::deadline_exceeded` as problem+json with the operation; the digest header and the `Veld-Rules` stamp still apply because it goes out through `handle`. A deadline is a declared error, not a failure: nothing goes to `on_error`. The instant is `tokio::time::Instant::now() + timeout` taken in `run_ctx`, so the crate depends on `tokio` with the `time` feature (added to `Cargo.toml` for a server with a deadline) and the server must run on a tokio runtime with its time driver (axum's does); an `sse` or `ws` endpoint has no deadline (`E0602`).
- **The idempotency key.** The wait is on `run_after_guard`, not on the whole of `run_ctx`, so the `Hold` of the key is still alive when the timeout fires: `idem_finish` receives the `504` (a `5xx`), releases the key and awaits it **before** the answer is sent, so the next request sees the key released and not "running", and the `Hold` has given the key up (`started` is `None`), so the drop guard does not release it a second time, and nothing of the cancelled handler can settle it later (its future no longer exists). A request dropped by the client at the same moment is still covered by the guard of section 14.
- **The client.** `ClientOptions::timeout` was always the timeout of the transport (`reqwest`: the request builder, `ureq`: the request), default 30 s. With `timeouts` the options remember whether the caller set it (`timeout_set`): a call of an endpoint with `timeout_ms` uses it when the caller did not, else `options.timeout`. The failure is the existing one, `Error::Transport` (a timed-out request). Streams are not affected (no deadline on them).
- **Tests.** `crates/emitters/rust/tests/platform_service_levels.rs` and `tests/toolchain/rust/levels-harness` (program `deadline`): an answer in time (the context has the deadline and not `expired()`; an endpoint without one has none), the `504` and its body, content type and timing, the future dropped (the handler never reaches its end, also after the time it needed), no `on_error`, an endpoint without a deadline not cut, the key released (a second request with the key runs, a third replays, the handler ran twice, the cancelled one never finished), and the client's default timeout against a server that never answers, the caller's timeout winning; `check_timeouts_are_generated`.

### 17.4 Service levels (`slo`)

The server declares it (a client generates nothing for `@slo`: the declaration is what it supports); `Features::slo`.

- **The hook.** `<Service>Hooks::metrics(&self, metric: &veld::server::Metric)`, optional (a default empty body), present in the trait **only for a service with an `@slo` endpoint**. `Handler::handle` and `invoke` call `Handler::measured` instead of `run`: it times the pipeline with `std::time::Instant` and, once the answer exists and before the adapter writes it (the core cannot see the write), calls `Endpoints::metrics` once for every request that matched an endpoint of the server, one that states no objective too. A hook that panics is ignored (`catch_unwind`); a pipeline cannot throw in Rust, so there is no "reported as `500`" case. With a deadline the `504` is what is measured.
- **The value.** `veld::server::Metric { name: "http.server.request.duration", unit: "s", value: f64, http_request_method, http_route (the full path template of the endpoint), http_response_status_code: u16, error_type: Option<String> (the status as text, only for a 5xx), veld_service ("<package>/<Service>", written into `EndpointSpec.service`), veld_endpoint, veld_operation (the whole operation signature) }`. *Differs:* the attributes are fields in snake case, not a map; `Metric::to_json()` gives the exact value of `spec/platform.md` section 13 with the dotted names of the OpenTelemetry conventions.
- **Tests.** `levels-harness` program `slo`: the metric of a `200`, a declared error, a `500` and a `504`, the attributes and their names, an endpoint without an objective measured and a route that matches nothing not, a hook that panics ignored; a server without an `@slo` has no `metrics` in its hooks, no `Metric` and no `measured` (`a_contract_without_them_has_none_of_the_words`); `check_slo_is_generated`.

### 17.5 The four together

`tests/toolchain/contract/platform_p2/all_four.veld` (a timed edge that is also flagged, a flagged `require` and invariant, a deadline, a service level, an idempotency key) generates in both roles, with the test handler, and the crates build and pass `clippy -D warnings` (`the_four_features_together_generate_and_build`); the server file and the test handler are snapshotted.

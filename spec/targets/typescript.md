# Targets: `node` (server) and `typescript` (client)

Status: normative for the built-in TypeScript generators. Both share one implementation of models, runtime and validation, so the same contract produces byte-identical `runtime/` and `models/` files in both roles.

## 0. Hard rules
- **Zero runtime dependencies.** No generated file imports a package, with one exception: the file of the framework the user chose (`nest`, `react`, `vue`, §1a). The WebSocket adapter `server/ws.ts` (§4b) is written against the `ws` package, a declared exception: it is typed structurally and imports nothing, and the server's `package.json` lists `ws` as a peer dependency, but only when the contract has `ws` endpoints. The plain adapters (`express`, `fastify`, `hono`, `node-http`) use *structural* types: a `RouterLike` shape, not `import express`.
- **Self-contained.** Every target directory compiles on its own under `tsc --strict` with `"module": "commonjs"` or `"nodenext"`. The oldest supported ECMAScript edition is ES2020: the output compiles with `tsc --strict --target es2020` and `--target es2022` (see the `typescript` option in §1a).
- **Identity by signature, never by class.** Every model, enum, union and error exposes `sig` from the IR verbatim. Equality uses `same()` (`spec/ir.md` §5.4), which needs the declaration identity of both operands (§2a): data alone never makes two values the same.
- Every file starts with `// Code generated by veld. DO NOT EDIT.`. Imports are relative, sorted, and use `import type` where possible. The formatting is fixed: two spaces, single quotes, semicolons and trailing commas.

## 1. Layout

Server target (`role = "server"`, `emitter = "node"`). The server's own package is laid out flat at the root. Any other package whose declarations the server uses goes under `deps/<package>/`. Each consumed service gets a self-contained client tree under `clients/<service>/`:
```
<out>/
  package.json                   the package manifest (section 1b)
  README.md                      how to import and regenerate (section 1c)
  index.ts                       barrel: models, errors, service interfaces, handler, adapters, clients
  runtime/veld.ts                VeldError, VeldHttpError, VeldTransportError, canonical(), same(),
                                 problem+json encode/decode, validation primitives, router core
  models/<module path>.ts        home package: one file per contract module: interfaces + companion objects
  errors/<module path>.ts        home package: error classes (only if the module declares errors)
  prelude.ts                     prelude errors used by this target (BadRequest, NotFound, ...)
  server/<service>.ts            `<Service>Service` interface, request types, `create<Service>Handler`
  server/adapters.ts             toExpress / toFastify / toHono / toNodeHttp (structural types only)
  server/ws.ts                   attachWebSocket (only when the contract has `ws` endpoints, §4b)
  deps/<package>/models/...      declarations of other packages that the server imports (and errors/...)
  clients/<consumed>/            one client tree for each service in `consumes` (client layout below,
                                 with its own index.ts and prelude.ts):
    index.ts
    prelude.ts
    <package>/{models,errors,client.ts}
```
Client target (`role = "client"`, `emitter = "typescript"`; `framework` is `react`, `vue` or absent, and any other value is `E0803`):
```
<out>/
  package.json                   the package manifest (section 1b)
  README.md                      how to import and regenerate (section 1c)
  index.ts                       barrel; also `createClients` (section 4)
  clients.ts                     `createClients(opts)`: one client per service
  runtime/veld.ts                identical bytes to the server's runtime/veld.ts
  prelude.ts
  <package>/models/<module path>.ts
  <package>/errors/<module path>.ts
  <package>/client.ts            `<Service>Client` class per service block
```

## 1a. Options, language version and frameworks

Both generators take the same language option in `[targets.options]` (validated centrally, `E0802` when wrong, the message lists the valid values):

| Option | Default | Meaning |
|---|---|---|
| `typescript` | `"es2020"` | The ECMAScript edition the output targets: `"es2020"` or `"es2022"`. The oldest supported is the default. The output is the same for both today; `Profile::ecmascript_at_least(2022)` is how newer syntax or library calls would be gated. |
| `validate` | `true` | `false` skips run-time **request** validation by default (the types are unchanged): the `node` handler is created with `validateRequests: false` (a `validateRequests` hook can turn it back on) and the `typescript` client with `validate: false` (the client option `validate: true` turns it back on). Responses are never validated unless `validateResponses` is set. |
| `query-options` | `false` | `typescript` client only: `true` also writes `<package>/queries.ts` (§4a.1). |
| `testing` | `false` | `node` server only: `true` also writes `server/<service>-test-handler.ts` for each service with endpoint rules (§5c). It must never be mounted in production. |
| `framework-version` | the first version | `nest` `"10"`, `react` `"18"`, `vue` `"3"`. The plain `node` adapters are unversioned, so any value for them is `E0803`. |

`framework` (`node` server): `express`, `fastify`, `hono`, `node-http` or `nest`. The list comes from the adapter registry (`crates/emitters/node/src/frameworks/`: `express.rs`, `fastify.rs`, `hono.rs`, `node_http.rs`, `nest.rs`), the single source of truth; each adapter needs ES2020 at least (`min_language`). `server/adapters.ts` always holds all four plain adapters in one fixed order, so choosing `express`, `fastify`, `hono` or `node-http` does not change the output. `nest` adds files (§5a) and changes none of the others.

`framework` (`typescript` client): none (the default, plain client), `react` (`framework-version = "18"`, zero-dependency hooks) or `vue` (`"3"`, Vue 3.3 or newer). With no framework the output is byte-identical to before; a framework only adds files (§4a).

| Framework | Role | Versions | Adds | Packages it imports |
|---|---|---|---|---|
| `nest` | `node` server | `"10"` | `server/nest/<service>.ts` | `@nestjs/common` |
| `react` | `typescript` client | `"18"` | `runtime/react.ts`, `<package>/react.ts` | `react` |
| `vue` | `typescript` client | `"3"` | `runtime/vue.ts`, `<package>/vue.ts` | `vue` |

Framework files are the only generated files that import a package, and only the one the target chose. They are not in the `index.ts` barrel, so importing the barrel never needs the framework installed: import `server/nest/<service>` or `<package>/react` explicitly.

## 1b. The generated package

Every `node` and `typescript` target writes `<out>/package.json`, so that the generated directory is an importable npm package:

```json
{
  "name": "@veld/<target name>",
  "version": "0.0.0",
  "private": true,
  "description": "Generated by Veld. DO NOT EDIT.",
  "main": "index.ts",
  "types": "index.ts",
  "sideEffects": false
}
```

- The name is `@veld/<target name>` (lowercased, other characters become `-`) unless the target option `package-name` is set; an invalid npm name is `E0802`. The CLI supplies the default because a generator does not see the target name; run directly, a generator names the package `@veld/generated`.
- There are no `dependencies`. A `react`, `vue` or `nest` target adds `peerDependencies` entries (`react ^18.0.0`; `vue ^3.3.0`; `@nestjs/common ^10.0.0`) and nothing else.
- The file is deterministic, listed in the manifest, and like every generated file it is not edited by hand.
- `main` and `types` point at the TypeScript source barrel: the package is meant for TypeScript toolchains (`tsc`, `tsx`, Vite, bundlers). Deep imports work because there is no `exports` map: `@veld/web/orders/react`.
- A server's consumed-service clients are part of the same package, re-exported by the barrel as namespaces (`import { iam } from '@veld/orders-api'`).
- `veld setup` adds `"@veld/<name>": "file:<relative out>"` to the consuming app's `package.json` (`spec/config.md`).

## 1c. The generated README

Every `node` and `typescript` target also writes `<out>/README.md`: the package name, how to import it (the client's `createClients` and client classes, or the server's handler factories and adapters), a note on the framework files that are not in the barrel, how `same()` works (§2a), and how to regenerate (`veld generate`; files listed in `.veld-manifest.json` are owned by Veld, and an edited file is kept unless `--force`). It is deterministic, holds no absolute path, host name or date, is the same for every framework (a framework only adds files), and is listed in the manifest like every generated file.

## 2. Type mapping

| Veld | TS |
|---|---|
| string, date, datetime, time, uuid, decimal, long, bytes | `string` (formats checked by validators) |
| int, float | `number` |
| bool | `boolean` |
| json | `unknown` |
| `T[]` | `T[]` |
| `Map<string,T>` | `Record<string, T>` |
| `Page<T>` | `Page<T>` from runtime (`{ items: T[]; total: string; page: number; size: number }`) |
| `name?: T` | `name?: T` |
| enum | `type Status = 'pending' \| 'paid'` (wire values) plus a companion `const Status = { pending: 'pending', … , sig }` |
| union | a discriminated union of the arm interfaces, each extended with `kind: 'label'` |
| model `extends` | `interface Child extends Parent` (the IR already flattened the fields; the emitter declares only the fields with `inherited_from == null`) |

Each model, enum and union also gets a **companion object** with the same name:
```ts
export const Order = {
  sig: 'veld:orders/Order@9f2c41d07ab3e855',
  validate(value: unknown, path = '$'): Issue[],   // full structural + constraint validation
  canonical(value: Order): string,                 // RFC 8785 JSON of the wire form
  same(a: Order, b: Order): boolean,
} as const;
```
Field names in TS use the source name, converted to camelCase only if they are not valid identifiers. If a wire name differs from the source name (`@wire`), the companion has `toWire`/`fromWire`, and the client and server call them. When the names are equal, no mapping code is emitted.

## 2a. Value identity and `same()`

`spec/ir.md` §5.4 says two values are the same only when their declaration signatures match and their canonical bytes match. Two *different* declarations with identical fields have identical canonical bytes, so bytes alone must never decide.

- **Values carry their declaration.** Every value the generated code produces gets two non-enumerable symbol properties: `Symbol.for('veld.sig')` (the declaration `sig`) and `Symbol.for('veld.schema')` (its schema, so defaults and normalisation apply). That covers a client decode (success values, list items, page items, union arms; a union value carries the *union's* sig), the request a server binds (body, query objects, `ws` messages), `fromWire`, and `Model.of(value)`. `Symbol.for` makes the symbols the same in every separately generated copy of the runtime. They are not enumerable, so `JSON.stringify`, `Object.keys`, `for...in` and `canonical()` never see them; a spread (`{ ...v }`) drops them.
- **Models get a factory.** The companion has `of(value)`: a shallow copy of `value` that carries the declaration identity. Enums are strings: they cannot carry identity, so compare them with `Status.same(a, b)` or `===`.
- **Global `same(a, b)`** (exported by the runtime and the barrel): errors compare by `sig`, `op` and canonical data as before (a model and an error are never the same, even with equal data); arrays compare element by element; any other pair needs a signature on *both* sides: different signatures are `false`, equal signatures compare canonical bytes with the schema's defaults applied.
- **When identity is missing** (a plain object literal, a spread, a primitive, a `Page`) `same` **throws a `TypeError`** that names the fix (`Model.same(a, b)` or `Model.of(...)`). Returning `false` would silently hide a real equality, and answering from the data would be the very bug this rule closes; a thrown error is loud, cannot be mistaken for an answer, and does not affect any value the generated code produced itself.
- **Companion `Model.same(a, b)`** keeps working for plain objects, because the declaration is implied. If either operand *does* carry another declaration's signature, it is `false`.
- The React and Vue helpers and the query options use canonical bytes only as a refetch or cache key for one endpoint of one service, never as an equality, so they do not need identity.

## 3. Errors

```ts
export class OutOfStock extends VeldError<{ sku: string }> {
  static readonly sig = 'veld:orders/OutOfStock@…';
  static readonly defaultStatus = 409;
  static matches(e: unknown): e is OutOfStock  // decl sig equal (+ same service when op is set)
}
```
- A `VeldError` instance has these fields: `sig`, `op` (operation sig, or `null` until it is raised from an endpoint), `status`, `data`, and `title` (the declaration name). It also has a `veld: 1` brand.
- `same(a, b)` from the runtime is duck-typed: it works across copies of the runtime in different directories, because it reads only `veld`, `sig`, `op` and the canonical data (schema defaults applied, via the class's static `schema`).
- **Server behaviour:**
  1. The adapter catches errors thrown by the implementation.
  2. If the error is a `VeldError` whose `sig` is declared for that endpoint, the adapter sets `op` and responds with problem+json at the declared status.
  3. Any other error, including an *undeclared* `VeldError`, becomes a `500 Internal` with no message. The original error goes to the `onError` hook. Internal details are never leaked.
- **Client behaviour:**
  - A problem+json `type` that matches one of the endpoint's declared errors is thrown as that class, with `op` and `status` set.
  - A recognised problem+json response with an unknown `type`, and any other non-2xx response, is thrown as `VeldHttpError`, with `status` and `body` set.
  - A network failure, or a body that is not valid JSON, is thrown as `VeldTransportError`.

## 4. Client

```ts
export interface ClientOptions { baseUrl?: string; fetch?: typeof fetch; headers?: Record<string,string> | (() => Record<string,string> | Promise<Record<string,string>>); auth?: { bearer?: () => string | Promise<string>; basic?: …; apiKey?: … }; }
export class OrdersClient {
  constructor(opts: ClientOptions = {})          // baseUrl: opts > env VELD_ORDERS_URL (if process exists) > IR base_url > throw VeldTransportError at construction
  getOrder(req: GetOrderRequest, init?: { signal?: AbortSignal }): Promise<Order>
}
export interface GetOrderRequest { id: string }   // path params by name, `body`, `query`, single @query params, headers by param name
```
- Method names come from `veld-codegen::naming::member`: an endpoint named `new`, `constructor`, `__proto__`, `prototype` or `then` becomes `new_`, `constructor_`, and so on (a construct signature, the constructor or a thenable would otherwise break the class or interface). Wire names and paths never change. The client keeps its internals in ECMAScript `#private` fields (`#core`), so no endpoint name can collide with them.
- Path params are encoded with `encodeURIComponent`. Query objects are serialised as repeated keys for lists, absent optionals are left out, and keys are sorted for determinism.
- Before sending, the client validates the request with the companion validators, and it throws a `VeldError` `ValidationError` locally with `op` set. The `validate` option is on by default.
- Success: the client parses JSON according to the success type, and resolves to `void` for no-body responses.
- SSE (`-> stream T` on get) returns `AsyncIterable<T>`, and `ws` endpoints return a `WsChannel` (§4b).
- **`createClients(opts, overrides?)`** (`clients.ts`, re-exported by `index.ts`) builds one client per service from one `ClientOptions`: `createClients({ baseUrl }) -> { orders: OrdersClient, iam: IamClient }`. The keys are the camelCase service names (qualified by the package when two packages of one target declare the same service name). `overrides` is `{ [service]?: ClientOptions }`, merged over the shared options, for the usual case of one `baseUrl` per service. `Clients` and `ClientOverrides` are exported types.

## 4a. React and Vue helpers (`framework = "react" | "vue"`)

Both are thin, typed wrappers over the generated client classes. The state machines live once in `runtime/<framework>.ts`; `<package>/<framework>.ts` adds one hook per endpoint. They use only the framework's own API (no TanStack Query), keep the typed error classes (`NotFound.matches(error)` works) and import nothing else. Endpoint hook names are `use<Endpoint>`, prefixed with the service name when two services of a package share an endpoint name.

- **Streams** (`get ... -> stream` and `ws`): `use<Endpoint>Stream(req | null, opts?)` with `opts = { enabled?, client?, accumulate?, max? }` returns `{ items, latest, error, streaming, restart }`, and `send` too for a `ws` endpoint. The stream re-opens when the canonical bytes of the request change, and is aborted on a change and on unmount (React) or scope disposal (Vue). A typed error lands in `error`. The streaming part of `runtime/<framework>.ts` is added only when the contract has streams.
- **Queries** (GET endpoints): `useGetOrder(req, opts?)` with `opts = { enabled?, client? }`. A `null` request or `enabled: false` holds the call back. The call re-runs when the **canonical bytes** of the request change (a new but equal object does not refetch), and the previous call is aborted on a change and on unmount (React) or scope disposal (Vue). Stale data is not shown for a different request. `refetch()` re-runs the call and keeps the data while loading.
- **Mutations** (every other method): `useCreateOrder(opts?)` returns `mutate(req)`, which never rejects: a failure lands in `error` and `mutate` resolves to `undefined`. Only the latest `mutate` updates the state, and it is not aborted on unmount.
- **React 18** (`react`): `useGetOrder(req | null, opts) -> { data, error, loading, refetch }`, `useCreateOrder() -> { mutate, data, error, loading, reset }`. `<VeldProvider clients={{ orders: client }}>` provides the clients and `useOrdersClient(client?)` reads them (or throws, naming `VeldProvider`). The files are plain `.ts` (`createElement`, no JSX).
- **Vue 3.3+** (`vue`): the same names, but `data`, `error` and `loading` are refs, and the request may be a ref or a getter: `useGetOrder(reqRef)` reacts to changes. The composables use `watch` and `onScopeDispose`, so they work in components and in a bare `effectScope`. `createVeldPlugin({ orders: client })` provides the clients (`app.use(...)`) and `useOrdersClient(client?)` injects them.
- Abort uses `globalThis.AbortController` when present, so the files need no DOM or Node typings.
- **Forms with rules** (only when the contract has rules; nothing is added otherwise). `useFormRules(model, draft)` takes a model's companion (`Booking`) and a draft of it, and runs `<Model>.partial(draft)` (§5b): a rule that needs a field the draft lacks is skipped, not failed. It returns `{ violations, messages, valid }`: `violations` are the violation objects of `partial`; `messages` maps a field to the messages of the rules that read it, taken from each violation's `fields` (`messages.end` is the list of messages for `end`, in the order of `violations`); `valid` is `true` when the draft currently has no violations (an incomplete draft can be valid). Names are **wire** names, as in `fields`; a violation of a nested value is keyed below the path of the value that carries the rule (`address.city`, `rows[1].qty`, with the leading `$` dropped). The pure function `formRules(violations)` does the grouping and is exported too. React: `useFormRules(Booking, draft)` returns the plain object and recomputes when `draft` is a new object (keep it in immutable state); Vue: the draft may be a ref, a getter or a reactive object, and the result is `{ violations, messages, valid }` as computed refs (`FormRulesRefs`). Both live in `runtime/<framework>.ts` and are re-exported by `<package>/<framework>.ts` with the types `FormModel` and `FormRules`; they add no import beyond the framework itself.

### 4a.1 Query options (`query-options = true`, no dependency)

With the target option `query-options = true`, the `typescript` client also writes `<package>/queries.ts` and re-exports it from the barrel. It is **off by default**, so the plain client output never changes; it needs no `framework` and no peer dependency. The file imports nothing from any package: it holds plain objects with the shape TanStack Query's `useQuery`, `useMutation` and `invalidateQueries` take, which work just as well with SWR or a hook of your own. You keep the choice of library (and of none).

Per service (`orders` for `Orders`):

```ts
export function createOrdersQueries(defaultClient: () => OrdersClient = () => new OrdersClient()) {
  const all = ['veld', 'orders'] as const;
  const keys = { all, getOrder: (req: GetOrderRequest) => [...all, 'getOrder', veld.canonical(req)] as const, /* ... */ };
  return {
    keys,
    getOrder: (req: GetOrderRequest, client: OrdersClient = defaultClient()) => ({
      queryKey: keys.getOrder(req),
      queryFn: (ctx: { signal?: veld.AbortSignalLike }): Promise<Order> => client.getOrder(req, { signal: ctx.signal }),
    }),
  };
}
export const ordersQueries = createOrdersQueries();
export function createOrdersMutations(defaultClient = ...) {
  return { createOrder: (client = defaultClient()) => ({ mutationKey: ['veld', 'orders', 'createOrder'] as const, mutationFn: (req: CreateOrderRequest) => client.createOrder(req) }) };
}
export const ordersMutations = createOrdersMutations();
export type OrdersGetOrderError = NotFound | Unauthorized | ... | veld.VeldHttpError | veld.VeldTransportError;
```

- **Queries** are the GET endpoints that are not streams; every other endpoint that is not a stream is a mutation. Streams (`stream`, `ws`) have no query form (use the stream hooks of §4a or the client directly).
- **Keys are stable and canonical**: `keys.all` (`['veld', '<service>']`) prefixes every query of a service, `keys.<endpoint>(req)` is `['veld', '<service>', '<endpoint>', canonical(req)]`. Equal requests share a key whatever the property order, because the key holds the canonical bytes of the request (`spec/ir.md` §5), never an object identity.
- **The client** comes from the last argument or from the `defaultClient` factory of `create<Service>Queries` / `create<Service>Mutations` (default: `new <Service>Client()`, which reads `baseUrl` from the environment or the contract). There is no global instance: build your own set with `createOrdersQueries(() => myClient)`.
- **Cancellation**: `queryFn` hands the `signal` of TanStack (or of your own `AbortController`) to the client.
- **Typed errors**: a failed call rejects with the generated error classes, so `NotFound.matches(e)` and `same()` keep their meaning. `<Service><Endpoint>Error` is the union a call can fail with (declared errors plus `VeldHttpError` and `VeldTransportError`): pass it as the error type, for example `useQuery<Order, OrdersGetOrderError>(ordersQueries.getOrder({ id }))`.
- **Invalidation** is plain TanStack: `queryClient.invalidateQueries({ queryKey: ordersQueries.keys.all })` after a mutation.
- Tested in `tests/toolchain/ts/query_options.tsx` against the real generated server with a pinned `@tanstack/react-query` (a test dependency only: the generated code never imports it), and with a hand-written hook that needs no library.

## 4b. Streaming (SSE and WebSocket)

Streaming goes through the same pipeline as every other endpoint (routing, auth, middleware, binding, validation, declared-error mapping); there is no second implementation of the semantics. `EndpointSpec` carries `stream: true` and a stream-body param carries `s: true`.

**Server-Sent Events** (`get ... -> stream T`).
- Wire: `200 text/event-stream`, `cache-control: no-cache`. Each event is `[id: X
][event: Y
][retry: N
]data: <canonical JSON of T>

` (`sseFrame`; the golden bytes are `tests/wire/streaming/sse.json`). `data` is the RFC 8785 canonical form, so it is always one line.
- Server: the implementation returns `AsyncIterable<T | SseEvent<T>>` (an `async *` generator is enough). Yield `veld.sseEvent(value, { event, id, retry })` to set the fields. `Last-Event-ID` is in `ctx.headers['last-event-id']`.
- The first item is pulled before the status is sent. An error raised before the first event is a normal problem+json response with the declared status, `sig` and `op`. After streaming has started an error is sent as a final `event: error` whose data is the problem JSON (`type`, `title`, `status`, `operation`, `data`), and the stream closes; an undeclared error becomes `Internal` without a message. With `validateResponses` every item is validated first (failure: `Internal`, by the same two rules).
- Closing: when the client goes away the adapter stops iterating and the generator's `finally` runs (at the latest when the next item is produced).
- Adapters: `node-http` and `express` write frames as they arrive; `fastify` needs `reply.raw` (the reply is hijacked); `hono` streams a `ReadableStream`; `nest` uses the plain adapter. `VeldResponse.stream` is the frame iterable.
- Client: the endpoint's method `ticks(req, { signal, lastEventId, onEventId })` returns an `AsyncIterable<T>` built on `fetch` streaming (not `EventSource`, so headers and auth work). The request is made when iteration starts. A non-2xx response and an `error` event are thrown as the typed error (same `matches()`/`same()` rules; unknown ones are `VeldHttpError`). Aborting the signal or `break` ends the iteration quietly and closes the connection. There is **no automatic reconnect** unless `reconnect` is given (below): call again with `lastEventId` (collected with `onEventId`) to resume.

**WebSocket** (`ws "/path" name(params, body: stream In) -> stream Out`).
- Path, query and header params come from the upgrade request. The stream body is not part of the request type.
- Frames are text. Client to server: the canonical JSON of the message. Server to client: `{"data":<canonical JSON>}` or the final `{"error":<problem JSON>}`; the envelope exists because an error must be distinguishable from a message. After an error frame the server closes with 1008 (declared errors, validation, auth) or 1011 (`Internal`); a normal end is 1000; a path that is not a `ws` endpoint is 4404; binary frames are 1003.
- Server: `chat(req, ctx, ws: WsSession<In, Out>): Promise<void>`. `ws.incoming` is an `AsyncIterable<In>` (validated, ends at close), `ws.send(out)` sends canonical JSON (validated when `validateResponses`), returning ends the socket. Every incoming message is validated against `In`; a bad one produces a `ValidationError` frame whose issues have the path `message` and closes. A thrown declared error is sent as a problem frame (typed on the client); anything else is `Internal`. Frames that arrive while auth and middleware run are held back.
- Auth uses the same hooks as HTTP, from headers, or when the header is absent from `?access_token=<token>` (bearer) or `?api_key=<key>` (API key), because browsers cannot set headers on a WebSocket. A token in a URL can end up in logs: prefer short-lived tokens. Basic auth is not available over WebSocket. `@header` params are read from the headers or the query string of the same name. A failed handshake is answered after the upgrade (problem frame, then close), so the client gets the typed `Unauthorized`.
- **Reconnect** (`reconnect?: { initialMs, maxMs, retries }`, on the `init` of `stream` and `ws` calls). Off by default in the plain client, so the semantics above hold; **on by default in the React and Vue stream hooks** (`reconnect: false` switches it off there). Defaults: 1000 ms doubling to 30000 ms, 10 consecutive failures. Only *connection failures* are retried: a refused or broken connection, a stream that breaks mid-way, an abnormal WebSocket close. A typed error, an error frame or event, a declared `VeldHttpError`, a normal end and an abort or `close()` (also during the backoff) never reconnect. SSE resumes with `Last-Event-ID` set to the last event id the caller was given, so the caller sees one continuous stream; the failure counter starts again after an event was delivered. A WebSocket opens a new socket (the server starts a new conversation, with no resume): messages sent while the connection is down are queued and sent after the reconnect, a message that was already written to the broken socket is lost, and the counter starts again after a frame arrives or after a connection that lived at least `maxMs`. When the attempts run out the last `VeldTransportError` is thrown.
- Mounting: `attachWebSocket(new WebSocketServer({ server }), handler)` from `server/ws.ts`; `handler.ws(req, socket)` is the transport-independent entry. `nest` leaves `ws` endpoints to this adapter.
- Client: `chat(req, { signal })` returns `WsChannel<Out, In>` (from the client's side: iterate the server's messages, `send` the client's). It uses the global `WebSocket` (browsers, Node 22) or `options.webSocket`; the socket opens immediately and `send` queues until it is open. `send` validates (unless `validate: false`) and throws the local `ValidationError`. Iteration ends on a normal close, throws the typed error of an error frame, and throws `VeldTransportError` when the connection fails or closes abnormally. `close()` or aborting the signal closes the socket.

## 5. Server

```ts
export interface OrdersService<Ctx = RequestContext> {
  getOrder(req: GetOrderRequest, ctx: Ctx): Promise<Order>;
  createOrder(req: CreateOrderRequest, ctx: Ctx): Promise<Order>;
  health(req: {}, ctx: Ctx): Promise<void>;
}
export interface OrdersHooks {
  auth?: { bearer?: (token: string, ctx: RequestContext) => Promise<unknown | null> };   // required (by type) if any endpoint needs it
  middleware?: { RateLimit: (ctx: RequestContext) => Promise<void> };                   // required if used
  onError?: (err: unknown, ctx: RequestContext) => void;
  validateResponses?: boolean;  // default false; when true, a response that fails validation becomes a 500
}
export function createOrdersHandler(impl: OrdersService, hooks: OrdersHooks): VeldHandler;
```
- `VeldHandler` is `(req: VeldRequest) => Promise<VeldResponse | null>`, where `null` means no route matched. Routing is done once in the runtime's router core, from the IR paths. Matching is exact on literal segments, with params extracted. HEAD is not implicit.
- The pipeline for each request is:
  1. match
  2. auth, which gives 401 `Unauthorized` if credentials are missing or rejected
  3. middleware, in declared order
  4. bind and validate path, query, headers and body, which gives 422 `ValidationError` with `issues`
  5. call the implementation
  6. optionally validate the response
  7. serialise with the declared success status
- `RequestContext` contains `{ method, path, headers, principal, raw }`, where `raw` is the framework's request object.
- **Adapters** in `server/adapters.ts`:
  - `toExpress(handler)` returns an Express-compatible middleware `(req, res, next)`. It reads `req.body` if a body parser already ran, otherwise it reads the stream.
  - `toFastify(handler)` returns a catch-all handler.
  - `toHono(handler)` returns `(c) => Response`.
  - `toNodeHttp(handler)` returns a `http.createServer` listener.
  
  All four use structural types and none imports anything.

## 5a. NestJS (`emitter = "node"`, `framework = "nest"`, `framework-version = "10"`)

`server/nest/<service>.ts` holds, per service, a `@Controller('<prefix>')` class with one decorated method per endpoint (`@Get(':id')`, `@Post()`, ... `@HttpCode(<success status>)`) at the **real paths**, so Nest and Swagger see the real routes. Literal routes are registered before parameterised ones, as in the router core.

```ts
@Module({ imports: [OrdersVeldModule.forRoot({ useClass: OrdersImpl, hooks })] }) class AppModule {}
OrdersVeldModule.forRoot({ useClass | useValue | useFactory (+ inject, imports), hooks })
```
- `ORDERS_SERVICE` and `ORDERS_HOOKS` are the DI tokens; the module exports `ORDERS_SERVICE`. `hooks` is required exactly when `OrdersHooks` has required members.
- Each method delegates, through `@Req()` / `@Res()` and the plain `toNodeHttp` adapter, to the SAME `create<Service>Handler` pipeline as every other adapter: auth, middleware, validation, declared-error mapping, undeclared errors becoming `Internal` without leaking, problem+json with `sig` and `op`. There is no second implementation of the semantics, and Veld's status codes and bodies are exact. A missing required hook fails when the module is created, not on the first request.
- Needs `experimentalDecorators` and `emitDecoratorMetadata` in `tsconfig.json`. Only `server/nest/**` needs them: every other generated file still compiles without those flags (`tsc --strict`, no decorator options, no Nest packages). Nest's own body parser runs first, so a malformed JSON body is answered by Nest (400) before Veld sees it.
- Limits: a global prefix (`app.setGlobalPrefix`) or URI versioning changes the path the router core sees and is not supported; mount the module under the contract's own prefix instead.

## 5b. Rules (invariants)

Both generators implement `rules_invariants` (`spec/rules.md` §5 and §8). The other three rules features (`rules_endpoint`, `rules_transitions`, `rules_policies`) are still refused with `E0801`.

**A contract without rules gets the same bytes as before.** The rule code is added in two ways only: `runtime/rules.ts` is emitted *only* when an emitted declaration has an invariant, and the lines of `runtime/veld.ts` that need to know about rules sit between `// #if rules` and `// #endif` marker lines in the embedded source. `veld_codegen::gate_regions` drops the marker lines, and drops the lines between them unless the contract has rules, so a contract without rules gets `runtime/veld.ts` exactly as it was before rules existed. Everything below is about a contract that has rules.

### Layout
```
runtime/rules.ts        the value helpers and the three evaluation errors (the list below); no imports
runtime/veld.ts         + the schema walk, the pipeline steps, the local client check (gated regions)
models/<module>.ts      + a check function `check<Decl>Rules` per declaration with rules, and `ruleIds`
```
A generated file that has a check function imports the helpers as `import * as veldRules from '<rel>/runtime/rules'`. Both generators emit the same models, so the same check functions.

### Values while a rule runs
`int` and `float` are `number`; `long`, `duration`, `datetime`, `date` (days since the epoch) and `time` (milliseconds since midnight) are `bigint`; `decimal` is a `Decimal` (`{ n: bigint, s: number }`, the value `n * 10^-s`); `string`, `uuid` (lower case), `bytes` (base64 text) and enums (wire strings) keep their wire form. A field read converts at the leaf (`self.price` of type `decimal` is `veldRules.dec(...)`), and a list read converts its elements once, so a lambda variable over scalars is a bare identifier (`l_<name>`). Comparisons, `&&`, `||`, `!`, `startsWith`, `endsWith`, `includes` and `===` are native; every checked or exact operation is a helper. A required step of a path goes through `veldRules.required(...)`, which throws `AbsentField` for an absent value (only a partial check can see one); an optional step the compiler proved present is read with `!`.

### Helper reference list (`runtime/rules.ts`)
The other targets mirror these names in their own naming style; `crates/veld-rules/src/helpers` is the reference for every one.

| Group | Names |
|---|---|
| Errors | `RuleEvalError` (`kind`: `overflow`, `division_by_zero`, `non_finite`), `AbsentField`, `required`, `unavailable`, `failed` |
| `int` (`number`) | `addInt`, `subInt`, `mulInt`, `divInt`, `remInt`, `negInt` |
| `long`, `duration` (`bigint`) | `addLong`, `subLong`, `mulLong`, `divLong`, `remLong`, `negLong`, `toLong` |
| `float` | `addFloat`, `subFloat`, `mulFloat`, `divFloat`, `remFloat` |
| duration | `days`, `hours`, `minutes`, `seconds`, `ms`, `dateDiff` |
| `decimal` | `dec`, `decFromInt`, `decFromLong`, `decAdd`, `decSub`, `decMul`, `decNeg`, `decCmp`, `decIn` |
| `date`, `datetime`, `time` | `toDate`, `toDatetime`, `toTime` (parsed by hand, never `Date.parse`; digits below the millisecond are dropped) |
| strings | `lenString` (code points), `lenBytes`, `lenMap`, `hasKey`, `toUuid`, `matches` (`new RegExp(pattern, 'u')`, the same as `@pattern`) |
| comprehensions | `countWhere`, `sumInt`, `sumLong`, `sumFloat`, `sumDecimal` (`all` and `any` are `every` and `some`) |

`int` arithmetic is checked against the 32-bit range, `long` and `duration` against the 64-bit range; `/` truncates toward zero and `%` takes the sign of the dividend (`divInt(a, b)` is `(a - a % b) / b`, which is exact in a double); a zero divisor is `division_by_zero` for floats too; a float result that is not finite is `non_finite`.

### Check functions
For every model or error with at least one rule, one plain function evaluates the rules in list order on one value:
```ts
function checkBookingRules(self: Booking, path: string, mode: veld.RuleMode, out: veld.Violation[]): void {
  try {
    if (!(veldRules.toDatetime(veldRules.required(self.end)) > veldRules.toDatetime(veldRules.required(self.start)))) {
      out.push({ rule: 'veld:…', path, fields: ['end', 'start'], message: 'A booking must end after it starts' });
    }
  } catch (e) {
    veldRules.failed(e, mode, out, 'veld:…', 'endAfterStart', path, ['end', 'start']);
  }
  // …one block per rule
}
```
- `mode` is `'full'`, `'request'` or `'partial'`. A rule with `reads_readonly` is wrapped in `if (mode !== 'request')`.
- `failed` records an evaluation error as a violation with `error` and the message `rule <name> could not be evaluated`; it ignores `AbsentField` in `'partial'` mode (the rule is skipped, not failed) and rethrows anything else. Nothing else can escape a check function except a bug.
- `fields` are the wire names of `Rule.reads`; `message` is the rule's message or `violates rule <name>`.
- The declaration's schema node carries the function: `{ k: 'object', fields: [...], rules: checkBookingRules }`. `checkValue(schema, value, path, mode)` in the runtime walks a value by its schema and calls the function of every object it visits, its own rules before its fields, with the paths of `spec/rules.md` §5.2 built from **wire** field names (`$`, `$.rows[1]`, `$.named.k`, `body.items[2]`; a union arm keeps the path of the union, a page adds `.items`).

### Public surface
Every companion has `check(value, path = '$'): Violation[]` and `partial(draft): Violation[]`, which walk nested values too. A declaration with rules also has `ruleIds`, a member holding the rule ids by rule name (`Booking.ruleIds.endAfterStart`). An error class with rules has the static `ruleIds` and `check(data)`.
- `partial(draft)` (`spec/rules.md` §5.4): the draft is not shape-validated, defaults are applied, a rule whose evaluation reads an absent required field is skipped.
- `Violation` is `{ rule, path, fields, message, error? }`.
- `VeldError` has `violations` (empty unless the problem document had the member) and `local` (true when the client raised it before sending).

### Client
Before sending, the client checks the invariants of a `body` and of a `query` object in request mode, after applying defaults, once the shape validation passed. On a violation it sends nothing and throws the typed `ValidationError` with `issues` (code `rule`, or `rule_error` for an evaluation error), `violations`, `local = true` and `op`. The option `rules: false` turns the check off; `validate: false` also skips it, because the shape of the value is then unknown. An error response that carries a `violations` member decodes with `violations` filled and `local = false`.

### Server
- Step 4 is unchanged. **Step 5** (after bind and validate, only when requests are validated): the invariants of the bound `body` and `query` object, in request mode. A violation answers `422 ValidationError` whose problem document has both `data.issues` (one issue per violation, code `rule` or `rule_error`) and the top-level `violations` member (`spec/rules.md` §7).
- **Step 8**: the invariants of the result, by output mode, default `strict`. When the mode is not `off` and the success type reaches a declaration with rules, the result's shape is validated first (a shape failure is the 500 of `validateResponses` in `strict`; in `audit` the rules are skipped). `strict` answers `500 Internal` with no rule detail; `audit` sends the response unchanged.
- The hooks object of a server that has rules gains `rules?: { output?: 'strict' | 'audit' | 'off' }` and `onRuleViolation?(event)`. The event is `{ rule, operation, position: 'input' | 'output', outcome: 'rejected' | 'audited', violation, elapsedMicros }`; it is called once per violation, and an exception in the hook never changes the response. A mode other than `strict` is reported once, with `console.warn`, when `create<Service>Handler` runs.
- **Declared errors** are outputs (`spec/rules.md` §5.2). When the server encodes a declared error whose schema has rules or reaches a declaration with rules (a model in a field), it first validates the error's data (a shape failure in `strict` is `500 Internal`, in `audit` the rules are skipped), then checks the rules under the output mode. `strict`: the caller gets `500 Internal` with no rule detail and `onRuleViolation` gets the violation (position `output`, outcome `rejected`); `audit`: the error is sent unchanged and the hook gets it (`audited`); `off`: skipped. This holds wherever the error is sent: the HTTP response, the final `event: error` of an SSE stream and the error frame of a WebSocket. A client never checks an error it decodes: it keeps the data as sent and `violations` stays empty (the static `Overbooked.check(data)` is there when the caller wants it).
- **Stream items** are outputs. Every item of an SSE stream and every message the server `send`s on a WebSocket is validated and checked under the output mode before it is written. In `strict` a violating item is not sent: the check throws inside the item step, so the stream ends the way it ends on any server failure (a first item that violates is a plain `500 Internal` response; a later one becomes the final `event: error` with `Internal`; on a WebSocket `send` throws into the implementation, which ends the socket with an `Internal` error frame and close code 1011 unless it catches the error). `audit` sends it and reports; `off` skips. The Nest adapter has no code of its own for this: it serves the same handler, so SSE items and errors are checked identically (`ws` endpoints are not Nest routes, §4b).
- **Client messages on a WebSocket** are inputs. The client's `send(message)` checks the invariants of the message in request mode after the shape check, with the path root `message` (`message.items[0]`), the same option `rules: false` turns it off (and `validate: false` too), and a violation throws the typed `ValidationError` with `violations` and `local = true` before anything is written. The server rejects a violating message the way it rejects one of the wrong shape: a `ValidationError` problem frame (with `data.issues` and the top-level `violations`, path root `message`), close code 1008. The hook gets the violation (position `input`, outcome `rejected`). The checks are skipped when request validation is off.
- **Request validation turned off** (`validate = false`, or `validateRequests: false` in the hooks): steps 5 and the checks of WebSocket messages are off, and so is the client's local check (§5.3 of `spec/rules.md`). `create<Service>Handler` runs `console.warn` once, when the handler is created, if any endpoint takes a body, a query object or a WebSocket message that reaches a declaration with rules. Generation reports the warning `W0904` for such a target (`veld generate` prints it as `warning[W0904]` and carries on; see `Generator::warnings` in `veld-codegen`).

## 5c. Endpoint rules (`spec/rules.md` §9, §12.4)

Both generators support `rules_endpoint`. A contract whose services have no endpoint block gets the bytes of invariants only, apart from the rules digest (below), which every service that reaches an invariant has. The `endpoint_rules` regions of `runtime/veld.ts` (`veld_codegen::gate_regions`, siblings of the `rules` regions: regions do not nest) are kept only when a requested service has an endpoint with statements; that also switches the `rules` regions and `runtime/rules.ts` on. The client and server runtimes stay byte-identical.

### Printing
`veld_emit_typescript::expr::EndpointPrinter` prints the expressions of a block with these roots, all in the developer-facing representation, converted at the leaf like a check function: parameters `p.<name>`, facts `f.<name>`, the success value `result`, the saved `old(...)` values `o[<slot>]`, and `now`, a `bigint` of milliseconds. A parameter or fact that may be absent is asserted (`f.coupon!`) where the compiler proved it present, and `has(coupon)` is `f.coupon !== undefined`. `old(e)` is one slot per distinct operand, evaluated before the handler runs; `snapshot` deep-copies plain objects and arrays, so a handler that changes a loaded object in place cannot change it. The principal stays unavailable (policies are a later phase).

### Server
- `server/<service>.ts` gains, per endpoint with facts, `<Endpoint>Facts` (`room: Room; coupon?: Coupon`), and the service interface takes `<Endpoint>Request & <Endpoint>Facts`: the handler gets the loaded facts with the parameters, under their names.
- One loader interface per service with facts, `<Service>FactLoaders`: one method per entry of `Service.facts`, `room(key: string, ctx): Promise<Room | null | undefined>` (a fact without a key takes only `ctx`). The hooks object requires `facts: <Service>FactLoaders` and takes `clock?: (ctx) => Date` (default: the system clock).
- `export function <service>Endpoints(impl, loaders)` builds the endpoint descriptions with their `rules` member (facts with a key function and a loader call, `require` steps with `holds` and an optional `otherwise`, the `old` operands, `ensure` steps with `holds`) and `digest`; `create<Service>Handler` is `createHandler(<service>Endpoints(impl, hooks.facts), …, hooks)`.
- **Step 6** (`prepare`): one clock reading; the facts in order (a required fact not found: `404 NotFound` with `resource` = the fact's name; an optional fact whose key is `undefined` is absent and its loader is not called); every `require` in order, the first failure wins: the declared `else` error with its payload (built only now), or `422 ValidationError` with one `rule` issue; either way one `violations` entry with `path: 'request'` and the parameter names the rule reads. An evaluation error is a failed rule with `error`; if the `else` payload itself cannot be evaluated the answer is `500 Internal`. The hook gets position `input`, outcome `rejected`. Then the `old` values are saved and the facts are merged into the parameters.
- **Step 9** (`checkEnsures`): every `ensure`, on a success result, after step 8, in the output mode (`strict` `500 Internal` with no detail, `audit` hook only, `off` skipped). The result's shape is validated first and defaults are applied. Position `output`.
- **`validate = false` / `validateRequests: false`**: step 6 is not evaluated (§5.3 of `spec/rules.md`): the facts are still loaded, because the handler's type holds them, but no `require`, `old` or `ensure` runs; a `console.warn` says so once.
- **Generation errors**: endpoint rules on a `ws` endpoint, a fact key or `else` payload that cannot be turned back into a developer-facing value (a `duration`) are `E0801`.

### Rules digest (§9.7)
For every service whose IR has a `rules_digest` (it reaches an invariant), with or without endpoint rules: the server sends `Veld-Rules: <digest>` on every response of a matched endpoint of a service that has one, errors included (a request no route matches gets none). The client (`ClientDefaults.service`, `.digest`) remembers the digest of the last response. It rejects locally only while that digest equals its own; before the first response, or when the header is missing, it sends anyway. A response with another digest stops the local checks and calls `onContractMismatch({ service, clientDigest, serverDigest })` once per digest it had not seen. A browser can read the header only if the server's CORS configuration sends `Access-Control-Expose-Headers: Veld-Rules`; otherwise the client behaves as before its first response and never rejects locally.

### Test handler (`testing = true`)
`server/<service>-test-handler.ts` (not exported from `index.ts`; the production files and the barrel are byte-identical with the option on or off) exports `create<Service>TestHandler(impl, hooks?)`. The file says at its top that it must never be mounted in production, and creating the handler reports it once with `console.warn`. It builds `<service>Endpoints` with loaders that read `Veld-Test-Facts`, drops authentication and middleware, and passes a clock that reads `Veld-Test-Now` (plain RFC 3339 text; the system clock when absent) and sets `ctx.principal` from `Veld-Test-Principal`. The facts, principal and result headers are base64url JSON, padded or not. A fact missing from the object is absent. `Veld-Test-Result` replaces the application's handler (decoded with the success schema); `Veld-Test-Dry-Run: 1` makes the handler step answer `204` with `Veld-Test-Passed: 1` through `EarlyResponse`, a response a `call` may return. `GET /__veld/test` answers `200` `{"veldTestHandler":1,"digests":{"<Service>":"<digest>"|null}}`. Nothing in `runtime/veld.ts` or the production module reads a test header.

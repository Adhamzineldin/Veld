# Target: `java` (server and client)

Status: normative for the built-in Java generator. It follows `spec/targets/typescript.md` semantically: the same contract gives the same wire behaviour, the same errors with the same signatures, and the same canonical bytes. One implementation of models and runtime serves both roles.

## 0. Hard rules
- **Java 17 or newer.** Generated code compiles with `javac --release 17 -Xlint:all -Werror` and with `--release 21`, with zero warnings in both. It uses records, sealed interfaces and `java.net.http`, and nothing newer than 17 unless the profile (`java = "21"`) says so; today the output is identical for both.
- **Zero dependencies.** Generated code imports only the JDK (`java.*`, and `com.sun.net.httpserver` for the JDK adapter). The single exception is the optional Spring adapter, which imports Spring Boot 3 (Jakarta) and is emitted only for `framework = "spring"`; for WebSocket it also imports Spring WebSocket (`spring-boot-starter-websocket`), but only in the WebSocket classes, which are emitted only when the contract has `ws` endpoints (section 6). There is no JSON library, no annotation library and no logging library: the runtime contains its own JSON parser and writer.
- **Identity by signature, never by class.** Two generated copies of a type in different Java packages are different classes. Every model, enum, union and error exposes `VELD_SIG`, equal to the IR signature verbatim (`spec/ir.md` §5.1).
- **Unsupported is loud.** Every feature is declared, but the `jdk` framework has no WebSocket server: a server target with `framework = "jdk"` (the default) whose contract has `ws` endpoints fails with `E0801` and a message that names `spring`. Nothing wrong is emitted. SSE and WebSocket are specified in section 6.
- Every file starts with `// Code generated by veld. DO NOT EDIT.`. Formatting is fixed: two spaces, imports sorted, one top-level type per file. Output is deterministic.

## 1. Options and layout

Options (`[server.options]` or `[client.options]`, validated, unknown keys are `E0802`):

| Option | Default | Meaning |
|---|---|---|
| `package` | `dev.veld.generated.<package of the first service>` | The base Java package. Must be a valid package name, else `E0802`. |
| `java` | `"17"` | The Java release the output targets: `"17"` or `"21"` (the oldest supported is the default). Anything else is `E0802`, and the message lists the valid values. The generated code is the same for every release today; `Profile::java_at_least(21)` is how newer syntax would be gated. |
| `validate` | `true` | `false` skips run-time **request** validation by default (the types are unchanged): the generated client defaults `ClientOptions` to no validation (`validate(true)` turns it back on) and the server hooks start with `validateRequests(false)`. Responses are validated only with `validateResponses(true)`. |
| `testing` | `false` | `true` also writes `server/<Service>TestHandler.java` and `runtime/TestSupport.java` for each service that has endpoint rules, an `@idempotent` endpoint, a guard or an endpoint that owes an `ETag` (sections 9.5 and 13.2). It must never be mounted in production. Not a boolean is `E0802`. |
| `runtime-prefix` | `veld` | The prefix of the Spring properties of the runtime config (`veld.services.iam.url`), for `framework = "spring"` (section 14). Lower-case words of letters and digits joined by `.` or `-`; anything else is `E0802`. |
| `framework-version` | the adapter's first version | The version of the framework. Only `spring` has versions (`"3"`: Spring Boot 3, Jakarta). A version outside the adapter's list, or a version for an unversioned framework (`jdk`), is `E0803`. |

`framework` (server only): `jdk` (default) or `spring`. Any other value, or a framework on a client target, is `E0803`. A framework whose `min_language` is newer than the chosen `java` release is `E0803` too (Spring Boot 3 and the JDK adapter both need Java 17). The framework list, versions and minimums come from the adapter registry (`crates/emitters/java/src/frameworks/`: `jdk.rs`, `spring.rs`), the single source of truth. Each framework emits only its own files: `jdk` (the default) emits `JdkHttpServerAdapter` and no Spring file, `spring` emits the Spring adapter and no JDK adapter.

Files go to `<out>/<base as path>/...`. Below the base package:

```
<base>.runtime                         the runtime (identical bytes in both roles)
<base>.prelude                         prelude errors used by the target: NotFound, Internal, ValidationError, ...
<base>.<package>.<module>              models, enums, unions, consts and errors of one contract module
<base>.<package>.client                <Service>Client and its <Operation>Request records   (client role)
<base>.<package>.server                <Service>Service, <Service>Hooks, <Service>Handler,
                                       <Operation>Request records                          (server role)
<base>.adapters                        JdkHttpServerAdapter | SpringAdapter (by framework)  (server role)
                                       SpringWebSocketAdapter (spring, only with ws endpoints)
<base>.adapters.<package>                 <Service>Controller (spring only)                   (server role)
                                       <Service>WebSocketConfig (spring, only if the service has ws endpoints)
<base>.clients.<service>.*             a self-contained client tree for each consumed service (server role)
```
The runtime package is `<base>.runtime`. Packages named `adapters`, `clients`, `prelude` and `runtime` are reserved below the base; identifiers that are Java keywords or clash with `Object` methods are escaped.

## 2. Type mapping

| Veld | Java | Wire |
|---|---|---|
| `string` | `String` | string |
| `int` / `long` / `float` / `bool` | `int` / `long` / `double` / `boolean`; boxed when optional | number; **`long` is a decimal string** |
| `decimal` | `java.math.BigDecimal` | string (text is significant: `1.50` is not `1.5`) |
| `date` / `time` | `LocalDate` / `LocalTime` | string |
| `datetime` | `Instant` | RFC 3339 string; any offset is accepted, canonical form is UTC |
| `uuid` | `UUID` | string; canonical form is lower case |
| `bytes` | `byte[]` | base64 string |
| `json` | `<base>.runtime.Json` (sealed: `Null`, `Bool`, `Num`, `Str`, `Arr`, `Obj`) | any JSON |
| `T[]`, `Map<string, T>` | `List<T>`, `Map<String, T>` | array, object |
| `Page<T>` | `<base>.runtime.Page<T>` record (`items`, `total`, `page`, `size`) | `{items,total,page,size}` |
| `model` | a `record`; component names are camelCase, `@wire` names are used on the wire | object |
| `enum` | a Java `enum`, constants in UPPER_SNAKE; `wire()` is the contract value | string |
| `union` | a `sealed interface` whose arms are the records of its member models; static `fromWire`/`toWire` use the discriminator | object with the discriminator field |

Optional fields and absent optional parameters are `null` (boxed types for scalars). Schema defaults are applied when decoding and when computing canonical bytes. `readonly` fields are dropped from request bodies (a request that lacks a required one still decodes: `Wire.fillReadonly` gives the record a placeholder, which no code reads). Each declaration has a static `SCHEMA` (validation, defaults, canonical bytes), `codec()`, `fromWire(Json)` and `toWire()`, and `veldCanonical()`.

## 3. Errors

```java
public final class OutOfStock extends VeldError {
  public static final String VELD_SIG = "veld:orders/OutOfStock@…";
  public static final int DEFAULT_STATUS = 409;
  public record Data(String sku) {}
  public OutOfStock(Data data) / OutOfStock(Data data, int status, String op)
  public Data data();
  public static boolean matches(Throwable e) / matches(Throwable e, String service)
}
```
- `VeldError extends RuntimeException` (unchecked) with `sig()`, `op()` (operation signature, `null` until raised from an endpoint), `status()`, `title()` (the declaration name), `data()`.
- `equals`, `hashCode`, `Veld.same(a, b)` and `Veld.matches(e, sig, service)` compare **signature, operation and canonical bytes** (schema defaults applied). They read `VELD_SIG`, `veldOp()` and `veldCanonical()` reflectively, so they work between different generated packages and between different copies of the runtime.
- `Veld.same` needs a signature on **both** sides: a generated value never equals a value without one (a `String`, a plain object), whatever its data, and two different declarations with identical fields (so identical canonical bytes) are never the same. `List`s and `Map`s compare element by element with `Veld.same`, so lists of generated values from different packages compare. Record `equals` is class based, so it never confuses two declarations either; across packages use `Veld.same`.
- `instanceof` and `catch (OutOfStock e)` are reliable only inside one generated package. Across packages use `matches` or `Veld.same`. The same rules as in TypeScript: `same` is false for a different op, different data, a different declaring package or service with the same error name, and a changed shape.
- **Server behaviour:** an error thrown by the implementation whose `sig` is declared for the endpoint gets `op` set and is answered as problem+json at its status. Anything else, including an undeclared `VeldError`, becomes `500 Internal` without a message; the original goes to the `onError` hook.
- **Client behaviour:** a problem+json `type` that is a declared error is thrown as that class with `op` and `status` set. Other non-2xx responses are `VeldHttpError` (`status()`, `body()`). Network failures and unreadable bodies are `VeldTransportError`. Both are unchecked.

## 4. Client

```java
OrdersClient client = new OrdersClient(ClientOptions.builder()
    .baseUrl("https://api.example.com").bearer(() -> token).build());
Order order = client.getOrder(new GetOrderRequest(id));
```
- Blocking, built on `java.net.http.HttpClient`. `ClientOptions` has `baseUrl`, `httpClient`, `headers` (map or supplier), `bearer`, `basic`, `apiKey`, `validate` (default true) and `timeout` (default 30 s).
- **Base URL:** the `baseUrl` option is required (`VeldTransportError` at construction without it). A client reads no environment variable and the contract's `base-url` is not compiled in; `<Target>Clients.create` fills `baseUrl` from the runtime config (section 14). The client has no constructor without options.
- One `<Operation>Request` record per operation holds the path params, `body`, `query` object, single `@query` params and headers by parameter name. Operations without parameters also get a no-argument overload.
- Path parameters are percent-encoded; query objects use repeated keys for lists; absent optionals are omitted.
- With `validate` the request is validated first and a `ValidationError` with `op` set is thrown locally.
- No-body responses return `void`.

## 5. Server

```java
public interface OrdersService { Order getOrder(GetOrderRequest request, RequestContext ctx) throws Exception; … }
public final class OrdersHooks { OrdersHooks(HandlerHooks.BearerAuth bearer, HandlerHooks.Middleware rateLimit);
                                 OrdersHooks onError(ErrorHook); OrdersHooks validateResponses(boolean); }
VeldHandler handler = OrdersHandler.create(impl, hooks);
HttpServer server = JdkHttpServerAdapter.listen(handler, new InetSocketAddress(8080));
```
- The constructor of `<Service>Hooks` takes exactly the hooks the endpoints need (auth kinds, then middleware by first use), so a missing hook is a compile error. A service that needs none also gets `OrdersHandler.create(impl)`.
- `VeldHandler` is `Optional<VeldResponse> handle(VeldRequest)`; empty means no route matched. `invoke(String endpoint, VeldRequest)` runs one named endpoint through the same pipeline without choosing it from the method and path (for frameworks that route themselves); empty when the endpoint is unknown or the path does not fit it. Routing is done by the runtime's router from the IR paths: exact on literal segments, a trailing slash is ignored, HEAD is not implicit.
- Pipeline: match, auth (`401 Unauthorized`), middleware in declared order, bind and validate path/query/headers/body (`422 ValidationError` with `issues`), call the implementation, optionally validate the response, serialise with the declared success status.
- `RequestContext` has `method()`, `path()`, `headers()`, `header(name)`, `principal()` and `raw()` (the framework's request object).
- **Adapters.** `JdkHttpServerAdapter` (`toHttpHandler`, `listen`) serves on `com.sun.net.httpserver`; unmatched requests get an empty 404. The Spring adapter (`framework = "spring"`, Spring Boot 3, Jakarta, Java 17+) is native: one `@RestController` per service, `<base>.adapters.<package>.<Service>Controller`, with a `@GetMapping`/`@PostMapping`/`@PutMapping`/`@PatchMapping`/`@DeleteMapping` method per endpoint at its real path (`{id}` path variables), so actuator and springdoc see the real routes. Its constructor takes the `<Service>Service` bean and the `<Service>Hooks` bean (for a service that needs no hooks, an optional `ObjectProvider<<Service>Hooks>`). Each method calls `SpringAdapter.respond(handler, "<endpoint>", request)`, which builds a `VeldRequest` from the servlet request, runs the endpoint through `VeldHandler.invoke(endpoint, request)` (the same pipeline as every other adapter, so auth, middleware, validation, declared-error mapping, `Internal` without leaks and problem+json are not reimplemented) and writes the `VeldResponse`. Register the controllers by component-scanning `<base>.adapters`. The controllers and `SpringAdapter` are the only generated files that import Spring.
- A server target also contains, for each service in `consumes`, a complete client tree under `<base>.clients.<service>`. `consumes` cycles are legal.

## 6. Streaming: Server-Sent Events and WebSocket

The wire behaviour is the TypeScript target's, byte for byte (`spec/targets/typescript.md`, `tests/wire/streaming/sse.json`); the Java API is below. Language semantics: `get` + `-> stream T` is SSE; `ws` + `-> stream T` is server-to-client messages; `ws` + `body: stream T` is client-to-server messages (the IR's `Success.stream` and `Param.stream`).

### 6.1 Wire

**SSE.** The response is `200 text/event-stream` with `cache-control: no-cache`. A frame is an optional `id: X\n`, an optional `event: Y\n`, an optional `retry: N\n`, then `data: <canonical JSON of T>\n\n` (RFC 8785, the same bytes as everywhere else; a line break in `id` or `event` is an error). The server pulls the **first** item before it sends the status: an error before the first event is a normal problem+json response (declared status, `sig`, `op`). After the stream has started an error is a final `event: error` frame carrying the problem JSON, and the stream ends (an undeclared error becomes `Internal` without its message and goes to `onError`). With `validateResponses` every item is validated, with the same before/after rules. An empty stream is a `200` with an empty body. The client sends `Accept: text/event-stream` and, to resume, `Last-Event-ID`.

**WebSocket.** Server-to-client frames are text envelopes: `{"data":<canonical JSON>}`, or the final `{"error":<problem JSON>}` followed by a close. Close codes: `1008` for declared and client-side errors (validation, auth, a declared error), `1011` for a `500`, `1000` for a normal end, `4404` when the path is not a `ws` endpoint. Client-to-server frames are the bare canonical JSON of the message. The server validates every incoming message against the stream body type; a failure is `{"error": ValidationError}` whose issue paths start with `message` (code `json` for text that is not JSON, `unexpected` when the endpoint takes no messages) and a close with `1008`. The client validates outgoing messages when `validate` is on (a local `ValidationError` with `op`). Auth uses the same hooks as HTTP: the `Authorization` header, else the query parameter `access_token=<token>` (bearer) or `api_key=<key>` (API key, when its header is absent); basic auth over a WebSocket is a `VeldTransportError` on the client. `@header` parameters are also read from the query string by the server and sent as query parameters by the client. Frames that arrive before authentication and middleware have finished are held back and then processed. Path, query and header parameters bind from the upgrade request; the stream body parameter is **not** a component of the request record.

### 6.2 Server API

```java
Stream<SseEvent<Tick>> ticks(TicksRequest request, RequestContext ctx) throws Exception;     // get ... -> stream Tick
void chat(ChatRequest request, RequestContext ctx, WsSession<Say, Heard> ws) throws Exception; // ws ... body: stream Say -> stream Heard
```
- **`java.util.stream.Stream<SseEvent<T>>`** is the SSE return type. It is blocking, closeable and needs no dependency, and it fits both a thread-per-request server (the JDK adapter) and Spring MVC. The server **closes** it when the client disconnects, when a frame cannot be written and when it ends, so `Stream.onClose` (or a `try`/`finally` around the source) is where an implementation cleans up. The first element is pulled eagerly: the implementation may throw a declared `VeldError` before returning the stream or from its iterator before the first element; either is a normal error response. `SseEvent<T>` is a record `(data, event, id, retry)` with `SseEvent.of(T)`, `of(T, event, id)` and `withRetry(int)`.
- **`WsSession<In, Out>`** has `Stream<In> incoming()` (blocking, validated, ends when the socket closes), `void send(Out)`, `void close()` and `boolean isClosed()`. A `ws` method runs on its own daemon thread; returning closes with `1000`, throwing a declared error sends it as the final `error` frame. `Void` marks a side that has no messages (`WsSession<Void, Tick>` for a server that only talks).
- `VeldHandler.ws(VeldRequest, WsSocket)` is the entry point for adapters, the counterpart of the TypeScript `handler.ws`: it returns `false` when no `ws` endpoint matches (the adapter closes with `4404`) and otherwise runs the same pipeline as HTTP (auth, middleware, binding, typed-error mapping).
- **JDK adapter**: SSE only. Each frame is written and flushed as it arrives; a failed write closes the stream. **A contract with `ws` endpoints is `E0801` for `framework = "jdk"`**: the JDK has no WebSocket server, and the generator never emits wrong code. The generator declares every feature in its capabilities; the framework check happens in `generate`, and the conformance kit is run per framework (`veld_emit_conformance::Setup`: a framework and the features it must reject with `E0801`).
- **Spring adapter**: an SSE endpoint is a controller method returning `ResponseEntity<StreamingResponseBody>` through `SpringAdapter.stream(...)`, the same pipeline and frames as the JDK adapter; the body is written on a Spring task thread for as long as the stream lives, so size `spring.task.execution.pool.*` for the number of concurrent streams. WebSocket uses Spring WebSocket: `SpringWebSocketAdapter` and one `<Service>WebSocketConfig` (`@Configuration @EnableWebSocket`, a `WebSocketConfigurer` registering the service's `ws` paths, `{param}` segments as `*`) per service with `ws` endpoints. `spring-boot-starter-websocket` is **the declared dependency exception** and is needed only when these classes are emitted. A request for a path that is not a `ws` endpoint fails the handshake with a `404` (Spring has no socket to close; `4404` is what the Node adapter does).

### 6.3 Client API

```java
try (Stream<Tick> ticks = client.ticks(new TicksRequest(5, null))) { ticks.forEach(...); }
Stream<Tick> resumed = client.roomEvents(request, SseOptions.resumeAfter(lastId).withOnEventId(ids::add));
try (WsChannel<Heard, Say> chat = client.chat(new ChatRequest("room", "ada"))) { chat.send(new Say("hi", null)); Heard h = chat.receive(); }
```
- An SSE method returns an `AutoCloseable` `Stream<T>` built on `java.net.http.HttpClient` and the runtime `SseParser` (WHATWG parsing). The HTTP call is **eager**: a non-2xx response throws its typed error (or `VeldHttpError`) from the method itself. Closing the stream cancels the request. An `event: error` frame throws the typed unchecked `VeldError` when it is consumed (`VeldHttpError` when undeclared); a broken connection is a `VeldTransportError`. **There is no automatic reconnect** unless a `Reconnect` policy is set (`ClientOptions.Builder.reconnect(...)` for the client, `SseOptions.withReconnect(...)` per call): callers otherwise resume by passing `SseOptions.resumeAfter(id)` (sent as `Last-Event-ID`); `withOnEventId` is called with every event id.
- **Reconnect** (`new Reconnect(initialMs, maxMs, retries)`, `Reconnect.defaults()` is 1000 ms doubling to 30000 ms, 10 attempts). The same rules as the TypeScript client (`spec/targets/typescript.md` §4b): only connection failures are retried (a refused connection, a stream that breaks, an abnormal WebSocket close); a typed error, an error frame, a normal end and `close()` are never retried. SSE reopens the request with `Last-Event-ID` set to the last event id delivered, so the stream is continuous (`ClientCore.stream` also retries the first connection). `WsChannel` opens a new socket on a background daemon thread, queues `send` while the connection is down and flushes it after the reconnect; the failure counter starts again after a frame arrives or a connection that lived at least `maxMs`. When the attempts run out the last `VeldTransportError` is thrown from `receive()` (or from the call that opens the connection). `Reconnect.java` is emitted only for a target that uses streaming.
- A `ws` method returns a `WsChannel<In, Out>` on `java.net.http.WebSocket` that is already connected: `send(Out)` (validated unless `validate(false)`), `In receive()` (blocking; `null` when the server ended the conversation normally; throws the typed error of an error frame), `Stream<In> messages()` and `close()`. The base URL scheme `http`/`https` becomes `ws`/`wss`. Auth goes in the query string as above.
- The default `HttpClient` is created for HTTP/1.1: over cleartext the JDK would otherwise offer `Upgrade: h2c` on every request, which a server that also hosts WebSocket upgrades (the Node `ws` package) answers with a `400`. Pass your own `httpClient` for HTTP/2.

## 6.4 The generated README

Every Java target writes `README.md` at the root of its output: the base package, how to use the generated classes (client or server), the `Veld.same` note, and how to regenerate (`veld generate`; the manifest lists the files Veld owns). It is deterministic and has no absolute path, host name or date.

## 8. Invariants (`rules_invariants`)

The structure of `spec/rules.md` §8, in Java. Endpoint rules are section 9, state machines section 10, policies section 11. A contract without rules gets exactly the files it got before: the rule classes below are emitted only when a model or error that the target emits has a rule, and every hook in an existing runtime class sits between `// #if rules` and `// #endif` marker lines that `veld_codegen::gate_regions` removes (with their content) when rules are off.

**Values in expressions.** `boolean`, `int`, `long`, `double`, `BigDecimal`, `String`, `UUID` and enum constants as they are. `datetime` is `long` epoch milliseconds (`Instant.toEpochMilli()`, so digits below the millisecond are dropped), `date` is `long` epoch days, `time` is `long` milliseconds of the day, `duration` is `long` milliseconds. A path that may read a boxed type (an optional or defaulted field, a list element) is cast to the primitive, so `==` never compares references. Decimals compare with `compareTo`, strings and uuids with `equals`, enums with `==`.

**Runtime helpers** (`Rules`, emitted only with rules; `RuleError` is the one unchecked exception for the three evaluation errors, with `kind()`):

| Group | Names |
|---|---|
| int | `addInt` `subInt` `mulInt` `divInt` `remInt` `negInt` (`MIN / -1` overflows, `MIN % -1` is `0`, a zero divisor is `division_by_zero`) |
| long, instants, dates, times, durations | `addLong` `subLong` `mulLong` `divLong` `remLong` `negLong`, `dateDiff` |
| float | `addFloat` `subFloat` `mulFloat` `divFloat` `remFloat` `finite` (Java only) (zero divisor checked first, result must be finite) |
| conversions | `toDatetime` `toDate` `toTime` (`instantMs` is an alias of `toDatetime`, kept in the runtime for code generated by the first release; the printer no longer writes it) |
| durations | `days` `hours` `minutes` `seconds` `ms` (checked multiplication) |
| strings | `lenString` (code points; `len` is an alias kept in the runtime, as above), `matches` (same `Pattern.find` semantics as `@pattern`) |
| membership | `in` (by `equals`), `decIn` (numeric), `inDouble`, `inTemporal` (`in`, `inDouble` and `inTemporal` are Java only) (list fields of `date`, `datetime`, `time` against the unit-converted value) |
| comprehensions | `all` `any` `countWhere` `sumInt` `sumLong` `sumFloat` `sumDecimal` |
| running a rule | `run(out, id, name, path, fields, message, test)` evaluates one rule, catches `RuleError` and records the violation (message `rule <name> could not be evaluated`, `error` = the kind) |

**Generated per declaration with rules** (model: in the record; error: in the error class, on `Data`):

```java
public static final String RULE_END_AFTER_START = "veld:bookings/Booking.endAfterStart@…";
static void checkOwn(Booking v, boolean request, String path, List<Violation> out)   // own rules in list order
private static void checkWire(Json json, boolean request, String path, List<Violation> out)
public static List<Violation> check(Booking value)          // full check, nested values included
public static List<Violation> checkRequest(Booking value)   // request position: rules that read a @readonly field are skipped
public static final Schema SCHEMA = Schema.object(…).checked(Booking::checkWire);
```

Rules that read a `@readonly` field are wrapped in `if (!request)`. Rule expressions are printed by `rule_expr.rs`, the Java `ExprPrinter`; a rule that reads `now`, `old`, a parameter, a fact, the principal or the result is `E0801`.

**Nesting is the runtime's.** `RuleWalk` walks a validated, prepared `Json` by its `Schema`: for an object it calls the schema's check (own rules first), then its fields in declaration order; lists by index (`$.rows[1]`), maps by key (`$.named.k`), pages through `items`, unions through their arm. In request position the check decodes the object with `fromWire` after `RuleWalk.forDecoding` filled the required fields a request cannot carry (read-only ones) with placeholders; a rule that reads such a field is skipped, so a placeholder is never read.

**`Violation`** is the runtime record `(rule, path, fields, message, error)`; `VeldError` gains `violations()` (empty without the member) and `raisedLocally()`.

**Client.** Before sending, with `validate` on and `ClientOptions.Builder.localRules(true)` (the default), the body and the `query` object are prepared in request mode and checked. A violation is thrown as the `ValidationError` built by the client's own factory, with issues of code `rule` / `rule_error`, the violations and `raisedLocally() == true`; nothing is sent. `localRules(false)` skips it. A problem document with a `violations` member decodes into the typed error with its violations.

**Server.** Step 5 runs after binding and validation (and only when request validation is on, since the rules need well formed values): a violation answers `422 ValidationError` with `data.issues` and the top-level `violations`. Step 8 follows the output mode `STRICT` (default) | `AUDIT` | `OFF`, set with `rules.output` of the runtime config (section 14; a server without a runtime config `rules.output` keeps `<Service>Hooks.rulesOutput(RuleWalk.OutputMode)`); unless `OFF`, the result's shape is validated first (an invalid result is a 500 as with `validateResponses`), `STRICT` answers `500 Internal` without detail. The same applies to a declared error the server encodes. A result whose schema reaches no rule is not touched. `<Service>Hooks.onRuleViolation(RuleWalk.Hook)` receives one `RuleWalk.Event(rule, operation, position, outcome, violation, elapsedMicros)` per violation (`INPUT`/`OUTPUT`, `REJECTED`/`AUDITED`). A mode other than `STRICT` is logged once, at `WARNING`, through `System.Logger` `veld.rules` when the router is created. Both adapters (JDK and Spring) go through the same router, so they behave the same.

**Streams.** Every item the server sends on an SSE stream or a WebSocket is checked under the output mode before it is written. `STRICT`: the item is not sent, the hook gets the violation (`OUTPUT`, `REJECTED`) and the stream ends as it ends on any server failure (an error before the first event is a plain `500 Internal`; later it is the final `event: error` frame of an SSE stream, or the `error` frame and close code 1011 of a WebSocket; the implementation's `send` throws and `onError` is not called). `AUDIT`: the item is sent and the hook gets it (`AUDITED`). `OFF`: skipped. A message the client sends on a WebSocket is an input: the server rejects a violating one with the final `ValidationError` frame (`data.issues`, the top-level `violations`, path root `message`) and close code 1008, and the hook gets it (`INPUT`, `REJECTED`); this check is skipped when request validation is off. The generated client's `WsChannel.send` checks the message locally in request mode after the shape check (violations with path root `message`, `raisedLocally()` true, nothing written); `ClientOptions.Builder.localRules(false)` turns it off.

**Request validation turned off** (`validate = false`). Step 5 and the WebSocket message check are off, and so is the client's local check. `Router.create` logs once, at `WARNING` through `System.Logger` `veld.rules`, when the handler is created and an endpoint takes a body, a query object or a WebSocket message that reaches a declaration with rules. The generator reports `W0904` through `Generator::warnings` when the target emits a declaration or an endpoint with rules.

**The 422 golden** (`tests/wire/rules`): `tests/rules_extras.rs` runs `request.json` against the JDK server and against the Spring adapter and compares the RFC 8785 canonical bytes of the answer with `problem.json`; both are equal. The Spring adapter maps every path (except `/`) with and without its trailing slash, because the shared router ignores a trailing slash (section 5) and Spring MVC 6 does not; `tests/spring_trailing_slash.rs` sends both forms to the JDK server and to the Spring adapter and compares the answers.

Tests: `crates/emitters/java/src/rule_expr/tests.rs` (exact printer output), `tests/rules.rs` (snapshots, `javac` on every role and release, no rule code without rules), `tests/rules_toolchain.rs` (the shared vectors of `tests/rules/core` through `tests/toolchain/java/rules/RuleVectors.java`, partial cases skipped; the HTTP round trip `RuleRoundtrip.java`), `tests/rules_extras.rs` (the 422 golden, streams, validation off, `W0904`).

## 9. Endpoint rules (`rules_endpoint`)

`spec/rules.md` §9 and §12.4, in Java; the structure of `spec/targets/typescript.md` §5c. A contract without endpoint rules gets the bytes it got before, with one exception that applies to every contract with invariants (section 9.4). The endpoint code in the runtime sits between `// #if endpoint` and `// #endif` lines, a sibling of the `rules` regions (`veld_codegen::gate_regions`; regions do not nest); the regions are kept, and `runtime/EndpointRules.java` is emitted, only for a **server** whose requested services have an endpoint with statements, and that also switches the `rules` regions on. Endpoint rules on a streaming endpoint (`ws`, or a response that streams) are `E0801`; so is a fact key or an `else` payload that is a duration, which has no Java type.

### 9.1 What a developer sees

- `<Endpoint>Facts` (`CreateBookingFacts`), one record per endpoint that has facts: one component per fact, in declaration order, typed like the fact; an absent optional fact is `null`.
- The service interface gets the facts between the request and the context: `Booking createBooking(CreateBookingRequest request, CreateBookingFacts facts, RequestContext ctx)`. An endpoint without facts keeps `(request, ctx)`.
- `<Service>FactLoaders`, one interface per service that has facts, one method per entry of `Service.facts`: `Optional<Room> room(UUID key, RequestContext ctx) throws Exception` (a fact without a key takes only the context). An empty `Optional` is "not found".
- `<Service>Handler.create(impl, loaders)` and `create(impl, loaders, hooks)`; the loaders are a required argument, so the type system asks for them. The Spring controller takes the loaders as a bean.
- `<Service>Hooks.clock(java.time.Clock)` (default `Clock.systemUTC()`): the clock `now` reads, once per request.
- `<Service>Handler.endpoints(...)` is package-private: the test handler builds the same endpoints.

### 9.2 Printing

`rule_expr.rs` prints the roots of an endpoint block with `JavaExpr::for_endpoint`: a parameter is `request.<name>()`, a fact is the local `fact_<name>`, `now` is the `long` local `now` (epoch milliseconds, the rule representation of a `datetime`), `result` is the local `result`, and `old(e)` is the saved slot `o<i>` (`(int) o0.get()`). The same operand is one slot. `has(fact)` is `fact_x != null`. The key of a fact and the values of an `else` payload are the developer-facing value: a plain path as it is (an `Instant`), anything computed converted back (`Instant.ofEpochMilli(...)`). The principal is `principal` (section 11), a local of the generated type of the principal's model.

### 9.3 Step 6 and step 9

The generated call of an endpoint with rules runs, in this order: the clock is read once; every fact in order (`run.required` answers `404 NotFound` with `resource` set to the fact's name; an optional fact whose key reads an absent optional value is not loaded and is `null`); every `require` in order (the first failure wins: the declared `else` error, built only now, or `422 ValidationError` with one issue of code `rule` or `rule_error`; either way one entry in `violations` with path `request` and the parameters the rule reads; the hook gets position `INPUT`, outcome `REJECTED`); every `old(...)`, saved as a value or the evaluation error that stopped it (reading it later fails that `ensure`); the handler; then the `ensure` checks are registered. A payload that cannot be evaluated, or an `else` error that breaks its own invariants, is `500 Internal` whatever the output mode. With request validation off (`validate = false`) no rule runs and no `old` is evaluated, but the facts are still loaded, because the handler's type holds them.

Step 9 is run by the router after step 8: each registered `ensure`, in source order, on the result's wire form, under the output mode: `STRICT` answers `500 Internal` without detail (the violation goes to the hook as `OUTPUT`, `REJECTED`), `AUDIT` sends and reports (`AUDITED`), `OFF` evaluates nothing. The result's shape is validated first, as for step 8. The checks reach the router through a thread local (`EndpointRules`), which the router clears when a request ends without reaching step 9. An `ensure` violation has path `request` and the parameters it reads.

### 9.4 The rules digest (`spec/rules.md` §9.7)

For every service that has a `rules_digest` in the IR, **including a contract that has invariants and no endpoint rules**: the generated handler is wrapped in `DigestHandler`, which sends `Veld-Rules: <digest>` on every response of a matched endpoint (errors included; a request no route matches gets none). The generated client tells its `ClientCore` the digest (`core.digest(service, digest)`); the core remembers the digest of the last response and runs the local check only while it equals its own. Before the first response, or when a response has no header, a request that fails the local check is sent and the server decides. A response with another digest calls `ClientOptions.Builder.onContractMismatch(Consumer<ClientOptions.ContractMismatch>)` once per digest it had not seen, with the service name, its own digest and the server's. A contract without rules does not change.

### 9.5 The test handler (`testing = true`)

`server/<Service>TestHandler.java` and `runtime/TestSupport.java`, for services with endpoint rules **and for services with an `@idempotent` endpoint, a version guard or an endpoint that owes an `ETag`, also when they have no other endpoint rule** (`spec/rules.md` 11.12: `veld test --live` must reach them). A service of the second kind has no `EndpointRules` and no rule class in the runtime: its dry run (below) ends through `Conditions.Early`, a small exception of the `Conditions` class that the router answers (`// #if early` regions of `Router`, `Conditions` and `TestSupport`, on for a server that uses `@version`/`@idempotent` and has no endpoint rule, whether or not `testing` is on), and `<Service>Handler.endpoints(impl, hooks)` exists for it too, without the clock parameter. The production files are byte for byte the same with the option on or off, and none of them reads a `Veld-Test-*` header. `<Service>TestHandler.create(impl[, hooks])` logs a warning once that it is a test handler and returns a `VeldHandler` that: builds `<Service>Handler.endpoints` with loaders that read `Veld-Test-Facts` (base64url JSON, padded or not; a fact missing from the object or `null` is absent) and a clock that reads `Veld-Test-Now` (plain RFC 3339; the system clock when absent); drops authentication and middleware and sets the principal from `Veld-Test-Principal` (`true` when absent; for a service with a principal, section 11, the wire JSON decoded as the principal's model, and `null` when absent); wraps the application in a service that, for a plain HTTP endpoint, answers a dry run (`Veld-Test-Dry-Run: 1`: `204` with `Veld-Test-Passed: 1` through `EndpointRules.Early`, the response a call may throw) or the result of `Veld-Test-Result` before it calls the application; and answers `GET /__veld/test` with `{"veldTestHandler":1,"digests":{"<Service>":"<digest>"|null}}`. The auth hooks of the `hooks` argument are never called and may be `null`. Mounting it with Spring is the application's job: one catch-all route that hands the request to the handler.

### 9.6 Tests

`tests/endpoint_rules.rs` and the drivers `EndpointServe.java` (the test handler on the JDK server), `EndpointHttp.java` (the production handler over HTTP: a missing fact, the order of the checks, `else` payloads and violations, an optional fact whose key is absent, `ensure` in `strict` and `audit`, `old`, the clock) and `EndpointDigest.java` (the header; the client's local check for the same, a different and a missing digest): every one of the 20 examples of `tests/rules/endpoints/bookings.veld` runs through `veld_testing::Live` in dry-run mode against the generated test handler on the JDK server and on the Spring adapter (a Spring Boot application with one catch-all controller, `spring-endpoints/App.java`); the printer in `src/rule_expr/endpoint_tests.rs`; snapshots `endpoint_rules__*`; `javac -Xlint:all -Werror` on the server (with and without `testing`) and the client for both releases.

## 10. State machines (`rules_transitions`)

`spec/rules.md` §10, in Java. A contract without a state machine and without a `transition` gets the bytes it got before: the enum helpers exist only for an enum with `flow` lines, `runtime/Transition.java` and the guard in `EndpointRules` are emitted only for a **server** with a `transition` (`// #if machine` regions; they come on top of the `endpoint` regions).

### 10.1 The helpers (client and server)

An enum with at least one `flow` gets, in its own class:

```java
/** The states that can follow this one, in declaration order of the edges (`flow`). */
public List<Status> nextStates()      // Status.PENDING.nextStates() is [PAID, CANCELLED]
/** Whether this state is final: no state follows it. */
public boolean isFinal()
```

`nextStates()` is a `switch` expression over every constant, so a state with no way out answers `List.of()`. `final` states are the only ones `isFinal()` is true for. An enum without flows is generated as before.

### 10.2 The guard and the transition

Step 6 runs, after the facts and (section 11) the policies and before the first `require`:

```java
Status transition_from = fact_booking.status();             // a defaulted field that is null reads its default
Transition<Status> transition = run.transition(id, "status", transition_from, List.of(Status.PENDING), Status.PAID,
    () -> InvalidTransition.fromWire(…, 409, null));
```

`run.transition` answers `409 InvalidTransition` when `transition_from` is not one of the sources: `data.field` is the wire path of the field inside the fact, `data.from` and `data.to` are wire values, and `violations` has one entry whose `rule` is the transition's id, `path` is `request`, `fields` is empty and `message` is `violates rule transition` (the text of the reference evaluator); the hook gets position `INPUT`, outcome `REJECTED`. The guard runs even when request validation is off, because it reads a fact, never a request value. An optional fact, or a path the printer cannot read, is `E0801`.

The handler receives the value next to the parameters and the facts, as an argument named `transition` before the context: `Booking payBooking(PayBookingRequest request, PayBookingFacts facts, Transition<Status> transition, RequestContext ctx)`. `Transition<S>` is the runtime record `(String field, S from, S to)`. The Javadoc of the interface method and of the record say that this is a guard and not an atomic guarantee, that the handler must write conditionally (compare-and-swap or a row lock, in its own transaction) and answer `InvalidTransition` itself when that write finds another value.

### 10.3 The target check

When the success type is the same declaration as the fact's type, step 9 registers, after the `ensure` statements, one more check on the result: the same field must hold the target state. It is registered through `run.ensure(id, "transition", List.of(), message, …)`, so it follows the output mode of every `ensure` (`STRICT`: `500 Internal` and the violation goes to the hook as `OUTPUT`; `AUDIT`: the hook only; `OFF`: skipped). The message is the reference evaluator's: ``the result must hold the state `paid` in `status`, found `pending` ``. An endpoint whose success type is another declaration, or none, has no target check.

### 10.4 Tests

`tests/state_machines.rs` with `tests/toolchain/java/rules/MachineServe.java` (the test handler on the JDK server), `spring-machine/App.java` (on Spring) and `MachineHttp.java` (the production handler over HTTP: a legal and an illegal move, the transition the handler receives, the order of the checks, several sources, a final state, an endpoint without a result, the target check in `strict` and `audit`): every one of the 14 examples of `tests/rules/endpoints/transitions.veld` runs through `veld_testing::Live` in dry-run mode on both adapters; snapshots `state_machines__*`; `javac -Xlint:all -Werror` on the server (with and without `testing`) and the client for both releases; the helpers appear in both roles and an enum without flows has none.

## 11. Policies and the principal (`rules_policies`)

`spec/rules.md` §11.1 to §11.5, in Java. A contract that uses no policy and does not read the principal gets the bytes it got before: `runtime/Policy.java`, the `// #if policies` regions of `EndpointRules` and `TestSupport`, the typed hooks and the `Policies` classes exist only when the services use `rules_policies` (an `allow`, or a statement that reads the principal). A principal that is declared and never read changes nothing.

### 11.1 The principal

For a service with a principal, `<Service>Hooks` declares one **typed** interface per auth hook it needs, nested in the hooks class, whose method returns the generated type of the principal's model:

```java
public interface BearerAuth { User authenticate(String token, RequestContext ctx) throws Exception; }   // also BasicAuth, ApiKeyAuth
public BookingsHooks(BearerAuth bearer)
```

The constructor adapts it to the untyped `HandlerHooks` hook (`builder.bearer(bearer::authenticate)`), so the runtime is unchanged. In an endpoint with auth the generated call starts with `User principal = (User) ctx.principal();` and the root `principal` of a rule reads that local (`principal.id()`). The principal is trusted and not validated. A service without a principal keeps the untyped hooks.

### 11.2 Policy functions (client and server)

For every policy that an `allow` of the generated services names, in the package of the policy (`<package>.<module>`), a class `Policies` (`Policies_` when a declaration of that package is called `Policies`) has:

```java
public static boolean manageBooking(User user, Booking booking)                          // reads the system clock
public static Policy.Verdict manageBookingVerdict(User user, Booking booking, long now)  // the server calls this one
```

`Policy.Verdict` is `(boolean permitted, String message)` with `denial()` (the message of the first `forbid` that was true, else `not permitted`). The verdict method evaluates every `forbid` in source order first (the first one that is true ends it with its message, or none), then the `permit` clauses. Every clause is wrapped in `Policy.permits(...)` / `Policy.forbids(...)`: an evaluation error (`RuleError`) is `false` for a `permit` and `true` for a `forbid`, so a clause that cannot be evaluated fails closed. A clause reads its parameters by name (a parameter called `now` is renamed), `now` is the `long` parameter of the verdict method. A policy that no `allow` names is not generated (the contract's feature set does not include it either).

### 11.3 `allow`

Step 6 runs, after the facts and before the transition guard, one `run.allow(policyId, reads, () -> Policies.xVerdict(args…, now), reason -> Forbidden.fromWire({message: reason}, 403, null))` per `allow`, in source order. The arguments are printed as values the developer sees (`app_value`). A denial, **or an argument that cannot be evaluated** (it fails closed, with `not permitted`), ends the request with `403 Forbidden`: `data.message` and the one violation's `message` are the text of the verdict, the violation's `rule` is the policy id, `path` is `request`, `fields` are the `reads` of that `allow`; the hook gets `INPUT`, `REJECTED`. Like the guard, `allow` runs even when request validation is off, because it decides who may call.

A `require` or an `ensure` may read the principal (`principal.roles`): the IR marks it with the policies feature and the printer reads the local above.

### 11.4 `can<Endpoint>` (client)

For every endpoint with an `allow` or a `transition`, `<Service>Client` has a **static** method that takes, in this order, the facts, the principal and the parameters that the endpoint's `allow` arguments and its `transition` read (only those; each by its name, with the generated type of the fact, the model or the parameter), and returns whether the server would let the call past the policies and the transition guard:

```java
public static boolean canPayBooking(Booking booking, User user)
// Policies.manageBookingVerdict(user, booking, now).permitted() && List.of(Status.PENDING).contains(booking.status())
```

It reads the system clock for `now`, never sends anything and never rejects: an evaluation error is `false`. The server decides.

### 11.5 The test handler

`TestSupport.endpoint(e, decode)` (a `policies` region, an overload) sets the principal from `Veld-Test-Principal` (unpadded base64url of the wire JSON) decoded as the principal's model, `null` when the header is absent; the generated test handler uses it for a service with a principal and leaves the one-argument method (the principal as plain JSON, or `true`) for every other service.

### 11.6 Choices where the spec leaves room

- The policy classes are emitted for the policies an `allow` names, not for every policy of the contract: a policy no endpoint uses does not use the feature (`spec/rules.md` §11.4) and so generates nothing.
- `allow` and the transition guard are not switched off by `validate = false` (the other statements are): authorization must not depend on a request-validation option. `W0904` is unchanged.
- The `now` of the boolean policy and `can<Endpoint>` methods is the system clock; the server passes the request's own clock reading.
- A policy parameter is never `null`; a `null` argument is an error of the application (`500`), not a denial.

### 11.7 Tests

`tests/policies.rs` with `tests/toolchain/java/rules/PolicyServe.java` (the test handler on the JDK server), `spring-policies/App.java` (on Spring) and `PolicyHttp.java` against the contract `tests/fixtures/guarded.veld` (the production handler over HTTP: `403` and its messages with a `forbid`, several `allow` lines, the order missing fact, denial, transition guard, `require`, fail-closed clauses and arguments, the principal the handler sees, and `can<Endpoint>` of the generated client against the server for every caller and both states): every one of the 10 examples of `tests/rules/endpoints/policies.veld` runs through `veld_testing::Live` in dry-run mode on both adapters; the printer for the `principal` root and for policy parameters in `src/rule_expr/endpoint_tests.rs` and `src/policy.rs`; snapshots `policies__*`; `javac -Xlint:all -Werror` on both contracts, server (with and without `testing`) and client, for both releases; `tests/conformance.rs` asserts that the generator declares and generates every rules feature.

## 12. Events (`spec/events.md`)

The `java` server declares `events` for every framework (`jdk`, `spring`); the client generates nothing for events and keeps its bytes. A contract without events gets the bytes it got before: the three runtime classes and the files below exist only for a service that publishes or subscribes.

### 12.1 Files

| File | Content |
|---|---|
| `<base>.runtime.Events` | the envelope, `publish`, `subscribe`, the hook records and the options (`Events.PublisherOptions`, `Events.ConsumerOptions`, `Events.EventMeta`, `Events.PublishedEvent`, `Events.EventRejected`, `Events.ContractMismatch`, `Events.HandlerFailure`) |
| `<base>.runtime.Transport` | the transport interface (`publish`, `subscribe`, `Message`, `Outcome`, `Subscription`) |
| `<base>.runtime.MemoryTransport` | the memory transport |
| `<base>.<package>.<module>.<Event>` | one record per event of the channels and per declaration only they reach, like a model (`VELD_SIG`, `SCHEMA`, `codec()`, `RULE_*`, `check`) |
| `<base>.<package>.server.<Service>Publisher` | per service that publishes |
| `<base>.<package>.server.<Service>EventHandlers`, `<Service>Subscriber` | per service that subscribes |

A service with events and no endpoints has no `<Service>Service`, `Hooks`, `Handler`, no Spring controller and no README line for them. The event files are identical for `jdk` and `spring`. A server with events carries the rule classes of section 8 even when no event has a rule (the events runtime reports violations).

### 12.2 API

- `BookingsPublisher.create(transport[, Events.PublisherOptions])`; `publisher.bookingEvents().bookingPaid(event)` returns `Events.PublishedEvent` (`id`, `source`, `type`, `subject`, `time`). The channel accessor and the method are the camelCase names. Options: `newId(Supplier<String>)`, `clock(Supplier<Instant>)`, `onRuleViolation(RuleWalk.Hook)`. The id defaults to `UUID.randomUUID()`, the clock to `Instant.now()`.
- A failure throws the prelude `ValidationError` when the contract has one, otherwise an `UntypedError` titled `ValidationError`, status 422, with `violations()` and `raisedLocally()`. `validate = false` does not switch any of this off.
- `<Service>EventHandlers` has one method per `on` line: `void sendReceipt(BookingPaid event, Events.EventMeta meta) throws Exception`. `NotificationsSubscriber.subscribe(transport, handlers[, Events.ConsumerOptions])` subscribes every `subscribes` line under its group and returns a `Transport.Subscription` whose `close()` closes all.
- Hooks (`ConsumerOptions`): `onEventRejected`, `onContractMismatch`, `onRuleViolation` (`RuleWalk.Hook`, with `RuleWalk.Event`: `operation` is the event signature, position `OUTPUT` in a publisher and `INPUT` in a consumer, outcome `REJECTED` or `AUDITED`), `onHandlerError`. The publisher takes `onRuleViolation` only. A failing hook is ignored.
- `Transport`: `publish(topic, key, byte[])` and `subscribe(topic, group, deliver) -> Subscription`, blocking and without checked exceptions. `deliver` answers `Transport.Outcome.DONE` or `AGAIN`.
- `MemoryTransport(maxAttempts = 3)`: one daemon thread per group delivers in publish order, one message at a time; `idle()` blocks until everything is delivered or dead-lettered (not to be called from a handler); `deadLetters()`.

### 12.3 Choices where `spec/events.md` was silent

- No `<Service>PublisherOptions` or `<Service>SubscriberOptions` types: Java has no type alias, the runtime option classes are used.
- The canonical datetime is written by `Events` itself (UTC, `.fff` only when the milliseconds are not zero), not by `Wire.normalizeDatetime`, which trims zeros.
- Hooks report the enforced violations first, then the audited ones (`spec/events.md` section 6.4). The Node runtime reports audited first; with one violation per side the goldens cannot tell.
- A typed value that the generated codec cannot decode after step 3 is rejected as `shape`.
- A handler that throws any `Exception` is not acknowledged; the memory transport also treats an `Error` thrown by a subscriber as `AGAIN`.

### 12.4 Tests

`tests/events.rs` with the drivers `tests/toolchain/java/events/*.java`, compiled with `javac -Xlint:all -Werror` for both releases: every case of `tests/wire/events/envelopes.json` and `consume.json` (publisher bytes equal the golden, the consumer takes them back; this is also the cross-target check with Node), the 11 event examples of `tests/events/bookings.veld` against the reference evaluator, two services in one process, audited event rules, events without rules, the prelude error, snapshots, and the capability check.

`@version` and `@idempotent` (`spec/rules.md` sections 11.7 to 11.12). The generator declares `rules_version` and `idempotency` for both roles. A contract that does not use either generates the bytes it generated before: every change to an existing runtime class sits in a `// #if conditional`, `preconditions` (and `testing_conditional`, `conditional_rules`) region that disappears with its markers, and the new classes are only emitted when used.

| `<base>.runtime.StoredAnswer` | `status`, `body` (`byte[]`, the bytes that were sent), `contentType`, `etag`, `location` (the last three may be `null`) |
| `<base>.runtime.MemoryIdempotencyStore` | the generated store for tests: atomic, keeps every entry |
| `<base>.runtime.IfMatch` | the `If-Match` of a client call: `IfMatch.of(long)` and `IfMatch.any()`. Emitted next to a client that has a guarded endpoint |
| `<Service>Handler.conditions()` | package-private: the `Conditions` of the service by operation signature, handed to `Router.create(endpoints, conditions, std, hooks)`; the test handler reuses it |

`HandlerHooks` gains `idempotencyStore(store)`, `idempotencyCaller(hook)` (`HandlerHooks.IdempotencyCaller`: `String caller(Object principal, RequestContext ctx)`) and `withIdempotency(store, caller)`, a copy with another store and caller (the test handler uses it). `RequestContext` keeps the version of the `If-Match` tag between step 5 and step 6.

### 13.2 The server

- **Step 5.** `Router` reads `If-Match` on an endpoint with a guard and the key on an `@idempotent` endpoint, and adds their issues in front of the others, whether or not `validate` is on. A header that has more than one value (two header lines) is malformed for both. When the parameters themselves are well formed, the header issues go to `RuleWalk.inputFailure` as its leading issues, so that a missing key and a violated rule of the body are one `422` with the issues and the violations of the reference, in its order.
- **The lookup** is in `Router.run` between step 5 and the call of the endpoint. The scope is the operation signature, and, when the endpoint's IR `caller` flag is set, a line feed and the text the caller hook gives (also in the test handler, whose spec has no auth). `Replay` sends the stored status, body bytes, content type, `ETag` and `Location` and `veld-idempotent-replay: true`; `Running` and `Other` are `409` with the `Conflict` of the prelude and the two messages of section 11.10. `complete` follows when the answer's status is below 500, `release` otherwise; both are in a `finally` that releases when something other than an `Exception` escapes after `begin`. A failing `begin` is an ordinary server failure: `500 Internal`, the handler not called, the exception in `onError`; a failing `complete` or `release` is only in `onError`.
- **The fingerprint** is the first 16 hex characters of `MessageDigest("SHA-256")` over `Json.Obj.canonical()` (the RFC 8785 writer of the runtime) of the bound parameters in wire form: the value of each parameter after `Wire.prepare(..., REQUEST)` (defaults applied, read-only members left out, no placeholders), an optional that was not sent left out. Scalars are taken as the request wrote them, so a path `uuid` in upper case has another fingerprint than the same one in lower case.
- **The guard** is `EndpointRules.Run.version(ctx, id, actual, stale)` in the body of the endpoint, after the policies and before the transition, whether or not `validate` is on. A tag that is not the fact's version is `412` with `expected` and `actual` as decimal strings (`Json.of(Long.toString(..))`: `long` is a string on the wire, an `int` version too), one violation (`path` `request`, no fields, `violates rule version`) reported to `onRuleViolation` as position `INPUT`, outcome `REJECTED`. An absent optional fact passes. The `Long` it returns is the version that was checked, or `null` for no header, `*` and an absent fact.
- **The handler** gets `version` after the facts and before the `transition`: `Long version` for a `long` field, `Integer version` for an `int` one. The Javadoc of the method says the check is a guard, not a guarantee.
- **The `ETag`** is written by `Router.success` for an endpoint whose `Conditions.etag` is set (the success is the model itself), on every 2xx, as `"<version>"` of the returned value, and replayed with a stored answer. A server without a rule at all (an `@idempotent` or an `ETag`-only service) has none of `RuleWalk`, `Violation` or `EndpointRules`: nothing above needs them.
- **The hooks.** `<Service>Hooks` takes `IdempotencyStore store` and, when an `@idempotent` endpoint has `caller: true`, a `caller` hook as constructor parameters, after the auth and middleware hooks, so the type requires them and there is no `create(impl)` without hooks. With a principal the caller hook is typed with the principal's class (`Hooks.IdempotencyCaller`). `null` is still possible, so `Router.create` also checks and throws an `IllegalStateException` that begins with the name of the first endpoint that lacks the store or the caller hook.
- **The test handler.** It generates for every service that uses either annotation, with or without other endpoint rules (section 9.5). It replaces the store and the caller of its hooks (`withIdempotency`): the store is the same for every request but dispatches to a fresh `MemoryIdempotencyStore` per request (a thread-local set by `TestSupport.handler`), seeded from `Veld-Test-Idempotency` before the first `begin` (`stored`: the problem document of the error, whose title is the name in its signature, or the stored body with its `ETag`; `other`; `running`), and the caller is `Veld-Test-Principal` as canonical JSON, or `caller`.

### 13.3 The client

A client request record has two components after the declared parameters: `IfMatch ifMatch` (an endpoint with a guard) and `String idempotencyKey` (an `@idempotent` endpoint). `null` sends no header. They are not parameters: they are not in `toWire()`, not in the `EndpointSpec` and not in the local validation. `ClientCore.call(spec, wire, ClientCore.conditional(ifMatch, header, key))` sends `If-Match: "3"` or `*` and the key under the header of the annotation; the client checks the syntax of neither. A record with these components has no `fromWire` (a client never reads a request from the wire), has no no-argument convenience method, and, for `required: true`, a canonical constructor that refuses a `null` key (`NullPointerException`), which is how Java requires it by type. A declared parameter whose Java name is `ifMatch` or `idempotencyKey` on an endpoint that takes the component is `E0801`, in the client and the server.

### 13.4 Choices where `spec/rules.md` was silent

- `IdempotencyStore` is synchronous, and its `Begin` is a sealed interface with four records, not an enum with a payload.
- `StoredAnswer.body` is a `byte[]`; an answer without a body has an empty array, and a replay of an empty body sends none.
- The `version` argument of the handler is after the facts and before the `transition`. It is a boxed type because it is `null` when nothing was compared.
- `IfMatch` is a class with two factories, not a union of a number and a constant: `IfMatch.of(version)` and `IfMatch.any()`.
- A service with `@idempotent`, a guard or an `ETag` and no other endpoint rule has a test handler (`spec/rules.md` 11.12); before that rule it had none. Its handler is `testing = true` only: production bytes do not change.
- **A failing `caller` hook** is a failing `begin`: the hook runs in the same place (before the store is asked), an exception from it is `500 Internal`, the store is not asked, the handler is not called, and the exception goes to `onError` (11.12). A hook that returns `null` is the same (`IllegalStateException`).
- **`validate = false`** keeps the guard, the syntax of `If-Match` and the key checks (11.10): they run in `Router` step 5 and in `EndpointRules.Run.version`, neither of which reads the validation switch.
- **The order of the handler's arguments** is the facts, `version`, `transition`, then the context (11.12): `request_params` in `server.rs` writes them in that order and `extra_args` passes them in that order.
- A request with a header issue and a violated rule of its body is one `422` (the reference's answer), with the header issues first.
- The fingerprint does not normalise scalars (section 13.2); the reference's goldens are all lower case.

### 13.5 Tests

`tests/conditional.rs` with the drivers `tests/toolchain/java/rules/{VersionStubs,VersionServe,IdempotencyStubs,IdempotencyServe,VersionHttp,IdempotencyHttp,IdempotencyFingerprint,ConditionalClient}.java` and `spring-version`, `spring-idempotency`: every example of the two vector files (19 and 21) through the generated test handler on the JDK server and on Spring; `VersionHttp` (a tag that matches, a stale tag and its body, `*`, no header, every malformed form, the `Long` and `Integer` the handler receives, the `ETag`, the order policy, version, transition, `require`, an endpoint that ignores `If-Match`); `IdempotencyHttp` (a new key, a replay with the handler not called and no fact loaded, other parameters, a running request, a stored error, a `500` that is not stored, a required and a malformed key, a replay before the guard, two callers, the hooks that fail at creation, a store that fails, a caller hook that fails); `ConditionalNoValidate` (the contract generated with `validate = false`: the rules of the request are off, the key, `If-Match` syntax, the stale tag, `*` and the version the handler gets stay on); `LiveOnlyHttp` (the test handlers of a key-only and of an `ETag`-only service: probe, dry run, the store state from `Veld-Test-Idempotency`, the result and its `ETag`); `IdempotencyFingerprint` (the goldens of `crates/veld-rules`); `ConditionalClient` (the headers); snapshots of a small contract; `javac -Xlint:all -Werror` for every role, with and without `testing`, for the vectors and the four contracts of the conformance kit (which have no endpoint rules); and `check_version_is_generated` and `check_idempotency_is_generated` in `tests/conformance.rs`.

## 14. Runtime config (`spec/runtime-config.md`)

A target that has settings (a client target; a server that consumes a service or has `rules.output`) gets a typed runtime config. The shared model decides which: this generator no longer decides "has rules" for `rules.output` itself.

### 14.1 Files

| File | Content |
|---|---|
| `runtime/RuntimeCheck.java`, `runtime/VeldConfigException.java` | the check and its error; emitted only for a target with settings, identical in every such target. |
| `<base>.runtimeconfig.<Target>Runtime` | the immutable runtime config. |
| `<base>.runtimeconfig.<Target>Clients` | every client of the target (not generated when the target has no URL). |
| `<base>.adapters.<Target>RuntimeProperties` | `framework = "spring"` only. |

A target without settings emits none of these, and its runtime classes are the ones of before (`ClientCore` keeps the environment fallback; it has no client to use it). The package `runtimeconfig` is reserved: a contract package of that name gets a `_`.

### 14.2 API

- `<Target>Runtime.builder()` has one method per setting, named after the path in camel case without `services` (`iamUrl`, `rulesOutput`; `rulesOutput` takes a `RuleWalk.OutputMode`). `build()` runs the check. The getters have the same names; `rulesOutput()` is `STRICT` when not set.
- `fromMap(Map<String,String>)` (keys are the paths), `fromEnv(Map<String,String> names)` (reads `System.getenv()`), `fromEnv(names, env)` (the same over an explicit map), and `fromValue(Object)` (the nested maps and strings a JSON or YAML parser gives; added by this target so the nested goldens run through the generated check). All end in the one check; a problem is a `VeldConfigException` with `problems()` (a `Problem(path, message)` each) and the error text of `spec/runtime-config.md` section 4.
- `ensure(runtime)` returns the config, or, for `null`, the config without any value, which throws when a path is required. Every generated function that receives a runtime config calls it first.
- `<Target>Clients.create(runtime, options)` (and `create(runtime)`) builds one client per service with `options.withBaseUrl(url)`; the getters are named after the services (`iam()`). `ClientOptions.withBaseUrl` is public for that.
- A server's `<Service>Handler.create(impl[, loaders], hooks, runtime)` takes the config last. When no path is required, `create(impl[, loaders], hooks)` and, when the service needs no hooks, `create(impl[, loaders])` remain and `null` stands for the defaults; when the service needs no hooks `create(impl[, loaders], runtime)` exists too. `<Service>TestHandler.create` has the same overloads. The mode of `rules.output` reaches the router through the package-private `<Service>Hooks.build(runtime)`; `<Service>Hooks.rulesOutput` exists only for a server whose model has no `rules.output`.
- With `framework = "spring"`, `<Target>RuntimeProperties` is a `@Component` and `@ConfigurationProperties(prefix = <runtime-prefix>, ignoreUnknownFields = false)` with a `services` map (`veld.services.<service>.url`) and `rules.output`; `toRuntime()` hands the values to `fromMap`. The controller and the WebSocket configuration of each service take the properties bean and pass `toRuntime()` to the entry. Spring Boot is needed for this class, as `spring` already means Spring Boot 3. A service name with a `-` is bound from `application.yml` or properties files; an environment variable cannot spell it (Spring's relaxed binding drops the dash).

### 14.3 Choices where `spec/runtime-config.md` was silent

- The classes live in `<base>.runtimeconfig`, not in `<base>.runtime`, so that the runtime stays identical in every target.
- `VeldConfigException` is unchecked.
- `rules.output` forces the rule classes (`Flags::rules`) of the runtime, whatever the generator's own predicate says.
- Where the shared model differs from this generator's old predicate: a server that only **consumes** a service with rules, or only has policies or `@rollout`, has the output mode for the old predicate and none for the model, so it gets no `rules.output` and keeps `<Service>Hooks.rulesOutput`. A server whose services have only invariants on declarations the old predicate did not reach (an unreached declaration of a package it does not serve) is the other direction. Every other use of the generator's own predicate (which runtime classes and members are emitted) is unchanged.

### 14.4 Tests

`crates/emitters/java/tests/runtime_config.rs` (snapshots of the runtime module of a consuming server with rules, of a client target and of the Spring properties class; the entries; the gate; the goldens of `tests/wire/runtime-config/cases.json` through `tests/toolchain/java/runtime-config/RuntimeConfigGolden.java`, one generated target per model) and `tests/toolchain/java/Roundtrip.java` (client requires `baseUrl`, `GenAClients.create`).

# Generated output: what each target writes and how to import it

This guide answers two questions: what does `veld generate` put in a target's `out` folder, and how
do you import it from your code. A second half explains how Veld manages those files so it never
destroys anything of yours.

The examples use [`examples/hello`](../../examples/hello) (one Node server, one React client) and
[`examples/microservices`](../../examples/microservices) (Node servers, a Java server, a React app).
Their generated output is committed, so you can read it. The normative file layouts are in
[`spec/targets/typescript.md`](../../spec/targets/typescript.md) (the `node` and `typescript`
emitters) and [`spec/targets/java.md`](../../spec/targets/java.md).

## The rules every target follows

- **Veld writes only inside `out`**, and only files that start with `// Code generated by veld. DO NOT EDIT.`
  (plus `package.json` and `.veld-manifest.json`). Your code lives outside `out`.
- **Zero runtime dependencies.** Generated code imports nothing but the language's own library. The one
  exception is the file of the framework you chose (`nest`, `react`, `vue`, `spring`), which imports
  that framework and nothing else.
- **Deterministic.** The same contracts give the same bytes: no timestamps, absolute paths or host names.
- **Equality by signature.** Every model, enum, union and error carries a signature that the compiler
  computed, so `NotFound` from `orders` is never confused with `NotFound` from `payments`, in any
  language or generated copy.
- **Unsupported is loud.** If a target cannot represent a contract feature it stops with `E0801` and writes nothing wrong.

## Node server (`emitter = "node"`, `role = "server"`)

```toml
[server]                     # in the veld.toml of the service `hello`
name = "api"
emitter = "node"
framework = "express"        # express | fastify | hono | node-http | nest
out = "server/src/generated"
```

```
server/src/generated/
  package.json              name @veld/api, private, no dependencies
  index.ts                  barrel: models, errors, service interfaces, handlers, adapters, clients
  runtime/veld.ts           errors, canonical JSON, validation, the router
  prelude.ts                prelude errors (NotFound, Unauthorized, ValidationError, ...)
  models/hello.ts           one file per contract module: types plus validators
  server/hello.ts           HelloService (interface you implement), request types, createHelloHandler
  server/adapters.ts        toExpress, toFastify, toHono, toNodeHttp
  .veld-manifest.json
```

After `veld generate` and `veld setup`, the app imports the package, never a relative path. You
implement the generated `<Service>Service` interface and give it to `create<Service>Handler`, which
runs the whole pipeline (routing, auth, middleware, validation, declared-error mapping) before
calling you:

```ts
import express from 'express';
import { NotFound, createHelloHandler, toExpress } from '@veld/api';
import type { GreetRequest, HelloService } from '@veld/api';

const hello: HelloService = {
  async greet({ name }: GreetRequest) {
    if (name.toLowerCase() === 'nobody') throw new NotFound({ resource: name });
    return { message: `Hello, ${name}!` };
  },
};

const app = express();
app.use(toExpress(createHelloHandler(hello)));
```

The handler is framework independent. Pick the adapter that matches your server:

| `framework` | Mount it with | Notes |
|---|---|---|
| `express` | `app.use(toExpress(handler))` | Reads `req.body` if a body parser ran, else the stream |
| `fastify` | `app.all('/*', toFastify(handler))` | A catch-all route; streams need `reply.raw` |
| `hono` | `app.use('*', toHono(handler))` | Web-standard `Response` |
| `node-http` | `http.createServer(toNodeHttp(handler))` | No framework at all |
| `nest` | `OrdersVeldModule.forRoot({ useClass: OrdersImpl, hooks })` | Real `@Controller` routes (Swagger sees them). Import `@veld/<target>/server/nest/<service>`. Needs `experimentalDecorators` and `emitDecoratorMetadata` in `tsconfig.json`, only for those files. Peer dependency: `@nestjs/common` |

The four plain adapters are all in `server/adapters.ts` whatever you choose, and they use
structural types, so no framework package is imported. Auth and middleware are hooks you pass as
the second argument: `createCardsHandler(impl, { auth: { bearer: authenticate } })`. Leaving out a
hook the contract needs is a compile error.

A contract with `ws` endpoints adds `server/ws.ts` (`attachWebSocket(new WebSocketServer({ server }), handler)`),
and the `package.json` lists `ws` as a peer dependency, only then. SSE (`get ... -> stream T`)
needs nothing extra.

## TypeScript client (`emitter = "typescript"`, `role = "client"`)

```toml
[client]
name = "web"
emitter = "typescript"
framework = "react"          # react | vue | omit for the plain client
out = "web/src/generated"
```

```
web/src/generated/
  package.json              name @veld/web; peerDependencies: react (only with framework = "react")
  index.ts                  barrel
  runtime/veld.ts           same bytes as the server runtime
  runtime/react.ts          only with framework = "react" (runtime/vue.ts for vue)
  prelude.ts
  hello/models/hello.ts
  hello/client.ts           HelloClient
  hello/react.ts            VeldProvider and the hooks (hello/vue.ts for vue)
```

Plain client:

```ts
import { HelloClient, NotFound } from '@veld/web';

const client = new HelloClient({ baseUrl: 'http://localhost:3000' });
const greeting = await client.greet({ name: 'Ada' });
```

`ClientOptions` take `baseUrl`, `auth` (`{ bearer: () => token }`, also `basic` and `apiKey`),
custom `headers`, a `fetch` implementation, a `webSocket` constructor and `validate` (default
true). Every call also takes an optional `{ signal }` to abort it. The base URL resolves from the constructor argument first,
then the environment variable `VELD_<SERVICE>_URL` (upper snake case), then the `base-url` in
`veld.toml`; with none of them the constructor throws. Declared errors come back as typed classes:
`NotFound.matches(e)`.

With a framework, the hooks are **not** in the barrel (so importing the barrel never needs React
or Vue installed). Import them from the per-service path:

```tsx
import { HelloClient } from '@veld/web';
import { VeldProvider, useGreet } from '@veld/web/hello/react';

const client = new HelloClient({ baseUrl: window.location.origin });

<VeldProvider clients={{ hello: client }}>
  <Greeter />
</VeldProvider>

// in Greeter:
const greeting = useGreet(name === '' ? null : { name });  // null holds the request back
// greeting.data, greeting.loading, greeting.error, greeting.refetch
```

`framework = "vue"` gives composables from `@veld/web/hello/vue` that run in a Vue 3.3+ effect scope.
Both abort the request on unmount.

### Query options (`query-options = true`)

```toml
[client.options]
query-options = true
```

adds `hello/queries.ts`: plain query-key, query-options and mutation-options objects (no import of any
package). They have the shape TanStack Query's `useQuery`, `useMutation` and `invalidateQueries` take,
and work with SWR or your own hook too:

```ts
import { helloQueries, helloMutations } from '@veld/web';

const greeting = useQuery(helloQueries.greet({ name }));        // GET endpoints are queries
helloQueries.keys.all;                                          // ['veld', 'hello'], for invalidation
helloQueries.greet({ name }, myClient);                         // or pass the client explicitly
```

Keys are built from the canonical request bytes, so equal requests share a key. Streams have no query
form.

### Skipping request validation (`validate = false`)

`validate = false` in `[server.options]` or `[client.options]` of a `node`, `typescript`, `java` or `rust` target skips run-time
request validation by default; the types stay. The TypeScript client option `validate: true` and the
Java `ClientOptions.builder().validate(true)` (Rust `ClientOptions::new().validate(true)`) switch the client check back on.

## Java (`emitter = "java"`, server and client)

```toml
[server]                     # in the veld.toml of the service `transactions`
name = "transactions-api"
emitter = "java"
framework = "jdk"            # jdk | spring (servers only)
out = "src/main/java"

[server.options]
package = "com.nexusbank.transactions"
java = "17"                  # "17" or "21"
```

Java has no npm. Files go under `out` in the packages below the base package you set:

```
<base>.runtime                     runtime (own JSON parser; no library)
<base>.prelude                     prelude errors
<base>.<package>.<module>          models (records), enums, unions (sealed interfaces), errors
<base>.<package>.client            <Service>Client and <Operation>Request records     (client)
<base>.<package>.server            <Service>Service, <Service>Hooks, <Service>Handler  (server)
<base>.adapters                    JdkHttpServerAdapter or SpringAdapter              (server)
<base>.clients.<service>.*         a client tree for each consumed service            (server)
```

`veld setup` makes the folder a source root of your Maven (`build-helper-maven-plugin`) or Gradle
(`sourceSets.main.java.srcDir`) build, unless `out` is already `src/main/java`. Then you import the
generated packages like any others and implement the service interface:

```java
import com.nexusbank.transactions.adapters.JdkHttpServerAdapter;
import com.nexusbank.transactions.runtime.VeldHandler;
import com.nexusbank.transactions.transactions.server.TransactionsHandler;
import com.nexusbank.transactions.transactions.server.TransactionsHooks;

VeldHandler handler = TransactionsHandler.create(
    new TransactionsServiceImpl(), new TransactionsHooks(TransactionsServiceImpl::authenticate));
JdkHttpServerAdapter.listen(handler, new InetSocketAddress(host, port));
```

With `framework = "spring"` (Spring Boot 3, Jakarta) Veld emits one `@RestController` per service
at the real paths, instead of the JDK adapter. Register your `<Service>Service` (and
`<Service>Hooks`) as beans and component-scan the generated `adapters` package. Needing
WebSocket on the JDK adapter is `E0801` (the JDK has no WebSocket server); choose `spring`.

A Java client:

```java
OrdersClient client = new OrdersClient(ClientOptions.builder()
    .baseUrl("https://api.example.com").bearer(() -> token).build());
Order order = client.getOrder(new GetOrderRequest(id));
```

Declared errors are unchecked exceptions. Inside one generated package `catch (OutOfStock e)`
works; across packages use `OutOfStock.matches(e)` or `Veld.same(a, b)`, which compare signature,
operation and canonical bytes.

## Rust (`emitter = "rust"`, server and client)

Rust output is a complete Cargo crate. Point `out` at an empty folder and add it to your workspace
(`veld setup` is not needed: `members = ["generated/orders-server"]` or a `path` dependency is enough).

```toml
[server]                     # in the veld.toml of the service `orders`
name = "orders-api"
emitter = "rust"
out = "generated"

[server.options]
crate-name = "orders-api"    # default: <package>-<role>
```

```
Cargo.toml                         serde + serde_json, and the framework you chose, nothing else
src/veld/                          the runtime: schemas, validation, canonical bytes, same(), the server and client cores
src/prelude.rs                     prelude errors
src/<package>/<module>.rs          models (structs), enums, unions (enums), errors, constants
src/<package>/<service>_server.rs  <Service>Service, <Service>Hooks, <Service>Handler   (server)
src/<package>/<service>_client.rs  <Service>Client<T> and its request structs           (client)
src/adapters/axum.rs               router(handler)                                      (server, framework = "axum")
src/clients/<service>/...          a client tree for each consumed service              (server)
```

The server implements the generated trait and mounts one route per endpoint with axum:

```rust
use orders_api::adapters::axum::router;
use orders_api::orders::orders_server::{OrdersHandler, OrdersService};

impl OrdersService for Orders {
    async fn get_order(&self, request: GetOrderRequest, ctx: &RequestContext) -> Result<Order, veld::Error> {
        self.find(&request.id).ok_or_else(|| NotFound { resource: Some("order".into()) }.into())
    }
}
let app = axum::Router::new().merge(router(OrdersHandler::create(Orders::new(), Hooks)));
```

A declared error is returned as `Err(NotFound { .. }.into())`; anything else becomes `Internal` without
its message. The client is generic over its HTTP stack, so you bring your own, or take an adapter
(`framework = "reqwest"`, the default, or `"ureq"`, blocking):

```rust
let client = OrdersClient::reqwest(ClientOptions::new().base_url("https://api.example.com").bearer(|| token()))?;
let order = client.get_order(GetOrderRequest { id }).await?;
match client.cancel_order(CancelOrderRequest { id }).await {
    Err(e) if NotFound::matches(&e) => { /* e.op() is the operation, NotFound::from_error(&e) the typed value */ }
    other => other?,
}
```

`veld::same(&a, &b)` compares signature, operation and canonical bytes; across two generated crates
build `veld::Identity::of(&a)` in each and compare with `veld::same_parts`. `datetime`, `uuid` and
`decimal` are `String`s in the generated types, so the crate needs no `chrono`, `uuid` or decimal
dependency. See [`spec/targets/rust.md`](../../spec/targets/rust.md).

## Consumed services

For every service in `consumes`, a server target also generates a client for it, in the same
language, so a service can call its dependencies without any other setup. In TypeScript they come
through the same package as namespaces; in Java they are under `<base>.clients.<service>`:

```ts
import { createAccountsHandler, iam, transactions } from '@veld/accounts-api';
const profile = await new iam.IamClient({ auth: { bearer: () => token } }).getProfile({});
```

Set `clients = false` on the target to opt out. See [microservices.md](microservices.md).

## Exports

`veld export openapi -o openapi.json` writes OpenAPI 3.1 for the whole project (add `--service S` for one
service). `veld export ir` prints the compiled IR with signatures, for plugin authors. Both print to
stdout without `-o`.

### Rules in the OpenAPI export

A contract without rules exports exactly as before. Business rules appear as `x-veld-*` extensions,
so the document doubles as living documentation (all expressions are printed as Veld text):

- a model or error schema with invariants has `x-veld-rules`: a list of `{name, id, message?, fields,
  expression}`, where `fields` are the wire names the rule reads (a child lists only its own rules);
- an operation has `x-veld-facts` (`{name, type, optional}`), `x-veld-rules` (`requires`:
  `{name?, id, expression, else?, message?}` and `ensures`: `{name?, id, expression, message?}`) and,
  when it has a `transition`, `x-veld-transition` (`{id, field, from, to}`, wire values);
- an enum that is a state machine has `x-veld-flows` (`{from, to}`, wire values) and `x-veld-finals`.

The implicit `404`, `409` and `422` answers are documented as the other implicit errors are: when the
compiled contract lists them for the operation.

## The manifest and your files

Every `out` folder gets a `.veld-manifest.json` that lists the files Veld wrote and the SHA-256 of
each:

```json
{
  "version": 1,
  "generator": "veld 2.0",
  "files": {
    "index.ts": "ec619edcd0cdc677cf3bb3169b2521f87f852a35659cf764baa1fa09aafb0572",
    "server/hello.ts": "68b4a434dbf8d1c9505efa0d75ba1da763f4379fbdae161d9eccc90d1f21b26d"
  }
}
```

Commit it with the generated code if you commit generated code. A file that is not listed belongs
to you.

### What `veld generate` does

1. Compile the contracts. If that fails, nothing on disk changes.
2. Check every `out` folder: two targets may not share one (`E0703`), and an `out` may not be the
   project root or a contracts folder (`E0704`).
3. Write all files into a hidden staging folder, `.veld-staging-*`, inside `out`. A stale one from an
   interrupted run is removed first.
4. Compare with the manifest. New files are created, changed files replaced, identical files left
   untouched (their modification time does not change), and files that are no longer generated are deleted.
5. Only if everything succeeded are the files moved into place, then the manifest and
   `veld.lock.ir.json` (the contract snapshot used by `veld diff`) are written.

```
✓ api -> server/src/generated: 7 created, 0 updated, 0 deleted, 0 unchanged
✓ web -> web/src/generated: 8 created, 0 updated, 0 deleted, 0 unchanged
2 targets, 15 files changed in 21ms
```

### Files you edited

A listed file whose content no longer matches the manifest hash is **user-modified**. Generate
refuses to overwrite or delete it and writes nothing for that target:

```
error: target `api`: 1 generated file(s) in `server/src/generated` were edited since Veld wrote them; nothing was written
  you edited generated file: server/hello.ts
  keep your edits elsewhere, or re-run with --force to overwrite them
```

Keep your edits outside `out`, or pass `--force` once to take the generated version. `--dry-run`
reports the same thing and writes nothing.

### Files Veld did not write

A file in `out` that the manifest does not list is never overwritten or deleted. If generated output
would land on top of one, the run stops and reports it as a conflict; `--force` replaces it.

### `veld clean`

Removes the unmodified generated files. Files you edited are kept, and the manifest left behind lists only
them with their original hashes, so a later `generate` still recognizes them as yours.
`veld clean --dry-run` shows what would go.

### Commit or ignore?

Both work. Committing the generated code (as the examples do) makes pull requests show what a
contract change does to the code, and lets CI prove it is up to date with `veld generate --check`
(see [ci.md](ci.md)). Ignoring it means every checkout runs `veld generate` before building. Always
commit `veld.toml` and `veld.lock.ir.json`.
